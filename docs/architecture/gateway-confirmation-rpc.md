# G6b-2d：Gateway 与同步器的隔离确认通信

> 2026-09-08。已实现跨进程确认、两端独立持久记录和失败时保持屏障。仍无热副本删除、冷驻留发布、回温或业务流量接线。

前置：[精确冷层确认](gateway-cold-confirmation.md)。本轮不是把 Server 心跳升级成执行授权，也不是自动接管协议。

## 1. 本轮交付与实际边界

- 同一个 `redis-syncer` 二进制新增显式 `-confirmation-config` 模式，与原 `-config` 互斥。普通同步服务的配置、回放白名单、部署和路由不变。
- 确认模式独占一个**已有的、停止捕获后的 named 源日志**，提供单任务、单未完成操作的 HTTP 确认接口；不启动 PSYNC、不继续普通回放、不清理日志。不能与原同步任务同时打开同一日志。
- Gateway 包新增独立客户端适配器，保存自己的意图/准备证据/确认结果；不打开同步器源日志，不读取其操作文件。重开时先恢复 key 屏障，每次确认都在线核验。
- 真实测试启动了独立 `redis-syncer` 二进制和先后运行的 Gateway 客户端测试进程。**Gateway 客户端当前由隔离调用方调用，不是 `cmd/gateway` 已经拦截业务请求。** 初始意图、热端准备标记和源捕获仍由隔离测试编排，未提供线上降冷入口。

因此本轮交付的是跨进程确认实验闭环，不是“持续同步器可以自动停在任意操作处、确认后继续运行”。在运行循环中管理准备标记、捕获推进和恢复仍需下一阶段实现。

## 2. 谁负责什么

| 组件 | 本轮职责 | 不能当作什么 |
| --- | --- | --- |
| Gateway 适配器 | 关闭目标 key 准入、等待在途请求结束、请求确认、核验回复、fsync 本地结果 | 线上所有命令已经经过此屏障 |
| 同步器确认模式 | 独占源日志、定位准备事件、检查实时源角色/历史、执行精确冷确认、fsync 同步器操作日志 | 自动所有权转移或删除热数据 |
| Server | 保持原来的固定登记/观测功能，本轮未修改 | 确认路由发现、执行授权或租约 |

Gateway 成功、失败、断连、取消都不会解除本轮屏障；关闭对象会终止整个屏障集合。重新打开时从本地意图恢复保护。恢复成功后也仍需重新请求同步器，不因存在本地 receipt 就宣称可删除。

仅适用于单执行者、独占冷 DB、无 TTL String。不能用多个进程的本地屏障代替全体业务入口的分布式准入控制。

## 3. 固定绑定、启动身份与认证

双方固定绑定以下字段：`syncer_id / gateway_id / task_id / source / cold / history / epoch`。绑定摘要来自规范 JSON；源和冷端点为规范化字面量 loopback 地址。

每端操作目录先持久保存 `confirmation-binding.json`，并持有文件独占锁。文件和目录分别要求当前用户所有的私有普通文件 0600、目录 0700；拒绝符号链接终点、多硬链接、截断和内容变化。绑定缺失而操作文件仍存在时拒绝自动认领；可能留下空的拒绝恢复文件，需要显式核查，不自动修复。

修改固定配置不能覆盖已有绑定。归属变化必须另行核查、隔离旧执行者并交接；不得删除绑定文件、改一个 epoch 就当成完成 fencing。

同步器每次启动生成随机 `boot_id`。客户端先取得当前会话，POST 必须带相同会话；重启后旧会话返回拒绝。收到确认后客户端再次检查会话，再持久化结果。这个检查只能发现观察到的重启，不是有效期租约，也不能证明之后不会切主。

接口使用独立 Bearer token 文件，至少 32 个可打印非空白 ASCII 字符；不支持空 token，不复用可空的 Proxy 内部凭据。禁止重定向、环境 HTTP 代理、DNS 和跨机明文端点，客户端也拒绝误指向 Redis/Kvrocks 后端端口。

当前只允许受信任本机的 loopback HTTP，不提供远端 TLS/mTLS。token 校验不是客户端对任意本机冒充服务的密码学身份证明；本机账号、端口和配置仍在信任边界内。跨机和真正执行授权待实现。

## 4. 具体请求流程

接口路径：`/internal/v1/cold-confirmation`。

1. `GET` 返回协议版本、绑定摘要、当前 `boot_id`；这是会话信息，不代表后端就绪。
2. Gateway 在屏障排空后 `POST` 会话和完整意图。它不提交“请相信这个 offset”、源日志字节或冷层 ACK。
3. 同步器在自己的已验证日志中查找唯一的精确准备记录，核验实时 Redis 仍是预期复制历史的主节点，源位置不低于准备事件。
4. 同步器打开固定 `confirmation-operation.log`，同操作才允许重试；记录准备证据，复用 G6b-2c 应用到准备标记之前、提交 Kvrocks 确认并本地 fsync。
5. 再核验实时源历史，返回会话、请求摘要、准备证据和 receipt。错误统一返回固定文案，不包含 key、路径、后端回复或 token。
6. Gateway 验证请求摘要、完整会话、意图、准备记录和前后 checkpoint 链；再次检查会话，然后把准备证据与 receipt 写入自己的操作日志并 fsync。这里信任受控同步器提供源证明，但不假装 Gateway 自己读取了源日志。

规范 JSON 拒绝未知字段、重复字段、额外文档，双向 body 上限 512 KiB。服务端一次仅执行一个请求，忙时拒绝，不建立无限操作队列；读请求、后端请求、整个确认和退出均有时间限制。

确认的重复请求会重新核验 Kvrocks，而不是直接返回缓存成功。冷层已提交但 HTTP 回复丢失时，Gateway 不保存成功凭据；重试恢复同步器自己的记录并在线重新核验，不重复 INCR。

客户端串行确认，等待屏障排空也包含在总超时内。热写结果未知会隔离该 key，不向同步器发确认；成功后也不解锁，不存在超时自动回温或自动 UNLINK。

## 5. 运行方式

示例：[syncer-confirmation-isolated.yaml](../examples/syncer-confirmation-isolated.yaml)。必须先替换实际 task/history/端点/私有凭据，准备独占冷 DB 和已有源日志，并停止原捕获/回放任务。

```sh
redis-syncer -confirmation-config /absolute/path/confirmation.yaml -check-config
redis-syncer -confirmation-config /absolute/path/confirmation.yaml
```

`-check-config` 严格校验 YAML 和凭据文件，但不打开源日志、不创建操作目录、不监听、不访问后端；因此成功不意味着持久日志可恢复。运行时先监听，再独占已有日志；缺失或无历史的日志不能作为新任务自动创建替代。

操作目录必须事先创建为 0700，不能与源日志目录重叠或经符号链接指向同一位置。运行退出会停止 HTTP、等待当前请求结束，再释放日志锁。原同步器配置和确认配置不能混用，不能启动两个模式争抢日志来模拟自动交接。

## 6. 验证

本地测试包括：真实 HTTP 客户端与模拟响应、鉴权、消息大小/重复字段、错误摘要/准备证据/receipt、重定向、丢回复、启动身份变化、本地 fsync 异常、屏障排空/未知热写、绑定持久恢复和配置只读检查。相关 race 测试连续三轮通过。模拟响应测试不等同于真实冷提交验证。

真实后端测试 `TestConfirmationProcessKvrocks` 使用独立 `redis-syncer` Linux 二进制与 Gateway 客户端测试子进程，覆盖：

- 真实 RDB/PSYNC 捕获、41 → INCR → 42、准备标记之前的精确应用。
- 冷层与同步器日志已确认后故意丢弃 HTTP 回复，Gateway 不记录成功；显式重试成功。
- 重复确认，两个先后运行的 Gateway 客户端进程恢复确认，成功后仍保持 key 屏障。
- 同步器进程强杀，离线时拒绝以本地 receipt 放行，重启后新 boot 在线核验；旧 boot 请求拒绝。
- 冲突意图拒绝；实时源变为从节点、随后提升产生新复制历史，旧确认均拒绝。
- 原捕获日志不能被另一个进程同时打开，冷热 counter 仍是 42，冷层不存在标记之后的业务 key，未删除热副本。

测试在 redis03 新建专用 `redis-pilot-rpc-cold-IXxg6k` 和 `redis-pilot-rpc-hot-IXxg6k` 容器，无宿主机端口，分别限 512 MiB/128 MiB。冷层 Kvrocks 2.15.0 开启同步 WAL；热层 Redis 7.2.5。未升级现有服务或变更业务路由；测试后停止专用容器并保留二进制供复查。每轮临时日志由测试清理，不作为长期留存证据。

实际命令、二进制摘要与最终结果见 [验证记录](benchmarks/g6-confirmation-rpc-20260908.log)。不是压测、断电验证、生产接管验收或完整 Redis 语义测试；不宣称生产热写延迟无损耗。

## 7. 下一步与待定项

首先把准备/确认状态纳入持续同步任务生命周期，确保运行中识别屏障、保持源日志、确认期间恢复以及有界停止，再接真实 Gateway 请求准入与热端准备操作。Server 权威任务配置、同步器地址发现、认证传输、明确的执行归属与代际隔离也尚未实现。

之后才接持久热副本移除、冷驻留发布与恢复。确认凭据只说明指定意图对应的数据曾在冷层被核验提交，后续该 key 再写、切主或所有权变化都会使它不再足以授权删除。自动 LRU、回温、TTL、复杂类型、Cluster 迁移和 FULLRESYNC 后冷层数据保护仍待实现/细化。
