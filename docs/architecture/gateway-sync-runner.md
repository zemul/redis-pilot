# G6a-8：隔离持续同步循环

后续进展：本阶段已提交 `19bc7b3`；[G6a-9 启停与观测](gateway-sync-lifecycle.md) 增加显式优雅停止和只读指标。下文“本轮”与未实现事项保留 G6a-8 验收时点；运行服务仍未接线。

## 范围

前序 G6a-7 已提交到 `dev`：`2cb02e7`。本轮把已有的 Redis 复制捕获、分段日志、冷层 pending 恢复、确认回收和孤儿清理串联成可显式调用的 `syncRunner`。

**仍是隔离原型，不是可部署的冷热功能。** 没有修改 Gateway 服务入口、配置、Server API、Agent 或 Proxy 路由；没有部署运行服务。热层仍须保存完整业务数据，禁止提前开启淘汰。实验目标限定为独占的 loopback Redis 和 Kvrocks，不能用于共享冷库。

## 执行与所有权

调用方提供已经打开的分段日志与 context。循环先校验参数、源凭据和源历史身份，再应用/核对已有日志、确认回收、清理孤儿并检查资源，然后才开始新的复制捕获。新日志必须先确认冷库为空；实际 bootstrap 时再次验证。启动失败不会先接入 Redis 并积累新数据。

一个循环只运行一个捕获协程，冷层应用、确认回收和目录清理由主循环串行调度。捕获内部 ACK 协程在捕获结束前回收。退出、冷层连接退避和资源暂停都会取消并等待捕获结束，不留下继续追加或发送 ACK 的旧协程。

同一个 runner 或同一个日志句柄不能同时启动两个循环；日志目录还保留既有文件锁。这只是进程内生命周期和本地文件锁保护，**不是分布式租约或 fencing**。调用方必须遵守独占所有权，不得绕过循环直接调用捕获/应用，也不能在循环返回前关闭日志。

循环不会自行关闭/重开日志，不会自动修复 poison 状态，不会重建冷库。显式重启仍先走 pending/历史校验，不能用“重启成功”替代恢复证据。

当前 context 取消是即时中断，不是“等当前事务提交完再停”的优雅排空。若取消正好打断 EXEC，也会保留结果不确定的终止状态，需要下次明确启动/对账后判断。不能把所有人为停止都显示为成功。服务化的优雅停止超时与强制停止策略待定。

## 重试边界

| 情况 | 行为 |
| --- | --- |
| 源连接、握手或读取发生网络中断 | 从本地已 fsync 的位置 PSYNC 续传，有上限的指数退避 |
| 冷层 open 阶段的 Dial/AUTH/INFO/CONFIG GET 发生网络中断 | 停止并等待源捕获，退避后重新校验冷层 |
| 捕获前资源水位拒绝 | 暂停捕获；继续冷层应用、确认与清理，条件恢复后续传 |
| 冷层提交回复丢失、结果不确定 | 终止循环，不自动重试业务写；明确重启后凭 pending/before/after 校验恢复 |
| 源历史缺口、协议或命令不支持、状态偏差、日志损坏/真实写失败 | 终止并保留证据，不跳过记录、不自动 FULLRESYNC 替换已有历史 |
| 日志逻辑容量上限 | 终止；目前该错误也可能代表单条记录过大，不能盲目当成可回收压力 |
| 正常取消 | 等待捕获退出；网络取消可归为停止，但已经发生的不确定提交和其他终态错误仍保留 |

自动重试标记只在已知安全的传输边界产生，不能把任意 EOF 或冷层应用错误统称为可重连。认证拒绝、版本/WAL 配置不合要求和未分类错误都停止。

open 返回后的 pendingMeta、空库 SCAN、WATCH 等阶段，即使只读或尚未提交，其网络错误目前也不自动重试；这是有意收窄的恢复边界。

源重试预算只在捕获位置实际持久化推进后重置，握手成功不算恢复。`MaxRetries` 表示初次尝试之外的额外重试次数。冷层连接恢复后必须重新核对 pending；不能假设上一次连接失败发生在业务写入前。

## 资源暂停与调度

复用 [G6a-7 资源协议](gateway-sync-resources.md)，不改变 Redis ACK 的含义：ACK 只表示本地捕获已持久化，不表示冷层已经提交。未确认复制字节仍以持久化的 Confirmed 为界。

资源检查分为当前状态和本次追加的预测预算。即使当前水位看似恢复，如果下一条记录仍放不下，也保留同一轮压力计时并退避，避免无限重连。实际捕获推进后才解除这种追加压力。超出最长暂停时间返回错误；不借机清空日志或自动重建冷层。

内部默认值仅为原型参数，未接 YAML/API，不是生产推荐值：

| 参数 | 默认值 |
| --- | --- |
| 调度间隔 | 100 ms |
| 连接重试初始 / 最大间隔 | 100 ms / 5 s |
| 额外重试次数 | 8 |
| 孤儿清理间隔 | 5 s |
| 单轮资源暂停上限 | 5 min |

当前退避没有随机抖动；源与冷层操作仍有各自的连接/读取超时。资源暂停上限不是严格实时中断保证：串行进行中的有界操作完成后才继续判断。清理超过目录项预算会停止，不放宽上限偷偷删除。

`snapshot()` 提供进程内状态副本：阶段、Captured/Applied/Confirmed、源尝试/重试次数、冷连接重试次数、资源状态和固定错误类别。没有 HTTP、心跳字段、Prometheus 指标或告警接线；位置差不是精确的时间滞后或丢失量。状态只供观测，不是故障接管授权。

## 验证方法

单测用可控操作覆盖启动顺序、重复启动、重试上限/退避、压力恢复与超时、清理失败、取消竞争、视图释放和退出等待。真实集成使用 redis03 的两个专用容器：Redis 7.2.5 与 Kvrocks 2.15.0，共享隔离网络命名空间，没有宿主机端口。

真实集成用例包括：

- 从 RDB 初始值 41 持续同步到 42；断开复制连接后自动续传到 43；停止并重开日志后消费停机期间写入，得到 44。
- 注入低可用空间，验证捕获暂停而源数据仍可写；恢复采样值后自动续传。没有实际填满主机磁盘。
- 丢弃真实冷层 INCR 事务的 EXEC 回复，循环停止；显式重启核对 42 而不重复加一，后续写入到 43。
- 真实源传播带 TTL 写入时拒绝应用，不静默忽略过期语义。
- 缩小专用源复制 backlog 并写入大值，制造真实历史缺口；拒绝 FULLRESYNC 替换既有冷层数据和本地历史。

最终结果、失败记录和环境收尾见 [执行记录](benchmarks/g6-runner-20260908.log)。这些是正确性与故障测试，不是吞吐、延迟、长期稳定性或主机断电验收。

最终五个真实用例连续十轮通过，原分段/资源/孤儿恢复的十一项回归通过；本地三轮目标 race、网关全包 race、项目全量测试和 vet 通过。测试期间发现并修正网络取消分类和测试退出断言，记录中保留失败经过。两个隔离容器已停止，合成数据清空，既有实例与 Agent 仍运行。本轮 G6a-8 尚未提交；前序 G6a-7 已提交，未推送。

## 当前限制与下一步

- 继承无 TTL String、小 RDB、SET/INCR/单 key DEL 等原型限制；没有 Lua、事务、多 key 命令和其他数据类型兼容性承诺。
- 没有服务接线、Cluster 路由/迁移、所有权 fencing、热层淘汰、回温或冷热目录。
- 捕获等于应用位置且空闲时，不持续探测冷层存活；新增日志或明确重启时才会再次访问冷层。服务化前需要独立的有界健康检查与状态时效定义。
- 源读取超时需要结合 Redis 复制 PING 周期配置。当前短测试不能证明健康但长期空闲的连接不会误触发超时/耗尽重试。
- 暂停会断开复制连接；热层继续写入可能耗尽源 backlog。源故障/历史永久丢失后的人工恢复流程仍待定。
- 冷层长时间故障时，是否限制热层写入、允许的最大滞后和 RPO，仍需业务确认。当前循环不拦截热写，不承诺热层丢失后零丢数据；Redis WAIT/min-replicas 与此复制客户端的相互影响也需单独验证。
- 接入受控运行入口前，应先补齐持续空闲/长故障的验证与可观测性；再扩展命令/TTL 协议。不要直接在现有业务链路上启用当前实验。
