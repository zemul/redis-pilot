# 冷热缓存设计

更新：2026-09-10。本文是新的目标设计，不代表已经实现。当前代码能力见 [实现状态](hot-cold-status.md)，运行限制见 [部署运维](gateway-deployment.md)。

## 方向与职责

Kvrocks 是唯一权威存储，保存完整业务数据；Redis 是可丢弃的热缓存。取消 Redis 先写、PSYNC 异步同步的方案，不维护两份同等地位的数据。

- Gateway 属于数据面：执行路由、缓存读取、回填、失效及一致性协调。独立宿主机二进制，由 systemd 管理。
- Proxy 保留统一接入与路由职责；是否合并 Gateway 进程待定，不因合并而免除缓存协调职责。
- Server 属于控制面：配置、状态与观测；不进入逐请求一致性路径。
- Agent 管理 Redis/Kvrocks 容器，不安装或启停 Gateway。
- 不再提供独立同步器、复制日志、复制位点、冷确认或主动降冷服务。

## 读路径

对明确支持缓存的命令：可信 Redis 缓存命中直接返回；未命中查 Kvrocks；存在则按容量和类型规则回填，不存在则返回不存在。冷层超时/故障不是不存在。

同一个 key 的冷层读取、回填与修改必须协调，避免旧值迟到回填。缓存读失败时可绕过缓存查冷层；已经从冷层读到数据但填缓存失败，不应仅因缓存未填成功而使该次读取失败。

普通热缓存为基础。短期空值缓存可选、需要容量上限和 TTL，创建/修改时也要失效，并参与同样的并发协调；暂不做全量布隆过滤器。

## 写路径与缓存策略

业务命令只在 Kvrocks 执行。写成功依赖冷层确认；持久性取决于冷层 WAL、刷盘及副本配置，不承诺跨库原子事务或 exactly-once。

| 写后策略 | 行为 | 实施顺序 |
| --- | --- | --- |
| 失效缓存 | 冷层修改成功后删除相关热缓存；后续读到再加热 | 第一版默认 |
| 更新已有缓存 | 只更新已经存在且完整的热缓存，不主动创建；不支持安全更新的命令退回失效 | 后续实现后才开放 |

关闭更新热缓存不等于忽略旧缓存。SET、INCR、HSET、HDEL、ZADD 等修改默认统一失效相关缓存；DEL 删除冷层业务数据后失效热缓存。仅内存淘汰只影响 Redis，不向冷层传播。

条件写、错误回复以及结果未知时必须按实际语义处理，不能无条件假定修改成功或未执行。INCR 等命令派发后响应丢失不能盲目重试。缓存失效失败不能通过重放业务修改来修复。

## 一致性与恢复约束

写冷与失效/更新热之间存在间隙。第一版目标是在一个有效 key 负责人内协调同 key 的读、写和回填；不同 key 可并发。锁范围、超时、取消、容量界限以及排队公平性待实现和验证。

- 多个 Gateway 的本地锁不能互相保护；共同归属、切换时旧执行者隔离方案待定。未完成前不允许多个独立写者接管同一缓存范围。
- 冷写成功而失效热失败时，必须让对应缓存不可读，读回落冷层，并自动恢复；不能释放锁后照常读旧缓存。
- Gateway 在冷写后崩溃时，旧 Redis 缓存可能仍在。恢复必须建立新的缓存可信边界；缓存代次、隔离命名空间或受控清理等具体机制待定，不能直接信任旧缓存。
- 不可丢失的协调状态不能依赖会被 LRU 淘汰的缓存 key。不能把普通分布式锁到期当作旧请求已经结束。
- 冷层故障时不能继续确认业务写成功；可信热缓存是否继续服务及一致性等级需明确。普通缓存故障不应永久停服，自动绕过与恢复是验收项。
- 原地更新热缓存时，存在性检查与更新必须原子执行，防止 key 被淘汰后 HSET/ZADD 创建残缺缓存。脚本错误、OOM、部分效果必须按失败路径处理。

## 数据类型、TTL 与容量

第一条完整链路：GET、普通 SET、单 key DEL、INCR。该范围是实施计划，不是当前已支持的冷热功能。

Hash/ZSet 目标采用有界的完整缓存：小对象完整加载并原子发布，大对象暂不缓存。字段缓存/成员缓存暂不做；不能把一次 HGET/ZRANGE 的局部结果当成完整 key。检查大小与加载过程也必须有界，不先无条件读取巨大对象。字段/成员数、字节数、回填并发和频率阈值待测试确定。

业务 TTL 以 Kvrocks 为准；回填不得延长业务有效期。缓存自己的有效期可更短，但不是严格一致性的替代。Hash 字段过期等引擎差异需单独核查。

热层使用配置内存上限与 allkeys-lru，淘汰整个 key；不再由 Gateway 扫描 LRU 或维持 80%/70% 主动降冷水位。需要预留进程额外内存并监控 OOM、命中率与冷层负载。

复杂读取在未实现正确缓存策略前可直接走冷层。多 key 命令、类型覆盖、RENAME、事务、Lua、阻塞命令、SCAN/KEYS 等需要明确影响范围和全局语义，不能因冷层认识命令就直接宣称兼容；支持矩阵与不支持时的行为待定。

## 扩容与性能

冷热容量不要求 1:1。热层扩容允许重新预热，但必须阻止迁移/重启后旧缓存重新可见，并处理重定向和缓存代次。冷层扩容涉及真实数据迁移和命令路由；添加节点不等于自动完成重分片。

Cluster 的 slot 路由、MOVED/ASK、跨 slot 命令、Pipeline 拆分保序、动态配置与负责人切换均待实现。当前固定单后端 Gateway 不能冒充 Cluster 缓存网关。

收益是移除复制及冷热所有权转移复杂度；代价是写延迟和写可用性由 Kvrocks 决定，默认失效模式下修改后首次读也访问冷层。完整功能后再压测，不沿用旧透传/旧同步方案的性能数字。

## 验收要求

覆盖基本命令、并发旧回填、冷写/失效间隙、失效失败、未知写结果、Gateway 崩溃重启、Redis 清空/淘汰、冷层故障及恢复、TTL、类型变化和大对象边界。所有恢复路径应能自动收敛；需要人工介入的真实数据损坏应与普通网络故障区分。
