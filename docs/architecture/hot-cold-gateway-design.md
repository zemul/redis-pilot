# 冷热存储：现行设计

更新：2026-09-09。本文维护当前架构、实现边界和已确认原则，不作为阶段流水账。能力与验收见 [实现进度](hot-cold-status.md)，运行方式见 [部署运维](gateway-deployment.md)。

## 目标与当前结论

在尽量不修改 Redis、Kvrocks 引擎的前提下，热读、热写优先走 Redis，修改异步同步到 Kvrocks；根据内存压力自动移除已同步的热副本，访问冷数据时回温。产品主要面向 Cluster，兼顾扩容期间读写、常见 Redis 命令和自动恢复，重点关注热写延迟与存储成本。

**当前不是完整冷热产品。** 已有单后端转发 Gateway、受限同步服务，以及可通过 `hot_cold` 开发配置启用的无 TTL String 降冷/冷读/回温闭环；可选内存水位后台调度复用同一协议。只有明确启用驻留协议的路径能够处理冷 key，默认 passthrough 不能代理部分热数据集。控制面切流、Cluster 协调与性能验收仍未完成。

## 组件职责

| 组件 | 职责 | 不承担 |
| --- | --- | --- |
| Proxy | 业务接入；未来按拓扑选择冷热 Gateway | 不与 Gateway 重复选择冷热层 |
| Gateway | 热层业务请求；内部模式处理单 key 驻留、回温和手动降冷 | 不内嵌同步器，不逐请求调用 Server 审批 |
| 独立 redis-syncer | PSYNC 捕获、本地日志、Kvrocks 应用和进度/操作确认 | 不处理业务 GET/SET，不按 Gateway 数量复制任务 |
| Server/API | 状态、配置、观测；未来发布拓扑与分配同步任务 | 不维护全量 key 的高频状态，不参与逐次热写 |
| Agent | 管理本机 Redis/Kvrocks 容器 | 不安装、启停 Gateway 或同步器二进制 |
| 运维与 systemd | 独立二进制的安装、升级、启停与开机启动 | 不代表已具备分布式故障接管 |

普通实例继续使用原有 Proxy → Redis 路径，不强制经过 Gateway。冷热实例的目标是单业务入口，热读写访问 Redis 主节点，不默认开启副本读。当前尚未实现 Proxy 自动切入冷热路由。

同步任务未来按 Redis 主分片组织；一个同步器进程可以承载多个任务。当前只有 1～8 个静态隔离任务，每任务独立日志、独占冷 DB；多写者隔离、跨机接管与动态调度未实现。

## 数据路径与一致性边界

### 热读写与同步

Gateway 将受支持请求转发到 Redis，不等待 Kvrocks，不为每次热写增加 Gateway 本地落盘。普通请求丢回复不自动重放 INCR，也不永久封 key。

独立同步器取得 RDB/复制流，持久记录复制历史和位置，再应用到 Kvrocks。当前业务回放限定无 TTL String，支持普通 SET、单 key DEL、INCR。待处理记录、预期前后值和 checkpoint 配合 WATCH/MULTI/EXEC 核对与恢复，不能把这个受限协议解释为任意 Redis 事务可靠回放。

热层持有尚未同步的修改时不是可随意丢弃的缓存。Gateway 重启不等于 Redis 丢失；异步同步也不保证 Redis 在修改尚未捕获时故障仍然零丢失。Redis 持久化/副本配置、可接受的数据损失窗口与长期积压下的限写策略仍待定。

### 降冷与回温：目标和已实现部分

降冷的正常动作是确认数据已同步后移除热副本，不是重新搬一遍数据。删除时必须区分缓存移除与业务 DEL，并防止确认之后的并发写被遗漏。

当前内部实验先取得 key 屏障、等待在途请求，保存操作意图，再用内部 Lua 原子检查值/类型/TTL 并写准备标记。同步器验证复制流中的准备事件及对应数据，在 Kvrocks 核对后提交确认。用户 Lua 不因此获得支持。

内部 `/internal/v1/hot-preparation/finish` 用于**保留热数据收尾**。Gateway 持久记录收尾请求并后台重试；同步器将已确认准备标记作为无业务副作用的控制记录，用 WATCH/MULTI/EXEC 中一条 MSET 同时推进 checkpoint、pending 和终态回执，然后继续后续日志。Gateway 核对并持久记录结束后才允许下一次转换。收尾不重放 INCR、不删除 Redis 数据、不赋予后续删除权限。

热访问与冷收尾分两步：持久化收尾请求后，Gateway 核对源复制历史、noeviction、无 TTL 的精确准备标记，先恢复该 key 的热访问；源标记始终保留，迟到脚本不会再产生准备事件。冷确认/终态仍后台完成，未完成前保留操作身份并拒绝下一次转换。重启不直接相信内存里的“已释放”，先恢复保护再核对源标记。此路径仅适用于从未删除业务热数据的实验，不能作为正式删除操作的通用取消协议。

收尾请求可跨 Gateway/同步器重启恢复；冷端已提交、本地终态尚未写入时，以精确终态回执和已证明的进度恢复。未请求收尾的持久准备默认 30 秒后自动发起保留热数据收尾，重复请求不延长当前计时；恢复启动重新安排这一等待窗口。热访问释放不再等待冷确认，但仍依赖源标记核对，不是保证 30 秒内解锁。固定本地操作文件可原子替换，支持连续操作；源 Redis 的每操作准备标记仍保留，防止迟到 EVAL 再发事件，安全回收和长期增长控制待实现，不能将此原型当作已完成元数据生命周期管理。

自动降冷已接入 Gateway 后台任务：默认关闭，配置 `hot_cold.auto_eviction` 显式启用。默认内存 80% 启动/70% 停止，以 Redis 扣除 `mem_not_counted_for_evict` 的 `used_memory` 对比 `maxmemory`，不是 RSS。每批结束等待 5 秒；每批 3 秒、最多尝试 4 key、串行执行。每次 SCAN 有界采样最多 64 个候选，按 OBJECT IDLETIME 排序，执行前重新筛选；不在 Gateway 存全量 LRU 表，不 GET/STRLEN 候选以免刷新热度。

第一版只选择 key 不超过 256 字节、无 TTL 的 String，空闲至少 1 分钟且 MEMORY USAGE 在 8KiB～64KiB；最终仍检查实际值大小。跳过小对象是保守成本门槛，并非完整元数据回收方案。同步预检查与冷连通性在单 key 屏障之前完成，默认源/已应用位点差不超过 1MiB；预检查不是删除授权，真正删除仍复用精确确认。无合格候选或冷层/同步异常只结束本批，下一轮重试；内存耗尽仍可能 OOM，不丢弃未同步修改。独立按字节速率限流、适应性调参、全局 LRU/LFU 与吞吐验收待定。当前准备实验的 30 秒自动收尾不满足最终短临界区要求。

v2 准备协议（内部 `hotPreparationOptions.BoundedMarkers`，由 `hot_cold` 配置统一启用）限制源标记增长：每任务使用固定 `prepare:<task>:current` key，操作意图包含 `previous_operation_id`。操作编号固定 32 位小写十六进制、严格递增，可由 API 自动分配或调用方显式提供；不是随机 UUID，不得回绕。Gateway 仅从已持久完成的前一操作构造新意图；Redis 脚本核对前驱编号、任务、复制历史及 epoch，以单条 SET 覆盖标记。原样重试不写任何记录，旧编号脚本在标记更新后被拒绝。编号采用字符串比较，epoch 比较原始十进制文本，避免 Lua 浮点精度问题。

v2 准备步骤不新增复制流事件种类，同步器仍消费同一准备 SET 并验证前驱操作链；只在冷收尾已完成后覆盖，不能在仅恢复热访问时提前覆盖。v1 测试兼容保留，正常冷热配置只启用 v2；已存在的操作目录与配置版本不符时拒绝启动，不自动迁移或删除旧标记。现有旧脚本仍可能迟到，迁移必须先隔离旧执行者。源元数据不能被外部删除/回滚；缺失已存在的前驱会拒绝新操作，而不是自动重建水位。多主、切主、原始数据回滚和分布式编号未验收。

新增内部 `ManualResidency` 单 key 执行路径（必须使用 v2 准备协议）：完成准备冷收尾后，核对复制历史、noeviction 和当前准备标记，从冷层读取已确认值并核对哈希。源脚本比较热值，在同一原子操作中 SET 每 key 冷驻留标记、UNLINK 热业务 key。同步器识别完整记录组、核对冷终态回执和当前冷值，用 v3 控制 pending 原子推进整个记录组的 checkpoint，不把内部 UNLINK 当业务删除；普通业务 DEL 仍同步。

确认成功不是永久删除许可：源脚本还比较准备标记、驻留操作编号和当前热值。驻留标记按任务及业务 key 的 SHA256 命名，保存 binary-safe 意图及 cold/hot 状态；回温后保留 hot 终态，拒绝迟到删除/回温。元数据随参与转换的 key 数增长，成本与安全回收待定，不以 Bloom 替代驻留状态。

开启该模式的单 key 业务请求用内部 Lua 原子检查驻留标记并执行原命令。若冷驻留，只返回明确的未执行信号；Gateway 查询 Kvrocks、核对无 TTL 和值哈希，以比较标记脚本回温，再执行原命令。并发请求已回温/写入时，旧回温脚本只无操作返回或拒绝，不覆盖新值。脚本部分回温留下相同业务值但仍为 cold 标记时允许补齐；冲突值不覆盖。冷层不可用不阻塞普通热 key，也不重放结果未知的业务写。

持久启用标记阻止同目录静默退回普通直通。`hot_cold` YAML 开发开关接入正常启动，并要求 `state_dir`、固定绑定、独占声明和独立管理凭据。一次性 `-init-state` 只初始化空私有目录，正常启动不自动重建丢失的状态；删除开关但保留状态目录也拒绝。尚不支持 Cluster 和源历史切换。当前每连接逐命令执行以保持冷缺失重试的 Pipeline 顺序；热请求无需等待冷层，但增加内部脚本开销，性能未验收。源码仍不修改 Redis/Kvrocks 引擎，内部元数据与绕过 Gateway 的直写权限必须隔离。

手动 API 可省略操作编号：持有本地控制器锁时读取持久前驱编号，按 128 位十六进制整数递增，新意图仍在派发前持久化；不依赖时钟，不回绕。未完成的同 key 请求复用当前编号；已冷 key 返回已有编号，即便其他 key 已使用任务的最后操作文件。响应返回编号便于明确重试。该机制不解决多 Gateway 同时拥有同一源的分布式编号/隔离问题。

Cluster 中内部操作标记与业务 key 的同 slot 布局必须在正式执行器前确定；不能沿用实验标记布局直接上线。具体位置元数据、扩容和切主协议待定。

## 故障处理：现状与要求

| 情况 | 当前行为 | 后续要求/缺口 |
| --- | --- | --- |
| 普通请求已发但丢回复 | 不重放、不永久封 key，不触发分片级冷热暂停 | 沿用 Redis 结果不确定语义，不冒充业务幂等 |
| 有效 dirty 记录重启 | 内部模式恢复已有操作的局部屏障，其他业务/新准备不因 dirty 被暂停 | dirty 仅诊断，不作全局停服理由 |
| 准备等待/只读检查失败，尚未持久化或派发 | 自动撤销本次尝试、释放屏障；普通在途请求计数不变 | 不是证明未知业务写没有执行，也不重放请求 |
| 已持久化操作或可能发出的准备结果未知 | 无人继续时默认 30 秒触发收尾，核对保留源标记后释放热访问，冷收尾后台重试并跨重启恢复 | 源不可达、身份改变或损坏状态仍有恢复缺口；正式删除的取消待实现 |
| 实验确认遇到准备标记 | 先停后续冷应用；保留热数据收尾后推进并继续 | 实际删除只走额外的手动比较删除路径；源标记迁移回收仍待实现 |
| 源/冷连接故障、资源压力 | 有受控重试与暂停；耗尽预算或部分终态会结束任务 | 常见故障自动恢复策略需补齐；不是所有异常都已自愈 |
| 状态损坏、历史/身份冲突 | 拒绝无法安全解释的状态 | 明确告警、影响范围和恢复措施，不能盲目放行 |

默认原则是自动恢复、局部降级；人工介入只用于不能安全自动判定的严重异常。不能靠“等待几秒/PING 成功”证明旧写已隔离，也不能靠一条历史确认永久解锁。当前同步器模板的 Restart=no 是实验现状，不是最终可用性方案。
