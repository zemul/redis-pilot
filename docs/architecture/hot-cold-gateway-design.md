# 冷热存储：现行设计

更新：2026-09-09。本文维护当前架构、实现边界和已确认原则，不作为阶段流水账。能力与验收见 [实现进度](hot-cold-status.md)，运行方式见 [部署运维](gateway-deployment.md)。

## 目标与当前结论

在尽量不修改 Redis、Kvrocks 引擎的前提下，热读、热写优先走 Redis，修改异步同步到 Kvrocks；根据内存压力自动移除已同步的热副本，访问冷数据时回温。产品主要面向 Cluster，兼顾扩容期间读写、常见 Redis 命令和自动恢复，重点关注热写延迟与存储成本。

**当前不是完整冷热系统。** 已有单后端转发 Gateway、受限同步服务以及内部准备/确认实验。热副本移除、冷读、回温、自动淘汰、Cluster 协调尚未接成业务闭环。不能让当前 Gateway 代理一个只保留部分业务数据的 Redis：它还不能正确处理冷 key。

## 组件职责

| 组件 | 职责 | 不承担 |
| --- | --- | --- |
| Proxy | 业务接入；未来按拓扑选择冷热 Gateway | 不与 Gateway 重复选择冷热层 |
| Gateway | 热层业务请求；未来负责冷热位置、回温、降冷协调 | 不内嵌同步器，不逐请求调用 Server 审批 |
| 独立 redis-syncer | PSYNC 捕获、本地日志、Kvrocks 应用和进度/操作确认 | 不处理业务 GET/SET，不按 Gateway 数量复制任务 |
| Server/API | 状态、配置、观测；未来发布拓扑与分配同步任务 | 不维护全量 key 的高频状态，不参与逐次热写 |
| Agent | 管理本机 Redis/Kvrocks 容器 | 不安装、启停 Gateway 或同步器二进制 |
| 运维与 systemd | 独立二进制的安装、升级、启停与开机启动 | 不代表已具备分布式故障接管 |

普通实例继续使用原有 Proxy → Redis 路径，不强制经过 Gateway。冷热实例的目标是单业务入口，热读写访问 Redis 主节点，不默认开启副本读。当前尚未实现 Proxy 自动切入冷热路由。

同步任务未来按 Redis 主分片组织；一个同步器进程可以承载多个任务。当前只有 1～8 个静态隔离任务，每任务独立日志、独占冷 DB；多写者隔离、跨机接管与动态调度未实现。

## 数据路径与一致性边界

### 热读写与同步

Gateway 将受支持请求转发到 Redis，不等待 Kvrocks，不为每次热写增加 Gateway 本地落盘。普通请求丢回复不自动重放 INCR，也不永久封 key。

独立同步器取得 RDB/复制流，持久记录复制历史和位置，再应用到 Kvrocks。当前业务回放限定无 TTL String，支持普通 SET、单 key DEL、INCR。待处理记录、预期前后值和 checkpoint 配合 WATCH/MULTI/EXEC 核对与恢复，不能把这个受限协议解释为任意 Redis 事务可靠回放。

热层持有尚未同步的修改时不是可随意丢弃的缓存。Gateway 重启不等于 Redis 丢失；异步同步也不保证 Redis 在修改尚未捕获时故障仍然零丢失。Redis 持久化/副本配置、可接受的数据损失窗口与长期积压下的限写策略仍待定。

### 降冷与回温：目标和已实现部分

降冷的正常动作是确认数据已同步后移除热副本，不是重新搬一遍数据。删除时必须区分缓存移除与业务 DEL，并防止确认之后的并发写被遗漏。

当前内部实验先取得 key 屏障、等待在途请求，保存操作意图，再用内部 Lua 原子检查值/类型/TTL 并写准备标记。同步器验证复制流中的准备事件及对应数据，在 Kvrocks 核对后提交确认。用户 Lua 不因此获得支持。

内部 `/internal/v1/hot-preparation/finish` 用于**保留热数据收尾**。Gateway 持久记录收尾请求并后台重试；同步器将已确认准备标记作为无业务副作用的控制记录，用 WATCH/MULTI/EXEC 中一条 MSET 同时推进 checkpoint、pending 和终态回执，然后继续后续日志。Gateway 核对并持久记录结束后才允许下一次转换。收尾不重放 INCR、不删除 Redis 数据、不赋予后续删除权限。

热访问与冷收尾分两步：持久化收尾请求后，Gateway 核对源复制历史、noeviction、无 TTL 的精确准备标记，先恢复该 key 的热访问；源标记始终保留，迟到脚本不会再产生准备事件。冷确认/终态仍后台完成，未完成前保留操作身份并拒绝下一次转换。重启不直接相信内存里的“已释放”，先恢复保护再核对源标记。此路径仅适用于从未删除业务热数据的实验，不能作为正式删除操作的通用取消协议。

收尾请求可跨 Gateway/同步器重启恢复；冷端已提交、本地终态尚未写入时，以精确终态回执和已证明的进度恢复。未请求收尾的持久准备默认 30 秒后自动发起保留热数据收尾，重复请求不延长当前计时；恢复启动重新安排这一等待窗口。热访问释放不再等待冷确认，但仍依赖源标记核对，不是保证 30 秒内解锁。固定本地操作文件可原子替换，支持连续操作；源 Redis 的每操作准备标记仍保留，防止迟到 EVAL 再发事件，安全回收和长期增长控制待实现，不能将此原型当作已完成元数据生命周期管理。

自动降冷的已确认方向（尚未实现）：按内存高/低水位启动和停止，小批量、按字节数和并发数限速；候选和同步预检查在单 key 屏障之前完成。初始建议为每秒检查一次、预算 80% 启动/70% 停止，均待配置与压测调整，不是每秒强制删除。关键切换等待过久应安全放弃；冷层异常或同步积压时暂停降冷而不是停止正常热读写，内存耗尽仍须背压，不能丢弃未同步修改。当前准备实验的 30 秒自动收尾不满足最终短临界区要求。

内部可选的 v2 准备协议（`hotPreparationOptions.BoundedMarkers`，无公开 YAML 开关）限制源标记增长：每任务使用固定 `prepare:<task>:current` key，操作意图包含 `previous_operation_id`。调用方提供固定 32 位小写十六进制、严格递增的操作编号；不是随机 UUID，编号不得回绕。Gateway 仅从已持久完成的前一操作构造新意图；Redis 脚本核对前驱编号、任务、复制历史及 epoch，以单条 SET 覆盖标记。原样重试不写任何记录，旧编号脚本在标记更新后被拒绝。编号采用字符串比较，epoch 比较原始十进制文本，避免 Lua 浮点精度问题。

v2 不新增复制流事件种类，同步器仍消费同一准备 SET 并验证前驱操作链；只在冷收尾已完成后覆盖，不能在仅恢复热访问时提前覆盖。v1 保持兼容，默认不启用 v2；已存在的操作目录与配置版本不符时拒绝启动，不自动迁移或删除旧标记。现有旧脚本仍可能迟到，迁移必须先隔离旧执行者。源元数据不能被外部删除/回滚；缺失已存在的前驱会拒绝新操作，而不是自动重建水位。多主、切主、原始数据回滚和生产编号分配未验收。

另有热副本移除记录组的格式/识别实验：匹配可信操作意图、完整事务和连续复制位置，未来仅跳过这组内部删除；普通业务删除仍需应用到冷层。**该识别器尚未接入正式淘汰执行器。** 内部命名空间需限制业务访问，绕过 Gateway 的直写权限也需约束。

确认成功不是永久删除许可。真正删除和位置切换仍需校验当前版本、冷提交位置以及旧执行者/迟到写入的边界。当前没有热删除、冷热目录、冷读或回温；过滤器选型与恢复方式待定，不能用 Bloom 判断代替完整的驻留和版本协议。

Cluster 中内部操作标记与业务 key 的同 slot 布局必须在正式执行器前确定；不能沿用实验标记布局直接上线。具体位置元数据、扩容和切主协议待定。

## 故障处理：现状与要求

| 情况 | 当前行为 | 后续要求/缺口 |
| --- | --- | --- |
| 普通请求已发但丢回复 | 不重放、不永久封 key，不触发分片级冷热暂停 | 沿用 Redis 结果不确定语义，不冒充业务幂等 |
| 有效 dirty 记录重启 | 内部模式恢复已有操作的局部屏障，其他业务/新准备不因 dirty 被暂停 | dirty 仅诊断，不作全局停服理由 |
| 准备等待/只读检查失败，尚未持久化或派发 | 自动撤销本次尝试、释放屏障；普通在途请求计数不变 | 不是证明未知业务写没有执行，也不重放请求 |
| 已持久化操作或可能发出的准备结果未知 | 无人继续时默认 30 秒触发收尾，核对保留源标记后释放热访问，冷收尾后台重试并跨重启恢复 | 源不可达、身份改变或损坏状态仍有恢复缺口；正式删除的取消待实现 |
| 实验确认遇到准备标记 | 先停后续冷应用；保留热数据收尾后推进并继续 | 确认本身不释放；源标记安全回收和实际删除尚未实现 |
| 源/冷连接故障、资源压力 | 有受控重试与暂停；耗尽预算或部分终态会结束任务 | 常见故障自动恢复策略需补齐；不是所有异常都已自愈 |
| 状态损坏、历史/身份冲突 | 拒绝无法安全解释的状态 | 明确告警、影响范围和恢复措施，不能盲目放行 |

默认原则是自动恢复、局部降级；人工介入只用于不能安全自动判定的严重异常。不能靠“等待几秒/PING 成功”证明旧写已隔离，也不能靠一条历史确认永久解锁。当前同步器模板的 Restart=no 是实验现状，不是最终可用性方案。
