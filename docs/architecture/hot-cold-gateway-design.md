# 冷热缓存设计

更新：2026-09-16。当前开发实现与限制见 [实现状态](hot-cold-status.md)，配置和部署见 [部署运维](gateway-deployment.md)。

## 控制面任务登记（2026-09-16）

Server 的 cold_clusters/cold_tasks/cold_resources 只保存期望拓扑、稳定任务身份、汇总进度和专用实例占用，不承担逐 key 交接。Gateway 显式开启 control_plane.manage_shards 后，通过现有 per-Gateway token 拉取任务；先持久化本地任务日志和运行引用，再激活迁移。控制面不可达时本地任务继续，恢复后补报；重复投递不创建第二任务，进度只能前进。最终 complete 才更新 Server 集群版本并释放旧实例，published 仍保留资源保护。

当前资源仅允许同主机、单点、无直接 Proxy 入口的 Redis/Kvrocks；托管模式不使用数据库密码，业务认证继续在 Proxy。数据库资源占用通过 SQLite 事务及触发器保护，阻止通用运维接口绕过迁移去停库、删库或改拓扑。新节点配置尚需运维加入 Gateway YAML 注册表并重启；注册表本身不改变 HRW 路由。此控制面不是部署器、分布式租约或多 Gateway 自动接管。

## 契约与职责

Kvrocks 是唯一权威存储，保存完整业务数据；Redis 是可丢弃缓存。所有业务访问必须经过同一个有效 Gateway，不能旁路修改冷库、缓存或内部元数据。不再使用 PSYNC 同步器、复制日志、冷热所有权转移和主动降冷器。

Gateway 属于数据面：读写路由、缓存更新、回填、一致性协调。独立二进制由 systemd 管理；Agent 只管理数据库容器，Server 管理配置/观测，Proxy 负责接入。当前固定本机回环端点、单 Gateway、DB 0；支持可选 HRW 冷分片启动/恢复，不提供 Redis Cluster 协议或多 Gateway。

## 冷分片配置与本地恢复（2026-09-16）

`cache.sharding` 与原 `cold_address/cold_password_file` 互斥，原单冷配置保持兼容。`nodes` 给出稳定分片 ID、回环地址和独立 password_file；`state_dir` 保存 Gateway 独占的 runtime.db（SQLite WAL/FULL）及 tasks 下逐任务交接日志。密码正文不进入路由快照或状态库。配置解析和 NewService 检查凭据，但不创建数据库、不连接后端；启动在取得现有 cache 锁和状态目录独占锁后恢复，再接管后端。

首次只对专用空冷库执行 `-init-sharding-state`：确认各冷节点 DBSIZE=0，再独占创建状态目录并持久化初始 HRW revision 1；已有目录拒绝覆盖，正常启动缺失/损坏状态拒绝猜测或自动初始化。这不是旧部署的数据导入命令，不能在 systemd 每次启动前重复执行。初始化期间也必须禁止其他写者；本地锁不提供跨主机互斥。

初始化后，YAML nodes 仅是端点/凭据登记表，不是当前权威路由。加入登记不触发扩容，删除仍在使用的节点或修改其地址拒绝启动。runtime.db 记录服务/Gateway/热端点身份、源拓扑与已接受任务的 ID/目标拓扑；先持久化任务日志，再登记引用，之后才能开始搬迁。已登记引用的日志丢失不自动重建；未登记的孤立任务目录不扫描激活。任务 active 时恢复交接，published 时按新拓扑服务并继续标记回收，complete 时只连接新拓扑，不要求已移除节点在线。已完成任务的快照/最终状态仍保留，不能手工删除其日志目录。

恢复 worker 自动继续扫描/确认/发布/回收，支持配置扫描批次、key/s 和 bytes/s 限速及单步超时；速率当前在进程启动时读取。Server 任务创建/下发、CLI 扩缩容和在线调速尚未接通，不能靠修改 YAML 绕过迁移。跨主机后端访问、时钟/持久性前置检查、多 Gateway 和自动切主继续留在后续阶段；此入口仍限本机独占开发部署，不声称完成生产验收。

目标：写请求返回成功后，随后发起的读不能返回旧缓存。响应丢失仍可能是已执行，不承诺 exactly-once；非幂等业务请求不自动重试。底层冷库回滚、复制丢写、备份恢复或外部写入不在缓存协议保证范围，不能用缓存补偿冷库持久性。

## 两种写后策略

| 配置 | 处理方式 |
| --- | --- |
| invalidate（默认） | 冷层执行修改，随后删除热缓存 |
| update_existing | 冷层执行修改后，原子检查热 key 存在并增量更新；缺失时不创建残缺对象；成功的全值字符串写入可以直接缓存完整新值 |

更新模式的正常局部写不再整对象重读/重建。HSET/HDEL、集合增删、列表确定性修改等增量执行；INCR/DECR/INCRBY/DECRBY 用冷层返回的最终字符串 SET，HINCRBY 用最终值 HSET，ZINCRBY 用最终分数 ZADD，SPOP 用冷层选中的成员 SREM，LPOP/RPOP 检查热侧弹出结果与冷侧一致。不能简单让随机或非幂等命令在两库各自计算。EXPIRE/PEXPIRE/PERSIST 按冷层剩余 TTL 更新缓存有效期。DEL/UNLINK、写命令错误或安全更新失败仍清理/隔离缓存。

扩展规则：HMSET/HSETNX 转为对应字段 HSET；INCRBYFLOAT/HINCRBYFLOAT 使用冷引擎最终字符串并在同一冷脚本内规范化存储值（String 保留 TTL）；ZADD 条件/INCR 完全由冷层决定，再只读取涉及成员的最终分数更新热层，XX 忽略的新成员不创建。SPOP count/ZPOPMIN/MAX 使用冷层实际选中的成员；LPOP/RPOP count 比较完整二进制弹出数组。GETDEL 清理热层；SETNX/SETEX/PSETEX/GETSET 成功时可以新建完整 String 缓存。正常局部写不重建 Hash/List/Set/ZSet。

缓存更新失败时，冷层已成功的业务不重做。确认清理或隔离热层后仍可返回冷层成功结果。已删除 max_object_bytes、max_object_elements 和 cache.types 单对象准入配置，不再因为对象大而清理已有完整缓存或拒绝回温。LRU、到期和资源故障仍可能导致对象离开缓存，不承诺永久驻留。

## 读与对象完整性

热 Redis 直接使用原始业务 key、原生数据类型，一个对象只对应一个正式 key；不再拼接运行标识、热代次、SHA256 或 data/complete 后缀，也不保存每对象完整性标记。可信热层内原子检查 key 存在后执行白名单读命令。未命中读取冷库，并尝试完整回温。不存在不填缓存；超时不当作不存在。TYPE 等状态回复按 Redis RESP2 对外规范转换。

五种类型按完整对象缓存，但分批传输：String GETRANGE（每批最多 64KiB，同时受帧预算影响），List LRANGE（每批 128 项），Hash/Set/ZSet 使用 HSCAN/SSCAN/ZSCAN COUNT 128。扫描 COUNT 是提示，不是总大小或返回批次的严格保证。先读取 TYPE、PTTL 和总长度/数量用于完成校验，不用于大小准入。整个过程中只保留当前批次，不在 Gateway 中累计整个对象。最终验证热侧完整长度/基数，失败删除半成品；中途被 LRU 淘汰时后续批次禁止重新创建残缺 key。

默认 4 个并发加载；保留 RESP 帧大小/元素数、连接、总工作区预算、请求超时和 Redis 自身内存保护。它们保护单次传输和资源，不再额外设置单对象容量上限。若一个字段、扫描返回批次或业务 HGETALL/GET 回复超过配置的协议帧限制，仍可能失败或无法完成回温；长回温超过请求期限会终止并删除半成品。取消大小准入不等于无限内存、无限响应或无限等待，必要时应调整已存在的协议/预算/超时配置。

同 key 锁覆盖冷读取、所有回温批次、完整性校验和失败处理，不允许业务读写穿插。首批创建原 key，后续脚本仅在 key 仍存在时追加；每批使用同一绝对过期时间，不重新计时。命令报错删除半成品；异常回复或网络结果不确定时立即隔离热层，清空恢复前不能命中。无需临时 key 或常驻 complete 标记。LRU 正常淘汰整个 key，下一次读冷层并回温。更新模式的存在性检查与局部修改在同一脚本中完成，防止先检查、后被淘汰、再 HSET 创建残缺 Hash。

支持 SET EX/PX/EXAT/PXAT、NX/XX、GET、KEEPTTL，以及 GETEX 和条件 EXPIRE/PEXPIRE/EXPIREAT/PEXPIREAT（NX/XX/GT/LT）、PERSIST。条件与业务过期由冷层执行；未生效的条件写不更新缓存。SET GET 的 nil 不能当作未写入：无条件/NX 创建新 key 成功也返回 nil；固定冷脚本根据真实结果与选项回传是否生效，不使用可能过期的事前 EXISTS。旧值为字符串 OK 时保留 bulk 回复。默认 SET 清除业务 TTL，KEEPTTL 保留它。TTL/PTTL/EXPIRETIME/PEXPIRETIME 始终查冷层。

Kvrocks 2.15 不原生接受条件 EXPIRE，在 owner 校验的同一冷脚本内比较绝对截止时间，再调用无条件过期命令，不在 Go 层拆成读、判断、写。为避免 Lua double 在极大整数上误判，条件值及涉及的毫秒截止时间限定在 ±(2^53−1)，超界返回明确错误。浮点计算仍是冷引擎语义，不实现另一套 Redis 浮点运算器。

HSCAN/SSCAN/ZSCAN 固定使用冷层游标，不读热层、不因扫描触发回温。翻页期间发生 LRU/回温也不会切换引擎。MATCH/COUNT 细节遵循冷引擎，不提供快照扫描。LPOS/随机成员/空数组等回复差异按命令语法规范化。完整命令与选项矩阵只维护在 [实现状态](hot-cold-status.md)。

带业务 TTL 的完整对象允许回温。发送 PTTL 前记录单调时间，以该时刻加剩余 TTL 作为保守截止时间，和缓存默认 5 分钟上限取较早者；快照、网络耗时均扣除。发布前读取热 Redis TIME，用收到回复时剩余生命周期计算热服务器自身的绝对过期时间；脚本检查已到期则跳过，否则 PEXPIREAT，避免迟到回填重新开始计时。不需要每 key 截止时间标记，也不要求两个服务器时钟完全相同，但不保证时钟突跳、外部直接修改 TTL 的语义。热读按 Redis 执行时的过期判断返回，不承诺数据在客户端收到回复时仍未到期。Hash 字段 TTL 尚未支持。

## 同 key 协调与热层恢复

当前使用固定 256 个锁桶：同 key 的读、写、冷读取和回填完整串行；不同桶并发，哈希碰撞会保守串行。锁等待有请求截止时间，不维护全量 key 目录。此处的锁桶不是集群 slot，也不提供分布式归属。

MGET/MSET/MSETNX、多 key DEL/UNLINK/EXISTS 使用同一组锁桶：先验证全部 key，桶编号去重并升序获取，逆序释放；等待超时撤销已获取的部分锁，不能只按业务 key 字典序排序。MGET 全命中时热侧一次原子读；有任何缺失或冷层专用 key 则整批冷侧原子读，不混拼各层的结果。多 key EXISTS 只查冷。冷读 MGET 按原生规则将非 String/不存在返回 nil，其他 String 可以在持锁期间回温，重复 key 只回温一次。

MSET/MSETNX/多 key DEL/UNLINK 在一个 owner 校验脚本中执行一次冷层原生命令，不能拆成单 key 循环。MSETNX 返回 0 时整批不更新缓存；MSET 清除旧业务 TTL。成功后删除模式统一删热，更新模式的 MSET/MSETNX 逐 key 发布完整 String（重复 key 使用最后值），DEL/UNLINK 始终删热。所有 key 的锁保持到缓存处理结束或热层已隔离，阻止单 key 请求观察到一半更新；任意热失败不允许旧缓存继续服务。冷结果未知不重放。这个原子性依赖当前单 Gateway、单冷后端前提，不能直接扩展成跨节点事务。

每个普通业务命令通过固定内部 EVAL 执行：检查冷层 owner token，再执行白名单命令。用户 Lua 使用下述受保护执行入口，不裸透传。INCR/DECR/INCRBY/DECRBY/HINCRBY 使用冷层最终字符串转回整数回复，避免 Lua double 丢失大于 2^53 的整数精度。

## 跨 key、事务与 Lua

RENAME/RENAMENX、SMOVE、LMOVE/RPOPLPUSH 和集合运算统一提取全部读写 key、复用升序锁桶，在冷层原子执行后保持锁直到缓存处理完成。更新模式下 RENAME 直接移动已有完整缓存；来源缺失则清理目标，不重新扫描大 Hash。列表移动使用冷层实际弹出的元素校验热侧；仅对已有完整目标增量插入。来源/目标属于冷层专用前缀时保守清理可缓存一侧。STORE 命令本来就替换整个目标，单独执行时可重新加载原本已驻留的目标；事务/脚本内则失效目标，避免先回填最终状态、再重放后续修改造成重复作用。普通 Hash 字段更新不受这个例外影响。

SCAN 固定查冷层，逐页过滤内部保留前缀，不把 Redis 缓存目录当成全库目录；不会为扫描回温。COUNT 为提示，游标必须原样传回，MATCH/TYPE 依赖所部署的冷引擎。Gateway 也支持 KEYS 并过滤控制 key，但现有 Proxy 安全策略仍拒绝 KEYS，业务建议使用 SCAN。

MULTI/EXEC/DISCARD/WATCH/UNWATCH 是每条前端连接的状态，不跨连接共享。Gateway 有界排队，语法/命令检查失败标记 EXECABORT，DISCARD/断连丢弃未执行队列；执行错误不回滚之前成功的命令，后续命令继续，这是 Redis 的事务语义。EXEC 时同时持有全部操作与 WATCH key 的锁，使用冷层原生 WATCH/MULTI/EXEC，并在事务中执行一个受保护的命令体；读全部来自同一冷层执行序列，提交后才更新/清理缓存。更新模式中的 HSET/HINCRBY 等仍按操作结果增量维护已有大 Hash，不通过全删来冒充支持事务。前后端网络结果未知不重试 EXEC。

Kvrocks 2.15 的 WATCH 不会因自然过期而按 Redis 预期中止：建立 WATCH 时，在 key 锁内读取冷层绝对到期时间；EXEC 的单个冷执行体先一次性检查全部到期时间，再执行整批，避免逐命令判断导致半批执行。写冲突仍由原生 WATCH 判断；私有 owner 同样被 WATCH，隔离跨重启/恢复的迟到 EXEC。到期时间落在捕获与 WATCH 之间时允许保守中止，客户端应按 WATCH 冲突重试整项业务。无每对象版本 key、事务日志 key 或全量版本目录。超过精确毫秒范围的 WATCH 到期时间拒绝，而非近似比较。

EVAL/EVALSHA（含 _RO）在冷层完整执行，不在热层重复运行脚本。调用方必须通过 KEYS 声明所有访问 key；沙箱仅开放本状态矩阵的业务命令、PING/ECHO/TIME、常用 Lua 基础库和受保护 redis.call/pcall，拒绝未声明 key、控制 key、管理/阻塞/嵌套脚本命令。用户源通过 loadstring/setfenv 进入独立环境，不能通过 _G/getfenv/加载字节码/字符串元表绕过保护。脚本源码和声明 key 不属于“任意 Redis 扩展都兼容”的承诺。

脚本写操作在可能修改数据前登记保守记录，成功后记录实际命令结果；记录与交给用户 Lua 的返回表分离，避免用户改表篡改缓存更新依据。更新模式只把这些已确认效果应用到热层，不重算随机弹出或自增；脚本先写后报错、缓存处理失败、返回超协议预算等场景同样清理或隔离热层。Kvrocks 的嵌套状态回复差异在脚本边界显式编码为 RESP2，再按协议限制验证。SCRIPT LOAD/EXISTS/FLUSH 管理 Gateway 的有界源码缓存；重启后 EVALSHA 可以 NOSCRIPT，客户端应 LOAD/EVAL。源码总量不超过 max_batch_bytes，Lua 命令次数及事务条目数受 limits.max_elements 约束，展开后的事务也受帧预算约束。长脚本仍占用冷引擎执行时间，客户端超时不代表脚本已取消。

Proxy 保持整个事务的专用连接：依据后端结果维护 MULTI/WATCH 状态，事务内 UNWATCH 的 QUEUED 不解 pin，PING/ECHO 不本地应答，阻塞类命令不走普通阻塞完成后的解 pin 分支。本地安全拒绝也会使后端队列报错，防止此前排队写被 EXEC 意外提交。

- 启动：持有本地私有 flock，读取旧 owner，通过比较交换设置随机新 token；热层默认禁用，清空成功后才启用。
- 冷请求结果未知：不重放请求；把本地 token 置为待确认新代次，后续冷 CAS 确认后才恢复请求。迟到旧命令因 token 不匹配而拒绝执行。CAS 可安全重试，迟到旧 CAS 不能覆盖新 token。
- 热请求/失效/发布失败：立即禁用热读、热写和回温。恢复过程等已准入的热操作结束，CLIENT KILL TYPE normal SKIPME yes 关闭热 Redis 上旧的普通连接（保留恢复连接），随后 FLUSHDB SYNC。两步确认成功后才重新启用；结果不确定继续走冷层并重试。只关闭本地 socket 不足以隔离服务端已缓冲的旧请求。所有业务热请求均在完成连接握手后才发送，恢复期间不准入新的热操作；不能通过会自行重连重放命令的中间代理接入热 Redis。
- 恢复中的冷读写不等待热层清理；绕过热层的普通写若与恢复重叠，会使本轮启用失效，之后再次清理确认。内部仅维护有界恢复状态，不为业务对象建状态目录或版本 key。
- 热节点不可用：使用较短 hot_timeout 给冷读取预留时间，后续请求继续尝试；不要求人工恢复缓存。
- 冷不可用：需要冷库的请求报错，不确认写成功。已有可信热读是否成功取决于当前 token 是否已确认；冷写结果未知时热层也被隔离，不能继续使用旧缓存。

冷库仅保存少量固定控制元数据，不保存每 key 同步位点。保留前缀 __pilot_cache_v1__:，业务命令禁止操作。配置 exclusive_backends 是部署前提声明，不是多节点租约；不同主机或不同锁路径启动重叠写者不受本地 flock 保护，禁止这样部署。

热 Redis 必须是本 Gateway 独占的可丢弃实例，DB 0，不可混放其他数据；恢复会断开其他普通连接并清空 DB 0。必须 maxmemory > 0、allkeys-lru、appendonly no、save 空，每次热连接核对。禁止混用其他 DB、绕过 Gateway 写入、在线改变这些约束或手工加载快照。冷库仍保留 owner 和 cold-only-policy 两个固定控制 key，不随业务对象数增长。

## 阻塞命令

首版仅支持 BLPOP/BRPOP，1～16 个 key、有限等待 (0,60] 秒。使用独立冷连接和并发限额，不持有普通 key 锁，不妨碍 LPUSH/RPUSH；不允许无限等待、BLMOVE、BZPOP 或任意阻塞命令透传。

所有阻塞 key 必须属于配置的 cold_only_prefixes，这些 key 的所有普通读写也始终绕过缓存。这样即使 Gateway 崩溃或弹出回复丢失，迟到弹出也不可能使新热缓存变旧。

前缀集合写入冷层固定策略元数据，重启时必须匹配；禁止原地移除/修改后直接缓存旧队列。动态“仅在阻塞期间绕过、结束再恢复”以及前缀变更迁移尚未实现。业务连接断开后的后台等待当前受有限超时/服务取消约束，不承诺立即取消服务端已经执行的弹出。

## 自主管理分片与扩缩容（内部请求链路已接入，尚未开放配置）

本节包含 HRW 设计及实现进度，不代表常驻开发部署已切换多节点。HRW、日志、逐 key 搬迁已接入 Gateway 请求路径，并通过真实 TCP 前端测试；2026-09-16 起 YAML 支持多冷节点初始化/恢复，公开任务 API 尚未接通。前文的单冷后端命令原子性和两个固定冷控制 key 描述仍适用于默认运行模式；本节跨节点非原子批量语义、临时迁移元数据适用于可选分片模式。

### 范围与路由

- 对标 Codis 的代理分片及常用批量命令能力，不照搬其 slot 索引和修改版 Redis；保持 Redis/Kvrocks 原版引擎。五大类型均纳入迁移范围，分片单位是顶层业务 key，Hash 字段、List 元素不跨节点拆分。
- 使用等权重 Rendezvous/HRW：对业务路由 key 与每个逻辑节点的稳定 ID 计算分数，最高分对应目标节点。相同配置必得相同结果；不使用 hash(key) % 节点数，不维护环、虚拟节点、永久 key 位置表或 slot→key 索引。
- 节点 ID 与 IP/端口分离，地址变更、同逻辑分片的副本接管不应自动改变哈希归属。已实现算法标识 hrw-sha256-v1：分别计算 SHA256("hrw-sha256-v1/key" + NUL + 路由 key) 和 SHA256("hrw-sha256-v1/node" + NUL + 节点 ID)，拼接两个 32 字节摘要后再 SHA256，按完整摘要的大端字典序选最大值；同分取字典序最小节点 ID。NUL 表示一个零字节；无运行时随机种子，配置版本和地址不参与评分。标签取首个左括号及其后的首个右括号之间非空内容；首个标签空/不完整时用全 key，不搜索后续标签。后续改规则必须显式迁移。
- 路由基础提供经校验、排序、不可变的 JSON 快照（algorithm/revision/nodes，节点含 id/address，无凭据），限制正版本、1～1024 节点和 1MiB 解码预算；ID 为至多 128 字节 ASCII 字母/数字/点/短横线/下划线，地址为非零端口的字面 IP，规范化后禁止复用。YAML 凭据绑定和本地状态恢复已接入，公开任务 API 待接；在线替换地址需要受控重连/故障切换，成员迁移计划明确拒绝同时改保留节点地址，或以新 ID 复用源地址。
- 支持 `{业务标签}` 作为共同路由输入，原始存储 key 不改名。没有标签时使用完整 key。HRW 基础查找为 O(N)，N 为节点数；节点规模预期不大，先测试开销，不引入复杂查找优化。容量权重和实时负载驱动重平衡不在第一版范围。
- 冷热层维护各自的节点集合，允许独立扩缩容，不要求一一对应。第一版同一集群同时只执行一个拓扑变更任务，任务内部可以有限并发。一次增加多台应直接生成最终目标配置，分批限速迁往最终位置，避免连续中间配置导致重复搬迁。
- 等容量、哈希均匀、直接迁到最终配置时，N→N+M 预计改变 M/(N+M) 的 key 归属；扩到 2N 约迁移一半。此为理论 key 数比例，不是实测字节数、QPS 或内存均衡保证；扫描量可以是全库，实际复制仅限归属变化的数据。
- Proxy 保持接入职责，Gateway 负责数据面路由、缓存、迁移协调；Server 负责配置版本、任务管理与观测。沿用独立二进制/systemd，不让 Agent 自动部署或启停 Gateway。第一版仍只允许一个有效 Gateway 操作执行者，不提供多活或跨主机自动接管；不默认新增 ZooKeeper/etcd 等外部服务。

### 分片模式的命令契约

| 命令范围 | 计划语义 |
| --- | --- |
| 当前矩阵内五大类型单 key 命令 | 保留支持和单 key 一致性，迁移、回温与写入共同协调；不承诺所有 Redis 命令 |
| 跨节点 MGET、EXISTS | 拆分并按原顺序/计数汇总；不保证跨节点统一快照，后端错误不能变成不存在或半份成功回复 |
| 跨节点 MSET、DEL、UNLINK | 批量执行，无整体原子性，允许中间状态与部分成功；只有所有子操作确认完成且对应缓存安全后才返回整体成功；失败/超时不表示整批未执行，不自动回滚或盲目重放 |
| MSETNX、RENAME/RENAMENX、SMOVE、LMOVE/RPOPLPUSH、集合及 ZSet 多 key 运算/STORE | 不用拆分冒充原子语义；相关 key 能在同一冷节点协调执行时支持，跨节点在产生业务副作用前拒绝 |
| MULTI/EXEC、WATCH、用户 Lua | 保留同冷节点能力，不做跨节点事务或分布式 Lua；这是保留本项目已有能力，并非声称 Codis 支持事务 |
| Pipeline | 不是事务，维持同连接命令与回复顺序；多后端并行优化不作为第一版前置条件 |

整批参数、保留 key、重复 key 语义必须在分发前检查；同一 key 的子操作仍保持顺序，不能因并发拆分改变 MSET 最后值或 DEL 去重计数。同冷节点批量请求优先沿用现有原子执行路径，不能为了跨节点适配无故削弱单节点语义。每个已执行子写即使整体报错，也必须处理对应缓存，不能因为其他节点失败而遗漏热失效/更新。

事务与 Lua 的全部读写 key 必须提前提取/声明（含 WATCH key）。取得相关控制权后固定本次执行归属，执行中不迁移。相同标签的 key 目标一致但可能交接进度不同：先协调本次请求涉及 key 的交接，再在一个冷节点执行；不要求预先维护或迁完整个标签组。无共同标签的 key 可能只是暂时同节点，扩容后分离则拒绝跨节点执行；迁移期间以实际及目标归属预检，不能执行一半才发现不支持。WATCH 期间发生相关归属切换时，计划保守使监视失效，EXEC 返回空结果，由客户端重新读取后重试，不跨节点延续原生 WATCH 状态。

所有业务流量都必须遵守 Gateway 控制，包括可信热读、回温、事务和迁移；不保证跨节点整批原子性不等于放弃单 key 不读旧、不重复执行和迁移不覆盖新值的要求。

### 扫描与逐 key 安全交接

扩容扫描可能迁出数据的旧节点，HRW 下通常是全部旧节点；缩容通常只扫描待下线节点。边扫描边计算新旧归属并限速处理，不先创建全库 key 名单。SCAN 不是快照、COUNT 不是严格批次上限；必须验证实际 Kvrocks 的遍历语义、重复返回和并发变更，不能仅凭 Redis 替身推断。

计划的单 key 交接逻辑如下；状态名称是逻辑概念，具体存储和原子提交协议待验证：

1. 取得这个 key 的排他控制权，等相关已准入操作结束。普通读写、回温、缓存更新与迁移必须共用控制；其他无关 key 尽量继续服务。
2. 持久化迁移准备记录，固定任务、源/目标、执行者与操作代次。无记录仅在当前迁移版本规则下表示尚未交接，不能跨任务复用这个解释。
3. 从源节点复制完整类型、内容和过期信息至目标。未完整对象不能向业务开放；使用有界工作区分批复制，不新增单对象大小准入上限。大对象可能使该 key 请求等待或超时，也可能通过底层资源竞争影响其他请求。
4. 确认目标复制完整，再持久化提交归属。客户端超时不是成功确认。TTL 不重新起算，复制中已过期对象不能复活；跨主机时钟和 TTL 精度的具体处理待验证。数量/长度校验不能单独证明内容一致。
5. 已交接后的业务仅访问目标，完成本次操作及热缓存处理后放行请求。源旧副本可随后清理，但删除必须受任务归属和旧执行者隔离约束，不能删掉后续新写入。

需要迁往新节点的请求也执行同一交接流程：已交接就访问目标；未交接先处理源数据，有旧对象先交接，源确认为空则记录空归属交接再执行目标写入。不能因收到 SET 就认定是新 key，不能把超时当源不存在。归属没变的新 key 留在原节点。进入迁移规则前需隔离/排空旧规则的在途请求，确保不会继续向旧归属创建待搬数据；迁移协议不变量成立后，存量由扫描覆盖，新增由请求路径覆盖。

每次正常任务采用两轮：第一轮扫描迁移；第二轮扫描旧节点核对归属及交接记录、补迁漏项、清理已交接残留，不把全部 value 再传一遍。游标归零或“两遍扫完”均不是独立成功条件：还要确认交接队列完成、无结果不明操作、旧规则请求被隔离、应迁出的数据已处理，再持久化发布最终路由。异常补处理后按需复查，不无条件宣告完成。扫描重启后可重扫，交接必须幂等；游标能否续用取决于实际引擎和任务版本。

### 持久化状态与故障恢复

| 状态 | 内容与生命周期 |
| --- | --- |
| 路由配置 | 算法规则、稳定节点 ID/地址、版本长期保存；任务保留新旧快照 |
| 迁移任务 | 阶段、源/目标集合、扫描/核查进度、错误及统计；任务结束后保留必要审计 |
| key 交接记录 | 仅归属变化且已开始交接的 key，包括请求路径创建的空归属交接；记录准备/已提交、源目标和防旧操作字段，不能只缓存于内存 |

低频配置/任务状态沿用 Server 的 pilot.db 方向；大量 key 交接记录采用 Gateway 本机独立任务目录下的 handoffs.db，复用现有 SQLite 驱动，不写入控制面 pilot.db，也不新增服务。当前仅支持单有效 Gateway 在原持久盘上重启；跨主机接管、日志盘丢失/回滚和协调备份恢复不在此实现保证内。日志不能单独恢复到早于已发布归属的历史版本。不引入永久业务 key 目录，也不能用概率过滤器判断交接成功。元数据不能被当作普通业务 key 迁移、返回或由缓存 LRU 淘汰。分片迁移引入的临时状态不应被误写为“仍然只有两个控制 key”。

已实现的日志基础（internal/gateway/sharding/journal.go）：

- 一个日志绑定一个任务 ID 和完整的新旧拓扑快照，恢复时逐项校验；新建目录与打开已有日志分开，禁止自动覆盖/重建丢失的活动日志。同一日志持有本机进程独占锁；这不替代控制面的同集群任务互斥或后端执行隔离。
- SQLite WAL + synchronous=FULL，单连接串行事务；准备、提交、清理确认均等待数据库提交结果，创建时同步任务及父目录。正常重复准备不重置状态。真实掉电、磁盘满和大规模 fsync 吞吐尚未验收，批量写入优化待定。
- 临时记录保存原始二进制 key、递增序号和 prepared/committed/cleaned 状态；源目标由不可变任务快照推导，不重复存地址或业务 value。仅归属变化的 key 可准备；空源新增 key 也必须交接。分页读取最多 1000 条，不把全部交接 key 放进 Go 内存。
- 状态推进核对任务、序号、key 和源目标，禁止跳阶段/倒退；重复确认幂等。已提交及已清理都只定位目标，目标不存在也不回旧源；未提交显式返回“需要交接”，不是允许直接执行目标命令。读取失败返回错误，不按记录不存在处理。写入返回错误时不能猜提交结果，应重读并由运行时恢复协议处理。
- 日志保存交接和最终发布状态；逐 key 复制/提交原语由内部请求路径及下述后台执行器调用，尚无公开任务管理入口。准备记录不是执行许可；数据库 CAS 只保护日志更新，不会阻止迟到后端命令。内部 Publish/Forget/Complete 已接入下述受控结束流程，不提供绕过后端隔离和清理条件的管理 API。

已实现的逐 key 搬迁原语（migration_fence.go / migration_copy.go）：

- 源、目标分别使用一个临时内部 Hash，名称为 `__pilot_cache_v1__:migration:<原 key 的 SHA-256>`。字段保存任务/记录身份、原 key、复制尝试标识、阶段和批次序号；不是热缓存 complete 标记，也不是永久 slot 索引。标记不设置 TTL，保留到未来任务级安全回收，不能交给 LRU 淘汰。
- 每个迁移脚本都在后端同时校验节点 owner、key 绑定、阶段和所需复制尝试/批次；所有访问 key 均声明在 EVAL KEYS 中。源冻结后，只有迁移感知业务保护能拒绝迟到写入；裸命令和原生阻塞写者不会自动受到 Hash 标记拦截，不能绕过下面的协调入口直接启用原语。
- 目标分批阶段为 copying，只有完整复制并确认后的 ready 才可提交日志；日志 committed 后将目标改为 serving，再清理源并记 cleaned。目标 ready 期间业务保护仍拒绝访问，日志提交失败不提前开放。提交后只补激活/清理，禁止重拷；源清理失败时目标归属不退回，运行时需将清理重试和业务准入分开。
- 复制尝试使用新随机标识并比较前一次标识；重复 Begin 不会删除已复制分批，旧 Begin 不能覆盖新尝试。分批按序执行，RPUSH 等不能因 ACK 丢失而盲重放。脚本在修改对象前记录 applying/resetting/sealing 等中间态，遇到执行错误不会把 Redis Lua 当成有回滚的事务；未提交时重新隔离并换尝试完整复制，已提交时不允许这样重置目标。
- String 每批最多 64KiB，同时按源/目标协议帧预算的四分之一缩小分块，给脚本及协议开销留空间；List 每批最多 128 个元素；Hash/Set/ZSet 使用对象扫描，出站参数再分批。原生对象直接在目标原 key 上构建，阶段屏障阻止半成品对业务可见；未用 DUMP/RESTORE，也未新增单对象大小准入上限。协议帧/单元素资源上限仍会使过大批次失败，不等于无限内存支持。内容正确性依赖源冻结、实际载荷及逐批确认；最终类型/数量校验只是补充，测试逐字段/成员/字节比较。
- 过期读取源的 PEXPIRETIME，并在完整目标设置同一绝对截止时刻，不在复制后重算一段完整 TTL；期间确认源已过期则清除目标半成品并交接空归属。未过期时复核源类型、大小、绝对过期时刻未变化。当前仅验证同机同钟模型，跨主机时钟偏差/突跳的准入和处理仍待实现，不承诺任意异步时钟下无过期偏差。[Kvrocks 命令表](https://kvrocks.apache.org/docs/supported-commands/)列出 PEXPIRETIME/PEXPIREAT 支持；这不是实际 Kvrocks 迁移验收。

这些原语要求调用者持有与所有业务/热回温共用的 key 准入控制，绑定正确后端及有效节点 owner，并已排空不能套脚本保护的写者。后端普通命令 ACK 不自动等于掉电持久化：真正删除权威源副本前，必须按冷库 WAL/刷盘/副本策略验证目标确认的持久性及业务要求；本地 SQLite FULL 不能替代 Kvrocks 的这项保证，当前复制原语不主动触发 Kvrocks 刷盘。内部后台扫描、最终发布/回收及同盘进程恢复已接入；跨主机时钟、真实引擎持久确认/阻塞排空、全部崩溃窗口和控制面任务装配尚未验收，不能部署为完整在线扩缩容。

内部后台迁移执行器（migration_worker.go / sharding/worker.go）：

- 与 Gateway 同进程，由 Service 启停并等待退出，不新增同步服务。同一个运行时只能有一个执行器；可选分片配置支持扫描批次提示、key/秒、通信字节/秒、单步超时，重试使用有界默认退避。默认单冷服务不启动它，在线调速和公开任务 API 未接通。
- 每轮先分页恢复 prepared/committed 记录，再对 ScanSources 做迁移扫描、从 0 开始的核查扫描。恢复分页绑定本轮序号上界，避免持续新增记录使扫描无法开始；不加载全库名单。核查补搬漏项，并检查遇到的应迁 key 已不在源端；发现 cleaned 日志与物理源残留矛盾时不宣告就绪，也不盲目删除矛盾数据。
- 单 key 失败登记安全错误码并继续其他 key；源扫描失败可继续其他源，本轮有失败则退避后重试。后台错误不会单独触发整库热隔离；实际受影响 key 的请求仍受交接保护。取消执行器只停止后台推进，不回滚已交接归属，不自动停掉业务路由。
- 所有扫描/交接受上下文取消与步骤超时约束。限速覆盖后台交接次数及主要扫描/复制请求和回复的编码字节，允许一帧突发，不是严格网卡带宽整形，也不包含建连、owner 探测等全部开销；取消等待不积累下一轮限速债务。前台按需交接不受后台速率限制。低速率与过短交接超时组合可使大对象反复失败，需要调整参数；这是操作时间预算，不是对象大小准入上限。
- handoffs.db 当前为 schema v3：v1→v2 事务性增加单行 worker_progress 和待恢复索引，v2→v3 增加最终发布状态，保留已有交接记录；已有版本要求的进度或发布状态缺失/损坏不能静默重建。进度含轮次、阶段、源序号、页游标、累计页数/访问数/交接尝试/失败及最后错误码，代次校验拒绝旧轮次写进度；发布后禁止重启复制或修改扫描进度。计数包含扫描重复项和重试，不作为唯一 key 数或完成百分比。
- 游标只用于观察，同盘重启或失败重试均增加轮次、重新恢复日志并从 0 扫描，绝不拿旧后端游标当继续扫描的可靠依据。已提交 key 只补目标开放/源清理，不用旧值重拷覆盖新值。进度落盘与逐 key 归属落盘分离，进度丢一页不会回滚权威归属。
- 两轮成功后，短暂取得拓扑写锁等待已准入请求结束，检查没有 prepared/committed，再持久化 awaiting_finalize 与交接序号上界。此状态只是“扫描核查暂时就绪”，不是任务完成、最终路由提交或允许下线节点。后续请求若留下新待处理交接，执行器自动唤醒恢复；内部最终发布仍重新核对屏障和日志，不能仅凭该状态操作。
- 执行器内部 Finalize 选项默认关闭，开启后自动衔接以下结束流程；公开分片配置的恢复装配固定开启，不提供可误关的 YAML 开关。已持久 published 的恢复不依赖该选项重新开启，必须继续采用目标路由及恢复清理；关闭内部选项不撤销已经发布的归属。任务准入仍需真实后端前置验收。

内部任务结束与下一轮（migration_finalize.go / sharding/finalize.go）：

- finalization 单行状态为 active→published→complete，与 worker_progress 分开。published 的原子落盘是“以后只认目标拓扑”的不可逆提交点；完整目标快照已随任务保存。进程恢复必须先打开准确的任务日志并装配发布状态，之后才开放监听，不能从旧配置直接开始业务。
- 发布前取得拓扑写锁，等待已准入请求结束、重新检查扫描就绪且没有未清理交接，并在所有参与冷节点上轮换 owner、确认成功，再提交 published。这样迟到的旧冻结/复制/写脚本即使遇到已删除标记，也无法重新执行。轮换失败不发布、不删标记，可自动重试。此阶段有受步骤超时限制的全局准入等待，不承诺零停顿。
- 发布成功后立即切换目标拓扑，丢弃迁移遍历对应的旧临时游标，取消源回落和新交接记录创建。待清理 key 的请求只访问目标，允许本任务 serving 标记仍在或已经清除，其他任务/阶段仍拒绝；与逐 key 清理共用锁。新的 key 直接在最终节点执行，不因旧日志缺记录而重新访问源。
- 标记回收按分页和限速逐 key 进行：源确认业务 key 已不存在、标记属于本任务且为 cleaned；目标标记属于本任务且为 serving。只删除标记，不删除业务数据；标记已不存在时幂等确认。两端都确认后才删除这条本地交接记录；回复丢失保留记录并重试，失败不阻断其他 key 或撤销目标路由。故障代码有事件计数，详细清理进度/管理指标尚待接入。
- 所有记录清除后，再次在拓扑屏障内轮换参与节点 owner，撤销本轮清理请求使用的凭据，阻止迟到清理碰到下一轮同名标记；随后持久 complete，解除任务互斥。新任务可以使用更高版本拓扑及新的日志目录，走同一链路扩容、缩容和再次扩容。每个结束屏障有步骤时间预算，但大 key 已准入操作可能额外延长等待。
- published/complete 写入结果未知时，先重读日志再决定路由；若连日志都暂不可读，拒绝未经确认的业务准入，由执行器自动重试，不能猜测回滚。这是权威路由状态不可确认的保护，不是普通清理失败就停止业务。清理到一半或清完但 complete 未确认均可同盘恢复。
- 启动/探测只检查当前拓扑及尚未清完任务需要的节点；complete 后已移除源节点不再影响启动和健康检查。保留的节点注册表仍可供内部下一轮装配，新增未初始化目标在进入迁移规则前初始化。不会自动关停或删除底层实例。
- complete 后保留任务身份、目标快照和汇总进度作为恢复/审计信息，不保留逐 key 交接行。SQLite DELETE 不保证文件立即变小，本阶段不自动 VACUUM、删除任务目录或清除所有历史文件。Gateway 本地 runtime.db 已保存准确任务引用并在启动时恢复，不按目录时间猜测最新任务；Server 持久登记、归档/磁盘空间回收仍待控制面接入，不能随意忽略最新日志或恢复到旧任务。

已接入的内部业务协调（sharding_backends.go / sharding_admission.go / sharding_runtime.go）：

- 启动前安装不可变节点注册表，各节点独立地址、密码和 owner；拓扑快照不保存密码。支持节点 owner 初始化、结果未知后轮换和探测；多冷配置与本地启动恢复见本文前节。
- 业务请求与迁移共用现有 key 锁桶；锁覆盖热读、回温、冷执行及缓存更新。拓扑切换先等待已准入请求退出；归属变化的 key 先交接再执行业务，空源新 key 同样写入交接记录。已提交但源未清理时只检查/开放目标，不让源不可达阻断目标业务。
- 实际冷写脚本外层校验迁移绑定及 serving 阶段，拒绝迟到源写或尚未开放的目标写；原脚本仍只看到原始 KEYS/ARGV。准入上下文绑定节点、key 集合及生命周期，禁止越界命令和释放后复用。原冷 owner 校验仍有效。
- 五类型普通命令、两种缓存策略、同节点 Lua/事务已接通；正常冷迁移不删可信热对象。跨节点 MGET/MSET/DEL/UNLINK/EXISTS 按节点顺序执行并汇总，保持重复 key 位置及同连接 Pipeline 顺序；跨节点写失败可能部分成功，不回滚或自动重放。跨节点原子命令、事务和 Lua 预先拒绝。
- WATCH 暂采用更保守规则：拓扑版本一旦变化，EXEC 返回空结果，即使被监视 key 的归属未变化。无 key 的受限脚本/事务选择固定节点；不授予未声明 key 的访问能力。
- 内部分片模式普通请求已支持 SCAN/HSCAN/SSCAN/ZSCAN，以及同节点冷层专用队列的 BLPOP/BRPOP，语义见下节；KEYS、跨节点阻塞及事务/脚本中的扫描/阻塞仍拒绝。默认单冷模式原有能力不变。不能在升级后带着未登记、未隔离的旧阻塞请求直接开启迁移。
- 当前仍只有一个共享热 Redis；热故障沿用隔离、清空和恢复机制。全库扫描、最终任务发布/标记回收、内部下一轮任务及同盘恢复已接入，尚无冷热独立拓扑、公开任务装配或全部崩溃窗口验收；内部显式迁移入口用于验证，不是管理 API。

内部分片模式的用户扫描（sharding_scan.go，不是后台迁移扫描执行器）：

- 对外游标仍为十进制 uint64，`0` 表示开始/完成。Gateway 本机内存最多保存 1024 个最近页面位置，每项有效期 5 分钟，满额淘汰最早签发项；只保存路由/后端游标和请求摘要，不保存业务 value 或全库 key 名单，不写 SQLite。成功读取且未失效的旧游标可重读页面，适用于前端回复丢失；Gateway 已观察到后端错误、身份变化或页面处理失败时删除本次使用的游标，后端恢复也不能复用它。重启、过期、淘汰或绑定不匹配返回 TRYAGAIN，要求从 0 重新遍历，不假报遍历结束。命令/key/选项摘要不匹配的误用请求不会删除原合法游标。
- 游标绑定命令、原 key（对象扫描）、选项原始字节、拓扑版本、当前节点/owner 和后端身份提示。Redis 优先使用 run_id；无该字段的 Kvrocks 使用 `process_id` 与秒级启动时间 `floor(server_time_usec/1000000)-uptime_in_seconds`。INFO 的两个时间字段非原子采样，在同一条不自动重连的直连连接上追加 TIME：仅当 TIME 仍在 INFO 记录的同一秒且微秒未倒退才接受，否则最多重新采样三次，失败只要求本次扫描从 0 重来。身份检查和当前页扫描使用同一条连接，每页结束关闭，不为遍历长期占用连接。缺失、重复、负数、溢出等无效字段明确拒绝，不用空身份放行。
- 启动时间＋PID 只是用户只读扫描的重启提示，不是严格的进程唯一标识：同秒重启且 PID 复用、时钟跳变等极端情况仍可能漏判或要求重扫，不能据此承诺跨进程重启的快照/完整遍历。它不用于迁移写入放行、旧阻塞连接排空或交接完成证明，也不创建后端控制 key。后续页保持相同选项，包含 COUNT；不支持套用原后端裸游标。后端游标本身按不透明字符串保存，上限 1024 字节。后台任务的每轮重扫及持久交接日志是另一条路径，不依赖此提示。
- HSCAN/SSCAN/ZSCAN 每页持 key 准入，只读权威冷对象，不触发热回温；第一次从 0 扫描可以先完成必要交接。旧拓扑下产生的游标不会被发送至新节点，遇拓扑版本变化从 0 重扫。迁移过程中开启的新对象遍历先交接到目标，后续页保持目标绑定。内容修改/删除重建沿用非快照扫描语义。
- 稳定拓扑下 SCAN 依次访问全部节点；迁移拓扑下先完整遍历全部旧节点，再完整遍历全部目标节点（保留节点也会再扫一次）。一页最多调用一个节点的 SCAN，空页不等于完成；不为去重保存全库 key 集合。后台迁移扫描源选择与这里的遍历顺序不同，不能共用“只扫缩容移除节点”的列表。
- 全库页面逐 key 在迁移锁下核对归属和日志，排除内部标记、非权威旧副本、未提交目标半成品；读取日志失败返回错误，不能当成无记录。扫描本身不主动交接看到的 key。依赖后端对持续存在元素的 SCAN 保证：旧遍历期间搬走的持续存在 key 会在目标遍历前到达目标，未搬走的由旧遍历覆盖。允许重复和并发新增/删除的不确定结果，不保证快照；本地 Redis 与真实 Kvrocks 2.15.0 的扩容/缩容分页交错迁移专项均已覆盖该顺序，不外推为所有引擎版本或跨故障完整遍历保证。
- 事务与 Lua 中暂不接受扫描：不能把 Gateway 游标交给原生脚本，也不能让它绕过上述绑定。KEYS 暂不做跨节点整库聚合。默认单冷模式保留此前矩阵，不受这些内部模式限制影响。

内部分片模式的原生阻塞与排空（sharding_blocking.go）：

- 仍只接受 BLPOP/BRPOP、1～16 个固定 cold_only_prefixes 队列和 (0,60] 秒等待；全部 key 的目标冷节点必须相同，跨节点预先拒绝。沿用 max_blocking 并发限额、原生多 key 优先顺序和返回值，不改成轮询 LPOP；队列不会回温。
- 在共同 key 准入内完成必要交接，为专用后端连接设置随机唯一名字并读取 CLIENT ID，再用带 owner 与迁移阶段校验的脚本登记。只有登记回复确认后才发送原生阻塞命令；登记未知则明确报“pop not sent”，不试探性执行。登记后释放普通 key/拓扑锁再等待，LPUSH/RPUSH 不会被阻塞消费者锁住。
- 2026-09-14 阻塞路径取消 INFO server/run_id 依赖。Kvrocks 2.15.0 缺少该字段的兼容性问题改由连接身份协议处理，不模拟进程 ID，也不使用 PID/推算启动时间证明旧请求结束；用户扫描的辅助身份规则见上节，与阻塞排空独立。
- 每个冷节点至多一份 `__pilot_cache_v1__:blocking` Hash，字段是随机会话 ID，v2 值保存版本、连接 ID/名字及涉及的原 key，不再写 run_id；二进制 key 以 JSON base64 编码保存。可读取旧 v1 登记，但其中 run_id 仅用于格式兼容，不能跳过连接确认。只有未完成/未清理的阻塞连接有记录，不是全库 key 目录或热缓存 complete 标记；每节点最多 256 项，满额拒绝新阻塞请求而不扩张登记表，不影响普通命令。最后一项清除后 Hash 自动消失。
- 搬迁仍持相应 key 锁，因而不能再登记这个 key 的新阻塞连接。源/目标处于 prepared 交接时先读取相关登记，在同一条固定直连且不自动重连的控制连接上执行 CLIENT LIST → 按 ID 关闭 → LIST 确认消失。先匹配随机名字，再核对唯一 ID；无该名字时不操作可能被复用的旧 ID，同名不同 ID 或重名则保留登记并报错。只有确认名字消失，才删除登记并继续复制。进程若在查找与关闭之间重启，原控制连接失效，本轮不重新连接发送旧 ID。仅关闭本地 socket、仅收到 KILL 的 0/1 返回值都不作为完成证明；超时/列表异常/身份变化保留记录并让受影响搬迁重试。非队列 key 不额外查询阻塞登记表。
- Kvrocks 2.15 的 KILL 是标记异步关闭，而非同步释放连接；实现据此增加列表确认。[Kvrocks 2.15 Worker 源码](https://github.com/apache/kvrocks/blob/v2.15.0/src/server/worker.cc) 中 KillClient/FreeConnection 展示这一区别。[命令表](https://kvrocks.apache.org/docs/supported-commands/)列出 CLIENT ID/SETNAME/LIST/KILL。真实测试发现，已阻塞连接可能一直保留至原生命令超时，期间相关 key 的迁移不能越过连接确认；正常等满 timeout 的空数组可以返回，传输中断/未知结果仍报错、不重放。等待排空也可能延迟该 key 的请求，其他 key 的普通读写不因此停服。测试必须在迁移返回后立即断言连接及登记已消失，不能仅等待弹出请求最终结束就宣称排空通过。
- 阻塞返回后尝试确认断连和清理；清理失败保留记录，现有探测循环自动处理本机已不活跃的遗留会话，不隔离热缓存或停止无关普通请求。Gateway 被强制终止后，本机活跃表虽丢失，冷节点登记仍在，重启后的探测及迁移准入可继续处理。冷进程重启后仍查询随机名字是否存在，不凭时间变化直接删除登记，也不拿未匹配名字的旧 ID 终止新进程连接。普通后端 ACK 的持久性、冷盘回滚/丢失仍属于单独的存储可靠性边界。
- 搬迁可能打断等待；原生弹出已执行但回复丢失时返回结果未知，不自动再次消费、不把打断当成正常空结果。登记 ACK 丢失则不能发送弹出，迟到的注册受 owner/阶段保护，已登记但迟到发送的原生命令由后端断连隔离。
- 当前前提仍是固定直连后端、单有效 Gateway、固定专用前缀和禁止绕过 Gateway 写入。不支持通过会重连/重放命令的代理连接冷层，不支持后台无协调切换地址、恢复数据库或在线调整 Kvrocks worker 造成连接重新登记；这些会破坏连接身份/列表观察的前提。迁移前也必须另外处理旧单冷版本留下的未登记阻塞连接。真实 Kvrocks 验收完成前，仍不开放生产配置。

- 目标只复制一部分或已写但归属未提交：不能开放目标或猜测成功；读取日志，在隔离旧执行者后恢复。日志与后端写入并非天然原子，需要明确提交点与所有崩溃窗口。
- 已提交但源残留：只访问目标，自动补清理。目标后来删除/过期时，禁止按“目标不存在”回落旧源使旧值复活。
- key 已提交记录保留至最终路由生效、旧执行者被隔离且相关旧副本安全清理后，才允许按任务回收；元数据不可用/结果不明不能当成“未交接”。
- 请求超时不取消后端已接收命令；迁移复制、发布、清理、业务写与热回温均需防迟到操作。代次必须在实际后端修改时原子校验，或由经验证的连接排空/隔离协议实现等效保障，不能只在 Go 内检查后裸发命令。当前本地 flock 与单冷 owner CAS 不是现成的跨节点迁移恢复协议。
- 故障时自动退避、恢复明确可重试的内部步骤；INCR、POP、EXEC、Lua 等业务请求结果未知不重放。无法确认时暂停受影响交接/请求或返回错误，尽量不阻断无关业务；不为了可用性返回旧数据。
- 计划缩容先检查剩余容量、迁移临时空间与负载，全部排空确认后才允许下线。源不可达且无副本不属于安全缩容；复制丢写、磁盘损坏、冷库恢复仍需独立的存储可靠性保障，不能从哈希排名选择一台空节点假装接管。

### 热层、资源与尚待验证事项

冷热分别选址；只迁移冷层且热节点不变时，协调完成后可保留可信完整热对象，不因换冷节点就整删大 Hash。后续写沿用 invalidate/update_existing，迟到回温不能覆盖新缓存。热层扩缩容可选择丢弃受影响缓存后按新路由回温，无需复制每份缓存；但必须隔离旧热路由上的写入/回温，不能新节点 miss 后回读旧缓存。热故障恢复的隔离范围从当前整库到多热节点如何划分，具体实现待定。

以下为实施前的技术验证项，不是另加产品能力：

- 临时状态存储基础已落地；继续完成它与实际后端写入之间的崩溃恢复协议，逐项验证源冻结、目标准备/提交、源清理的迟到操作隔离；禁止仅凭本地锁或关闭本地 socket 声称安全。
- 五种类型逻辑分批复制与目标阶段屏障已有独立实现及本地 Redis 测试；继续验证真实 Kvrocks 下的完整性、二进制内容、分批重试、Lua 错误/崩溃持久性与跨主机 TTL，不假设 Redis 测试结果可直接替代。
- 当前 256 锁桶有碰撞，长迁移可能阻塞无关 key；评估是否引入只覆盖活跃 key 的有界控制结构，不承诺现有桶锁能精确只暂停一个 key。
- 同节点 BLPOP/BRPOP 的连接登记、后端排空和遗留会话自动清理已接入内部链路；2026-09-14 在真实 Kvrocks 2.15.0、workers=2 下阻塞专项三轮通过，覆盖迟到发送、异步 KILL 假确认、控制连接断开和双方进程强杀重启。旧未登记连接升级排空、更广泛配置及长期稳定性仍待验证。默认单冷阻塞路径不变。
- 外部 SCAN 和对象扫描的内部路由/游标实现已接入，继续验证真实 Kvrocks、并发变更和故障边界；这里的用户遍历不替代后台迁移任务的两轮扫描、进度持久化和完成证明。SCAN 不承诺快照语义。
- Server/API/CLI 的任务启动、状态查询、限速、暂停/恢复、指标和基础界面接入；限制任务重叠。暂停不是回滚，已交接 key 继续访问新位置，取消/逆向迁移策略待定。

若验证表明必须修改数据库源码、新增外部服务、支持多活或牺牲已约定的一致性，先说明并取得用户决定，不自行扩大范围。

### 实现顺序与验收

先实现稳定路由及新旧配置比较、后端选择与命令边界；再闭环实现状态存储、五类型复制、安全交接和自动恢复；随后接入两轮扫描、冷热独立扩缩容、任务管理与观测。按完整功能链路集成，不以“能复制一次”作为完成；开发过程中保留必要单测，集成完成后进行真实开发环境的端到端与故障验证。

验收至少覆盖：固定配置跨重启路由一致、N+1/2N/任意节点缩容、重复扫描、持续新增/更新/删除/过期、两种缓存策略、已有大 Hash 保持完整、事务/Lua 交接保护、WATCH 失效、重复 key 批量顺序及部分失败、迁移各持久化边界 SIGKILL、ACK/回复丢失、迟到复制/删除/回温、状态存储失败、磁盘不足、任务续跑与安全清理。以真实 Kvrocks 验证，不以 Redis 替身或理论迁移比例代替数据正确性和性能结论。

参考：Codis [批量分发实现](https://github.com/CodisLabs/codis/blob/release3.2/pkg/proxy/session.go)、[命令限制](https://github.com/CodisLabs/codis/blob/release3.2/doc/unsupported_cmds.md)、[迁移转发](https://github.com/CodisLabs/codis/blob/release3.2/pkg/proxy/forward.go)、[修改版数据库迁移实现](https://github.com/CodisLabs/codis/blob/release3.2/extern/redis-3.2.11/src/slots_async.c)；[Jump Hash 论文（含 HRW 比较）](https://arxiv.org/pdf/1406.2294)。Codis 的屏障/ACK/数据库执行包装不等于本设计已具备持久化代次协议；放弃 slot 索引只替换发现待搬 key 的方式，不替代安全交接。

## 其他后续边界

当前已支持明确矩阵内的跨 key 操作、事务和受保护用户 Lua；任意阻塞命令、Hash 字段 TTL、位图/Bitfield/HyperLogLog 等未列扩展仍不支持。字段缓存、大对象白名单、全量布隆过滤器未引入；不承诺所有 Redis 版本或所有引擎极端语义完全一致。验收基线为热 Redis 7.2.5 + 冷 Kvrocks 2.15.0。

后端路由与冷热请求已分离；当前连接按操作建立，尚未做连接池和吞吐优化。HRW 路由、迁移日志和逐 key 搬迁已接入请求链路，多冷 YAML 启动/恢复已开放，但公开任务调度入口尚未接通，不能视为完整在线扩缩容；Redis Cluster 的 MOVED/ASK 协议、多 Gateway 多活/跨主机接管、冷库复制与故障切换不在本次实现范围。不能把固定锁桶或已有单冷 token 校验当成这些能力。
