# 冷热缓存设计

更新：2026-09-10。当前开发实现与限制见 [实现状态](hot-cold-status.md)，配置和部署见 [部署运维](gateway-deployment.md)。

## 契约与职责

Kvrocks 是唯一权威存储，保存完整业务数据；Redis 是可丢弃缓存。所有业务访问必须经过同一个有效 Gateway，不能旁路修改冷库、缓存或内部元数据。不再使用 PSYNC 同步器、复制日志、冷热所有权转移和主动降冷器。

Gateway 属于数据面：读写路由、缓存更新、回填、一致性协调。独立二进制由 systemd 管理；Agent 只管理数据库容器，Server 管理配置/观测，Proxy 负责接入。当前固定本机回环端点、单 Gateway、DB 0；不是多 Gateway 或 Cluster 方案。

目标：写请求返回成功后，随后发起的读不能返回旧缓存。响应丢失仍可能是已执行，不承诺 exactly-once；非幂等业务请求不自动重试。底层冷库回滚、复制丢写、备份恢复或外部写入不在缓存协议保证范围，不能用缓存补偿冷库持久性。

## 两种写后策略

| 配置 | 处理方式 |
| --- | --- |
| invalidate（默认） | 冷层执行修改，随后删除热缓存 |
| update_existing | 冷层执行修改后，对支持的命令同步重建已有完整小缓存；未缓存的复杂类型不主动创建；普通 SET 可创建小缓存 |

首版的更新策略采用有界完整重读/重建，不是在两库分别执行同一条修改命令，因此 SPOP 随机选择、INCR 重放等不会造成两边独立运算。支持更新的命令见实现状态；其他写命令回退失效。这比原地增量更新多冷读开销，后续性能优化不能改变正确性边界。

缓存更新失败时，冷层已成功的业务不重做。使旧缓存命名空间失效后仍可返回冷层成功结果。大小和元素限制同时约束读回填与写后更新；超过限制只走冷层。

## 读与对象完整性

可信缓存命中时在 Redis 原子检查 data 和 complete 两个 key，再执行白名单读命令。未命中读取冷库，并尝试加载完整小对象。不存在不填缓存；超时不当作不存在。TYPE 等状态回复按 Redis RESP2 对外规范转换，不直接暴露不同引擎脚本结果的形状差异。

五种类型按完整对象缓存：String GET、Hash HGETALL、List LRANGE、Set SMEMBERS、ZSet ZRANGE WITHSCORES。先检查 TYPE、PTTL 和长度/数量；超过数量限制立即放弃加载。回复解析另设缓存快照字节/元素上限，超限丢弃该只读连接，不无限制累积内容。业务响应仍受独立 RESP 上限约束；大对象不缓存不等于无限制响应。

默认 64KiB、256 个元素、4 个并发加载；可用 cache.types 按 string/hash/list/set/zset 覆盖字节数和元素数。字节数包含字段名、值、成员及分数的编码，不等于 Redis RSS。一次 HGETALL/SMEMBERS 等在后端自身构造回复的临时开销不受 Gateway 解码上限控制，极端大字段仍需后端资源约束与后续加载优化。

发布脚本先删除旧 data/complete，构造完整原生对象、设置缓存 TTL，最后发布 complete 标记。脚本不是可回滚事务；中途 OOM/错误可能留下部分数据，但没有 complete 的对象不可命中。任何缓存执行错误会换本地热代次，隔离迟到脚本。LRU 淘汰任一 key 都只造成未命中，不会把残缺集合当完整对象。

支持 SET EX/PX、NX/XX、KEEPTTL（过期选项互斥、条件选项互斥），以及无条件 EXPIRE/PEXPIRE/PERSIST。所有条件与业务过期时间由冷层执行；明确未生效的条件写不更新缓存。默认 SET 清除业务 TTL，KEEPTTL 保留它。TTL/PTTL 始终查冷层。

带业务 TTL 的完整小对象允许回温。发送 PTTL 前记录单调时间，以该时刻加剩余 TTL 作为保守截止时间，和缓存默认 5 分钟上限取较早者；快照、网络耗时均扣除。完成标记携带相对本进程单调时间原点的截止时间，Gateway 收到热读回复后再次校验，避免迟到发布/回复延长生命周期；Redis 相对 TTL 用于回收，不单独承担正确性。重启不复用旧命名空间。仍要求冷层时钟正常运行，不保证冷层时钟突跳或外部直接改 TTL 后的缓存一致性。Hash 字段 TTL 尚未支持。

## 同 key 协调与代次

当前使用固定 256 个锁桶：同 key 的读、写、冷读取和回填完整串行；不同桶并发，哈希碰撞会保守串行。锁等待有请求截止时间，不维护全量 key 目录。此处的锁桶不是集群 slot，也不提供分布式归属。

每个普通业务命令通过固定内部 EVAL 执行：检查冷层 owner token，再执行白名单命令。用户 Lua 不能透传。INCR/DECR/INCRBY/DECRBY/HINCRBY 使用冷层最终字符串转回整数回复，避免 Lua double 丢失大于 2^53 的整数精度。

- 启动：持有本地私有 flock，读取旧 owner，通过比较交换设置随机新 token；新热缓存命名空间不读取上次进程遗留缓存。
- 冷请求结果未知：不重放请求；把本地 token 置为待确认新代次，后续冷 CAS 确认后才恢复请求。迟到旧命令因 token 不匹配而拒绝执行。CAS 可安全重试，迟到旧 CAS 不能覆盖新 token。
- 热请求/失效/发布失败：递增本地热代次，旧缓存即时不可见；后续请求自动尝试新命名空间，不扫描或清空 Redis。
- 热节点不可用：使用较短 hot_timeout 给冷读取预留时间，后续请求继续尝试；不要求人工恢复缓存。
- 冷不可用：需要冷库的请求报错，不确认写成功。已有可信热读是否成功取决于当前 token 是否已确认；冷写结果未知后的旧代缓存不能继续使用。

冷库仅保存少量固定控制元数据，不保存每 key 同步位点。保留前缀 __pilot_cache_v1__:，业务命令禁止操作。配置 exclusive_backends 是部署前提声明，不是多节点租约；不同主机或不同锁路径启动重叠写者不受本地 flock 保护，禁止这样部署。

热 Redis 必须 maxmemory > 0、allkeys-lru、appendonly no、save 空。每次热连接核对这些约束；禁用持久化避免 Redis 重启恢复同一代已失效的旧缓存。不能在线改变这些约束或手工加载旧快照。

## 阻塞命令

首版仅支持 BLPOP/BRPOP，1～16 个 key、有限等待 (0,60] 秒。使用独立冷连接和并发限额，不持有普通 key 锁，不妨碍 LPUSH/RPUSH；不允许无限等待、BLMOVE、BZPOP 或任意阻塞命令透传。

所有阻塞 key 必须属于配置的 cold_only_prefixes，这些 key 的所有普通读写也始终绕过缓存。这样即使 Gateway 崩溃或弹出回复丢失，迟到弹出也不可能使新热缓存变旧。

前缀集合写入冷层固定策略元数据，重启时必须匹配；禁止原地移除/修改后直接缓存旧队列。动态“仅在阻塞期间绕过、结束再恢复”以及前缀变更迁移尚未实现。业务连接断开后的后台等待当前受有限超时/服务取消约束，不承诺立即取消服务端已经执行的弹出。

## 后续边界

多 key、事务、用户 Lua、任意阻塞命令、EXAT/PXAT、EXPIRE 条件选项、字段缓存、大对象白名单、全量布隆过滤器均不在当前命令范围。有限单 key 支持不等于五种类型的所有命令兼容。

后端路由与冷热请求已分离；当前连接按操作建立，尚未做连接池和增量缓存更新优化。分片、冷热独立扩缩容、MOVED/ASK、跨 slot Pipeline、多 Gateway 接管和旧写者隔离待单独设计。不能把缓存代次或固定锁桶当成这些能力。
