## 当前能力清单

| 普通丢回复/dirty | 已修正 | 不自动重放、不永久封普通 key、不设置分片级永久暂停；已有操作局部保护仍保留 |

| Cluster/高可用 | 未实现于冷热链路 | slot/重定向、动态任务、扩容/切主、分布式归属和旧执行者隔离待做 |
| 性能与长期稳定性 | 未完成验收 | 已有隔离短测试，不代表生产热写延迟、同步吞吐、内存收益或长测通过 |

## 当前交付：单 key 冷热闭环与水位自动调度

`hot_cold` 开发配置统一启用内部 `ManualResidency` 与 `BoundedMarkers`，要求独占 Gateway 入口、noeviction、固定复制历史及独占冷 DB。没有修改 Redis/Kvrocks 引擎，没有控制面自动切流；部署步骤见 [运行文档](gateway-deployment.md#从配置启用手动冷热模式)。

- `POST /internal/v1/hot-preparation/evict` 接受 `key`（JSON base64）及可选 `operation_id`。省略编号时从持久的前一操作递增 128 位编号；同 key 未完成操作复用编号，已冷 key 返回已有编号，溢出拒绝而不回绕。接口允许普通 JSON 空格/字段顺序，拒绝重复字段、未知字段和尾随内容；内部签名/哈希证据仍使用原严格解析。响应及 `X-Operation-ID` 返回编号，超时可用该编号重试；自动后台收尾只保留热数据，不自行降冷。
- 源 Redis 每个参与转换的 key 使用一个哈希命名的驻留标记，保存操作意图及 cold/hot 状态。删除热副本和发布 cold 标记是同一个内部脚本；标记不因回温立即删除，防止迟到旧脚本再次删除新值。元数据成本随参与转换的 key 数增长；隔离 32 KiB String 的键分配从 41,024 字节降为两个标记合计 1,056 字节，但不是 RSS 或整体成本验收，小值可能不划算。
- 业务请求仍去 Redis：内部脚本原子检查驻留状态并执行命令。冷 key 返回明确的“尚未执行业务”；Gateway 从 Kvrocks 读取无 TTL String、核对意图哈希，条件回温后再执行原请求。已经执行但丢回复的 INCR 不重放。其他请求已回温并修改时，旧回温脚本不会覆盖新值。
- 同步器将精确的内部 MULTI/SET/UNLINK/EXEC 或回温 MULTI/SET/SET/EXEC 识别为一个 v3 控制 pending，检查完整逐帧链与冷值，再原子推进 checkpoint，不对冷数据执行内部 UNLINK。普通业务 DEL 照常同步。日志回收保留整组开头，不能只保留 EXEC 所在段。
- 冷连接不可用只使确实需要回温的请求返回 TRYAGAIN；热 key 请求不等待冷连接。热删除回复不确定时不永久锁 key：原子驻留检查处理已经降冷的事实。同目录重启保留此行为；持久启用标记禁止静默退回无驻留检查的模式。
- 当前为验证正确性，开启此内部模式后每条连接逐命令完成，包括 Pipeline；保序但暂不批量派发。热请求增加 Redis 内部脚本执行，不同步等待 Kvrocks。没有完成性能验收，不能沿用旧 passthrough 性能结论。

边界：只支持现有单 key 无 TTL String 子集；没有 Cluster、任意切主/FULLRESYNC 替换保证。Redis 驻留标记必须与业务数据一起持久化/恢复，外部删除元数据或源数据回滚不在已验证范围。编号分配目前是单 Gateway 本地串行持久协议，不是多写者编号服务；元数据压缩/回收及热写性能优化仍待实现。

自动模式通过 `hot_cold.auto_eviction.enabled` 显式开启，默认关闭；同一个 Gateway 的后台任务复用上述降冷协议，不新增进程。默认 80% 开始、70% 停止，每批结束后等待 5 秒，最多采样 64 个 key、尝试 4 个、总耗时 3 秒。使用 `(used_memory - mem_not_counted_for_evict) / maxmemory`，不是 RSS；maxmemory 未设置或观测异常时不执行降冷。

候选仅限不超过 256 字节的非内部 key、无 TTL String，空闲至少 1 分钟，`MEMORY USAGE` 在 8KiB 与现有 64KiB 值上限之间。内存用量不是 String 长度，最终准备仍检查实际值大小；保守跳过小对象及部分接近上限对象。只保存一页候选，按空闲时间排序；执行前重新检查资格。采样不 GET/STRLEN，不刷新 LRU；这不是全局最冷保证，也不保证降冷后一定不再访问。

每批预检绑定、同步进度（默认源/已应用差距不超过 1MiB）和冷库连通性；真正删除仍必须经过原有精确冷确认。失败结束本批，后续自动检查；不关闭普通热读写。已有未完成转换交给原后台收尾，不重复分配操作。没有合格候选、冷热抖动、同步持续落后或冷库长期故障时，不保证达到低水位，内存满仍可能 Redis OOM。指标见部署文档。

新增启动能力：`-check-config` 只检查配置/凭据，不创建状态；`-init-state` 只允许显式初始化空私有目录，正常启动只恢复。启动核对源角色/复制历史/noeviction。首次引导同步后再固定复制历史，避免使用建立 backlog 之前的编号。已在 redis03 使用独立二进制 + systemd 部署，原 redis01 Gateway 和业务 Proxy 路由不变。

## 已有基础：保留热数据的准备收尾

本轮完整链路验证见 [手动冷热闭环测试记录](benchmarks/manual-residency-20260909.log)：真实 Redis/Kvrocks 三轮通过，覆盖冷态 Gateway 重建、独立同步器重启、Pipeline 保序、并发 INCR、普通 DEL、迟到脚本和注入冷连接故障；不替代性能、Redis 源重启和生产部署验收。

该基础路径本身不删除热数据；上面的手动闭环在此基础上额外校验并转换驻留状态。不宣称完成整个冷热产品。

2026-09-09：准备等待/只读检查等前置失败，在尚未开始持久化意图且未派发准备时自动撤销。已持久化操作新增内部 `/internal/v1/hot-preparation/finish`：表示保留热数据结束本次准备，不是删除授权，不是降冷成功。

已实现路径：

- Gateway 先持久化收尾意图，必要时重试准备/确认，再调用同步器。后台退避重试，客户端断开、Gateway 重启后仍继续已有收尾请求。
- 未显式请求收尾的操作，控制器从持久操作接入起默认等待 30 秒后自动持久化收尾意图；重复准备/确认不延长当前计时。重启恢复未完成操作时重新安排 30 秒兜底，不恢复原来的绝对截止时间。已持久化收尾请求仍直接进入重试。该时间只控制内部实验兜底，不是生产降冷频率，也不是最长阻挡时间。
- 同步器用一条事务内 MSET 原子提交准备标记对应的 checkpoint、控制型 pending 和终态回执；不再次执行业务 INCR，不删除热数据。
- 同步器持久化本地终态并恢复后续应用；若冷层已提交而本地终态尚未写入，重启后核对精确回执及日志进度恢复。
- Gateway 持久收尾意图后，核对 Redis 复制历史、noeviction、准备标记精确内容及无 TTL；缺少有效标记时只在原准备条件仍成立时补准备，再核对。核对成功即释放匹配 key 屏障，进入 `hot_available_sync_pending`，冷确认在后台继续。旧脚本遇保留标记只能无操作返回或拒绝，不会再次产生准备事件。
- 热访问释放不持久伪造冷层成功；Gateway 重启先恢复保护，再核对源标记并释放。冷收尾成功后才清理收尾意图、结束当前任务操作并接受下一次转换；只释放普通业务，不放开下一次降冷。冷确认不再重新准备，也不会把恢复访问后的新值写回成旧值。
- 本地操作文件原子替换，保留最后一次操作；完整但落盘结果不确定的帧可重开、验证、再次 fsync，损坏记录不盲目解锁。

尚未完成，不能视为整项产品验收通过：

1. 源 Redis 不可达、历史改变、准备标记损坏或无法补准备时仍不能核对并释放；不能声称“超时就一定恢复访问”。已核对源标记的保留热数据路径不等待冷确认，但不适用于未来已经发出热删除的操作。仍要求独占源入口、标记不被外部删除、noeviction；切主隔离未验收。
2. 旧 v1 每操作准备标记仍保留且随操作数增长。开发冷热配置固定使用 v2，复用一个准备标记，不做 DEL；只支持新建、独占的协议环境，已有 v1 操作目录不能直接切换。配置与本地自动编号已实现，旧脚本隔离、旧标记迁移清理、多写者分布式归属仍待实现；原子替换遇进程崩溃时的临时文件回收也待补。
3. 复制历史改变、记录损坏、资源耗尽与同步任务终止后的恢复仍有边界；不是任意故障都已自动修复。
4. 手动热副本删除、冷读和回温已有开发配置入口；TTL、Cluster、性能与生产故障边界仍未验收，不做生产切流。
