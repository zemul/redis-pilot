# G6a-11：独立同步服务的静态多任务与身份隔离

> 历史阶段归档：保留当时的方案与验收记录，不代表当前能力或恢复策略。现状以 [现行设计](../../hot-cold-gateway-design.md) 和 [实现进度](../../hot-cold-status.md) 为准。

## 本轮目标与边界

在 [G6a-10 独立服务入口](syncer-service.md) 上增加单进程 **1～8 个静态隔离任务**。任务分别持有复制连接、日志、冷层连接和确认状态；Gateway 不启动同步器，Agent 也不安装或启停同步器。继续使用独立二进制 + systemd，不新增第三个协调服务。

这里的“多任务”是本地受控并发管理，不是生产 Cluster：仍只接受 loopback 后端，不能把示例中的三个地址换成远端 Cluster 节点后直接使用。每个任务必须独占一个冷 DB；本阶段没有冷层共享、动态配置热更新、Server 任务分配、分布式所有权、fencing、故障接管或扩容迁移协议。

未来按每个启用冷热功能的 Redis 主分片设置一个活跃同步任务，因此 3 主 3 从应是 3 个任务，不要求三个同步服务进程。G6a-11 只实现这一模型的静态多任务运行，不证明真实主分片切换、slot 迁移或自动增加任务已经安全。

## 配置模型与兼容

完整三任务配置见 [syncer-multitask.yaml](../../../examples/syncer-multitask.yaml)。服务级 `mode`、`admin_listen`、`io_timeout`、`shutdown_timeout` 在顶层，源/冷目标、凭据、日志和资源预算逐任务指定：

| 作用域 | 字段与约束 |
| --- | --- |
| 服务 | `mode: isolated`；loopback 管理监听；I/O 与停止预算沿用 G6a-10 |
| 任务标识 | `task_id` 必须唯一，为 1～64 个 ASCII 字母、数字、下划线或连字符；是非敏感运维标识，可出现在状态、日志和指标中 |
| 独占后端 | 每任务明确 `source_address`、`cold_address` 与 `confirm_exclusive_cold: true`；源冷不能相同，任务间任意源/冷端点也不得复用 |
| 凭据 | 每任务独立密码文件；无密码必须明确 `allow_unauthenticated: true`；仍不支持配置内明文密码 |
| 本地状态 | 每任务独立、绝对路径的 `journal_dir`；父目录预先准备，不能复用、嵌套或通过路径别名绕过隔离检查 |
| 日志预算 | 每任务 `segment_bytes` 默认 4 MiB、`journal_bytes` 默认 128 MiB；有效范围沿用隔离内核约束，全进程任务声明总预算不超过 1 GiB |

原顶层单任务 YAML 继续按 legacy 模式运行，不强制补 `task_id`。`tasks` 配置与任何显式 legacy 任务字段不能混用，包括空字符串、`false` 和 `0`。不能把顶层预算当作多任务默认覆盖；多任务预算应在每个任务内填写或使用该任务默认值。

一旦使用 `tasks`，即使只配一个任务也要有稳定 `task_id`，按 named-task 协议运行。增减或调整配置需要有界停止并重启服务，不提供在线增删任务接口。`-check-config` 仍只读取配置和凭据，不创建日志、不连接后端；通过检查不代表旧日志身份或冷层数据满足运行条件。

日志路径比较会只读解析已有祖先的路径别名，启动前重新校验；这不是对整个文件系统的锁定。配置、日志目录及父目录必须由可信账户控制，运行期间不得切换符号链接或挂载。系统已有等价路径别名不被一概禁止，不能用它们绕过同目录/父子目录冲突。

## 元数据与持久身份隔离

每个 named task 派生自己的冷层元数据：

```text
__pilot_sync_v1__:{task:<task_id>}:v2-checkpoint
__pilot_sync_v1__:{task:<task_id>}:v2-pending
__pilot_sync_v1__:{task:<task_id>}:v2-anchor
```

legacy 空 ID 继续使用原 `{isolated}` 键，不替换已有恢复协议。命名隔离只是防止误用元数据的一个保护，不表示多个任务能共享一个冷 DB：任务打开冷层时仍检查独占与 bootstrap 条件，发现其他同步任务元数据应停止，不采用、不覆盖它们。

named journal 的持久身份绑定 `task_id`、规范化源地址和冷地址。重启时必须一致：改变 ID、源地址、冷地址，或把 named 改回 legacy，都会拒绝继续运行。规范化等价的地址写法不是迁移。此处绑定的是配置端点；仍不等于已实现主从切换的逻辑分片身份、复制历史接管或 DNS 发现。

已有 legacy journal 使用原格式，不自动升级或收编为 named journal，**即使旧日志为空也不能通过加一个 ID 直接复用**。已有数据的转换方案待定；不得删目录、删冷元数据或另起空目录来绕过检查。初次受控测试的 named task 必须使用专属新日志目录与专属空冷 DB。

独立日志锁只保护对应的本地目录。不同机器、不同目录或不同同步服务进程的端点归属仍没有全局互斥；配置冲突检查只覆盖本进程任务列表。运维必须确保测试后端不会被其他进程同时使用，不能把本地多任务检查当作分布式 fencing。

## 生命周期与失败隔离

所有配置和凭据先校验，管理监听成功后才启动任务。各任务独立运行；一个任务遇到终态失败时保留其错误，服务进入 `degraded`，其他未结束任务继续同步，不因一个任务失败而丢弃其他任务的已持久进度。

这不包含失败任务的外层无限重启。源/冷连接受控重试仍由单任务内核处理；uncertain、日志身份/历史冲突等终态要保留现场，由操作者确认恢复方式。所有任务都结束时服务退出；非预期结束或任何任务历史失败使最终退出码非零。收到停止信号后其他任务完成排空，不能把先前失败改写为“全服务正常停止”。

SIGTERM/SIGINT 向所有未结束任务发出停止请求，并等待全部任务清理。每个任务按已有 G6a-9/G6a-10 规则停止捕获、固定本地尾部、尝试冷层确认；这是并发停止，不是逐任务累加十秒。达到预算会强制中断，但本地文件系统操作仍无严格最坏返回时间；systemd 超时必须预留清理空间。

`drained` 只覆盖该任务已持久日志的固定尾部，不保证全部 Redis 成功写入被捕获，也不能作为 Gateway 安全淘汰某个 key 的证明。Gateway 与同步器之间的确认、归属和操作屏障协议仍待实现。

## 状态、日志与指标

管理接口仍是 loopback 只读 GET/HEAD，不增加管理写接口：

- `/status`：多任务通过 `tasks[]` 返回 `task_id`、固定状态/错误类别、运行标识和状态更新时间；legacy 保持原 `task` 单任务视图。多任务使用方不得读取 legacy `task` 占位值来判断全部任务。
- `/livez`：只说明服务调度循环仍在运行。`degraded` 时仍可能返回存活；这不是冷层健康、任务全成功或业务 readiness。
- `/metrics`：多任务的已有同步指标增加 `task_id` 标签，legacy 指标保留无此标签的原契约。最多 8 个合法 ID 限制本进程基数；不要在 ID 中编码密钥或业务 key。
- CLI 退出前逐任务输出脱敏的最终状态，再输出服务总结；失败和正常停止都覆盖全部任务，不只记录第一项。日志不输出后端地址、日志目录、凭据内容或原始协议错误。

现有指标名称暂保留 `redis_pilot_gateway_sync_` 前缀，与进程部署无关。缺失或不同源历史的复制位置仍不能报告为“零滞后”；字节偏移差不是时间差，状态更新时间不是实时冷层健康采样。

## 资源与部署约束

三个任务不是三个完全隔离的服务：仍共享进程内 CPU、内存、Go GC、文件描述符，以及主机磁盘和网络。每任务日志预算与全进程不超过 1 GiB 的声明检查都不是物理磁盘配额，也不能替代全进程资源控制；例如三个默认任务单就 journal 配置上限合计为 384 MiB，还要考虑快照、临时文件、剩余磁盘和内存。8 只是当前静态安全上限，不是性能容量结论。

沿用 [systemd 模板](../../../examples/redis-syncer.service)，把三个日志目录直接放在 `/var/lib/redis-syncer/` 下可复用它的持久可写目录。所有任务停止预算应适配模板总退出窗口；调整配置前先确认磁盘预算和实际退出耗时。CPU/内存/I/O 配额、跨机部署、负载分配和自动扩缩容触发条件待定。

本阶段不加入默认 `make deploy`，不通过 Agent 自动安装服务，也不启动远端实例或长测。静态 YAML 仍由操作者显式准备；未来 Server 自动分配任务的实现不能绕过这些身份与独占约束。

## 验证范围与后续工作

本轮已验证配置兼容与冲突拒绝、持久身份误配拒绝、跨任务冷元数据拒绝、任务失败隔离、并发停止、逐任务观测和脱敏。完整命令、结果和边界见 [G6a-11 验证记录](../../benchmarks/g6-syncer-multitask-20260908.log)，不沿用 G6a-10 结果冒充多任务验收。

进程级测试使用受控 RESP 后端，要求三个任务同时达到 PSYNC，收到 SIGTERM 后三个源连接都关闭，并能重新打开原来的三个空 journal。fixture 不提供 RDB、不接收业务写入：该测试仅证明进程信号/任务并发生命周期/空日志重开，不是真实 Redis/Kvrocks 数据续传、持久一致性、Cluster 或扩容验收。

本轮 CLI 全包三轮 race 已通过（`go test -race ./cmd/syncer -count=3 -timeout=120s`，最终复测 14.966s），包含 legacy 与三任务的真实子进程停止/重开、逐任务最终日志、只读配置检查和脱敏。三轮中的三任务场景合计完成六次子进程启动/停止，使用受控测试端点，不是六次真实数据库验收。

最终全项目 `go test ./...` 通过；`internal/gateway`、`internal/syncer`、`cmd/syncer` 的合并 race 与 `go vet` 通过。本机二进制构建、legacy/多任务两个示例的只读配置检查、Linux amd64 静态交叉编译均通过。复查额外补上了服务凭据检查与任务退出的并发保护，以及日志文件被替换成 FIFO 时的非阻塞拒绝。G6a-10 与 G6a-11 改动当前均未提交。

真实多后端联测、Linux systemd 实测、资源竞争与热写尾延迟、4/24 小时长测仍后置。后续 [G6a-12](syncer-control-plane.md) 已增加本地任务固定登记与状态上报，不等于 Server 自动分配或故障接管。确认的推进顺序是先做好原地恢复/观测、同步异常时 Gateway 保护，再做计划迁移/人工接管，最后评估自动接管；冷热业务语义、TTL/更多命令、回温、受控淘汰和确认协议继续独立推进。
