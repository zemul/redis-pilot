## 接入位置与行为

Service 可由内部编排在启动前安装一个固定 `keyBarrierSet`。所有会发给 Redis 的业务命令，在认证、命令白名单及 QUIT 截断处理之后、组装实际发送批次之前，取得对应 key 的在途句柄。服务运行期间不能更换集合。

- 同一 key 的普通请求仍可并行，不增加逐命令网络往返或落盘；这不是请求串行锁。实际性能影响尚未压测。
- 准备侧对同一集合调用 `reserve` 后立即拒绝新请求；已取得句柄的请求允许继续执行，准备侧必须等待并重新校验屏障，不能只等待通知便视为安全。
- 当前 passthrough 白名单都有显式 key 提取规则。MGET、MSET、DEL、UNLINK、EXISTS 等多 key 命令一次性取得全部不同 key 的准入，任一 key 被保护或预算不足，整条命令都不发送，不拆成部分执行。
- 多 key 准入共用同一把短时内存锁；失败时回滚全部本次占用，不影响其他已在途请求。重复 key 只记一次在途，原命令及重复参数不改写。
- 保留前缀 `syncMetadataPrefix` 下的 key 不允许通过受保护业务入口访问；值及 PING/ECHO 的普通载荷不被当作 key。新命令即使加进转发白名单，没有提取规则仍拒绝。
- 命令不符合安全提取规则时返回固定 ERR；屏障、状态不确定、预算不足或集合关闭时返回固定 TRYAGAIN，并明确本条命令未发送。错误与指标不携带 key/value。

这份提取表只说明怎样保护请求，**不代表同步器已经支持这些命令**。实际降冷模式仍须另设冷回放兼容策略，目前不能因为 MSET/TTL 命令可被识别就允许其进入不支持它们的同步链路。

## 结果如何影响屏障

| 事件 | 处理 |
| --- | --- |
| 后端初始化失败，或写线程启动前上下文取消 | 业务命令确定未发送，释放本批在途占用 |
| 收到一个完整 Redis 回复，包括命令错误 | 先把该条命令标记为确定完成，再向客户端写回复 |
| 写线程启动后发生短写、读失败、超时或取消 | 未读到完整回复的命令不自动重放；普通 key 仍可访问，也可申请新准备；已有转换 key 继续保护，不设置分片级暂停 |
| 客户端写回复失败 | 已取得后端回复的命令仍为确定结果；剩余未知结果按普通请求/已有转换分别处理 |
| 优雅停机排空完成 | 释放已确定请求的占用 |
| 停机排空超时 | 关闭连接并等待工作线程退出；未确认请求保留不确定状态 |

客户端断开、取消或“写返回错误”不证明 Redis 没有执行。不会自动重发 INCR/MSET 等请求，但普通 key 不会因此永久封锁。已有转换操作的未知结果不能被后来的普通成功回复自动清除。

Pipeline 保留原响应顺序及并行读写后端连接的方式。内部发送协程退出后统一清理未完成句柄；定案后的句柄重复清理无效，不会误释放下一条请求。

## 验证范围

- key 提取表覆盖现有全部转发命令、大小写、空 key、二进制 key、多 key/重复 key、非法参数、保留元数据和未知命令。
- 多 key 准入覆盖条目/字节/在途预算、超长 key、状态不确定、部分取得后回滚及与 reserve 的并发竞争。
- 实际 Service TCP 监听器 + 可控 RESP 后端：一个连接的 INCR 在途时建立屏障，另一个连接 Pipeline 中的 GET/MSET 被阻断，其他 key 的 GET 正常；原请求结束后屏障仍保持。
- Pipeline 故障测试覆盖部分回复、Redis 错误、客户端回复失败、本地错误回复时断开、发送前取消、后端初始化失败、短写和优雅/强制停机。

以上是本地确定性协议测试，不是本轮新增的真实 Redis/Kvrocks 集成或性能数据。前一阶段的真实后端验证见其独立文档。

本轮验证：`go test ./...` 通过；`go test -race ./internal/gateway ./internal/syncer ./cmd/syncer` 通过；请求准入、key 屏障、Pipeline 和停机专项 race 测试连续三轮通过；相关包 `go vet` 及 `git diff --check` 通过。需要外部后端的测试仍遵循原有显式启用/跳过规则，不能把本地包测试通过理解为重新完成真实后端验收。

## 为什么暂不开放开关

后续 [G6b-2f-2 持久启动保护](gateway-admission-restart.md) 已实现 dirty/clean 启停标记、异常重启拒绝启动及内部 Service 生命周期接线。以下关于恢复的描述是本阶段提出的问题；目前仍未接准备管理入口，也没有 dirty 自动核查/解除流程。

本轮的普通请求不确定状态仍是进程内状态。单纯在重启后新建集合会丢失保护，因此没有将此内部接线作为可启用的完整功能暴露。多个 Gateway 或直连 Redis 的写入也不会被一个本地集合拦截。

下一步按以下顺序接入：

1. 持久启动/退出保护已在 G6b-2f-2 采用启动落盘标记加异常重启整体拒绝启动；核查恢复流程仍待定，不承诺自动恢复。
2. 独立认证、有界并发的准备管理入口，启动前恢复现有意图及对应屏障；确认适配器和 Service 必须共享同一集合。
3. 校验独占执行前提、源角色/历史、禁自主淘汰及当前 String/无 TTL 约束，先持久记录意图，再内部原子校验值并写准备标记；丢回复后复用同一操作核查。
4. 接持续同步器确认并验证进程重启窗口，确认后仍保持屏障。热副本移除、冷驻留发布、解除屏障/继续冷应用另行实现。

Server 授权、跨进程 fencing、真实 Cluster 路由迁移、多操作并行、TTL/复杂类型和回温仍待后续阶段处理。
