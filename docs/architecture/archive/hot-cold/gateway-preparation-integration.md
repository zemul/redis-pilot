# G6b-2f-4：准备入口与真实持续同步链路联合验证

本文记录此前全局 dirty 拒绝策略下的验证结果。该策略已按用户确认修正为 [恢复业务、局部保护](gateway-admission-restart.md)，联合用例现已改为检查重启后普通 key 可访问、操作 key 仍受保护；旧执行记录不代表现行策略。

2026-09-08。本轮新增联合测试及验证记录，没有新增配置开关或部署正式服务。前置实现见 [热端准备入口](gateway-hot-preparation.md)。

## 本次连接了哪些真实组件

- Gateway：运行实际 Service 的 RESP 业务监听器和 HTTP 管理监听器，不直接调用准备脚本或确认客户端来代替入口。
- 同步器：独立运行编译出的 `redis-syncer` 二进制，使用 `isolated-confirmation-live` 模式。
- 热层：专用 Redis 7.2.5。
- 冷层：专用 Apache Kvrocks 2.15.0，启用同步 WAL。

Gateway Service 本身运行在测试进程内，不是已经公开配置的 `cmd/gateway` 独立部署。源日志仍通过测试夹具建立已有固定历史前缀，再独占交接给同步器；首次初始化/自动注册发现不属于本次验证。

## 验证结果

1. 初始热数据和冷应用前缀为 counter=42。通过 Gateway RESP 执行 INCR 后得到 43，再从 Gateway 管理入口发起准备。
2. 同 ID/key 的重复准备成功；后续业务 INCR 被屏障拒绝，其他 key 的 SET 仍能执行。
3. 同步器实际观察准备标记并停止在相应冷应用位置，counter 已同步为 43；后续 key 只继续捕获，不应用到冷库。
4. 确认前强杀并重启同步器，未确认屏障恢复，未跨过准备位置。
5. 转发真实确认到同步器，待 Kvrocks 提交成功后丢弃 HTTP 回复：Gateway 管理入口返回失败，本地没有伪造 receipt。显式重试成功，热层和冷层都仍为 43。
6. 确认后同步器继续捕获其他 key 的变化，但冷应用位置不移动。确认不会自动解除屏障或删除热 key。
7. 再次停止同步器：Gateway 不能凭本地 receipt 返回成功。重启后状态要求重新核验，管理入口在线确认成功。
8. 不同操作 ID 的准备被拒绝。Gateway 带未完成屏障退出时保留 dirty，重新启动在接收业务前被拒绝。

新用例先独立运行三轮，再与旧离线确认、持续确认用例组合运行三轮，全部通过。时间仅为测试执行时间，不是吞吐量或延迟基准。完整命令、二进制摘要与输出摘要见 [验证记录](../../benchmarks/g6-preparation-joint-20260908.log)。

## 环境与清理

在 redis03 新建两个专用临时容器，共用隔离网络空间，不开放宿主机端口，设置内存/PID 上限。没有重启或修改原有 Server、Agent、Proxy、Gateway 或四个既有运行容器，也没有修改路由。

每轮测试只清理夹具创建的指定 key；不对既有实例执行 FLUSHDB。测试结束后停止两个专用容器，保留容器及测试二进制供追溯，没有配置开机自启。

## 仍然没有证明什么

- 没有实现热副本移除、冷驻留发布、解除屏障、继续冷应用、回温或自动 LRU 淘汰。
- 没有解除 dirty 状态，没有实现管理专用恢复模式；完整业务重启仍要求安全条件，而不是“有 receipt 就放行”。
- 新联合用例覆盖 Gateway 的受保护退出/拒绝重启，未把 Gateway 改成独立子进程执行强杀；本地启动标记的子进程强杀测试另见上一阶段。
- 本次真实 Linux 后端运行使用普通二进制，未启用 race。相关包在本地运行 race，外部后端用例按显式环境条件跳过，不能混称真实 Kvrocks 已通过 race。
- 未覆盖设备掉电、长时压力、所有文件系统故障窗口、Cluster 扩容迁移、多 Gateway fencing 或完整 Redis 语义。

下一步先设计并实现 **dirty 下的管理专用只读观察**，保持业务不放行、不自动重试不确定操作、不修改 clean/dirty，再补明确的人工核查/恢复授权流程。
