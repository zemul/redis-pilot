本轮把准备控制器接入真实 Service 管理监听器，共用业务请求的 key 屏障集合和既有冷确认客户端。仍仅供内部显式编排/隔离测试，没有新增 YAML 开关或默认启用，不执行热删除、冷驻留发布或回温。

## 管理接口

| 接口 | 行为 |
| --- | --- |
| GET `/internal/v1/hot-preparation` | 只读观察 idle、held、持久意图待重验、准备标记已观察或持久化不确定状态 |
| POST `/internal/v1/hot-preparation` | 关闭 key 准入、排空在途请求、持久保存意图、校验并写准备标记 |
| POST `/internal/v1/hot-preparation/confirm` | 使用已有意图向固定同步器请求精确确认，验证并保存回复，继续保持屏障 |

POST 使用规范 JSON，仅包含 `operation_id` 和 `key`。操作 ID 是调用方选择的非零 16 字节小写十六进制字符串；key 使用 JSON 的 Base64 字节表示，支持空 key、非 UTF-8 key，限制 64 KiB。请求受长度限制，拒绝非规范 JSON、未知/重复字段、非法 ID 和保留元数据 key。

管理 token 独立于同步器 token、前端和后端密码，必须来自私有凭据文件，不允许空 token 或复用这些凭据。接口沿用 Service 的 loopback 管理监听地址及读写超时，不新增公网端口，不支持跨机明文调用。

每个控制器只允许一个正在处理的管理请求和一个未完成操作，不排无界队列。忙时返回 409；认证/请求错误分别返回 401/400；准备或确认无法安全完成时返回固定 503，不暴露 key、值、路径或原始后端错误。

## 准备步骤

1. 验证操作 ID/key。首次调用在共享集合中 reserve 该 key；新业务请求立即被拒绝。后续请求必须携带相同 ID 和 key，否则拒绝。
2. 等待已取得准入的请求结束，再检查集合未关闭、没有不确定结果、在途计数为零。超时或不确定结果不解除屏障。
3. 使用 Gateway 的独立后端凭据建立连接，验证 standalone master；检查复制历史与固定绑定一致、淘汰策略为 noeviction，读取 String 值且要求 PTTL=-1。值最大 64 KiB。
4. 将 ID、key、值摘要、history、epoch 等意图写入固定 `confirmation-operation.log` 并 fsync。文件创建结果不明时使控制器进入拒绝继续状态，不覆盖或新建另一个意图。
5. 内部执行原子准备脚本：再次核验类型、无 TTL 和完整值相等，随后写保留前缀下的准备标记。该脚本不修改业务值，也不删除热副本；业务客户端仍不能调用 EVAL。
6. 脚本返回成功后再次检查历史、角色及淘汰策略。检查失败、超时、取消或回复丢失均保持原操作和屏障，不返回准备成功。

检查不能代替分布式 fencing。调用方必须明确承担独占热端写入的前提，不能有绕过该 Gateway 的业务入口、其他 Gateway 或未经协调的配置修改。初始数据无 TTL、支持的类型和源历史的部署核验仍需后续完整接入流程。

同一操作重试时复用已持久化意图并重新核验值摘要。若标记已存在且类型、TTL、内容完全相同，脚本返回幂等成功，不重新写标记。值改变、标记冲突或 ID/key 改变均不能通过重试覆盖。

## 命令与资源边界

为避免入口产生现有冷回放器不支持的写，内部启用此控制器时，业务写暂限 `SET key value`、单 key `INCR` 和 `DEL`；读限单 key GET/TYPE/TTL/PTTL/EXISTS，以及 PING/ECHO。AUTH/QUIT 沿用会话处理。

SET 选项、TTL 修改、多 key 命令、DECR、APPEND、复杂类型、事务和用户 Lua 暂不进入这条实验路径。普通 passthrough 的白名单与默认行为不变。该阶段不是“尽可能完整 Redis 语义”已经完成。

控制器从 Service 共享内存预算中额外保留一份有界工作空间，并限制为串行管理操作。业务请求仍只做内存准入检查，不等待同步器确认，也不逐热写 fsync。未做性能压测，不能据此量化延迟影响。

## 确认、退出与恢复

准备控制器和确认客户端共用同一个意图文件与 key 屏障。确认复用既有固定绑定、同步器会话校验、准备证据/receipt 校验和本地持久保存。确认成功不代表允许删除，失败也不解除屏障。

Service 必须先成功取得并持久化启动保护，再构造控制器；配置的操作目录与完整绑定必须相同。停机先阻止新管理请求并取消当前操作，随后关闭 HTTP/业务入口并等待所有相关工作结束，再关闭控制器、释放其文件和预算，最后判断启动标记是否可写 clean。未完成屏障会保持 dirty 并返回需要核查的错误。

控制器重新打开已有操作时会先恢复对应 key 的屏障；已有 receipt 不恢复“本次已核验”的标签，确认仍需在线请求。这是控制器级恢复能力，**不绕过 Service 的 dirty 启动保护**。目前异常重启或存在未完成操作的退出之后，完整 Service 仍拒绝重新放行业务；尚没有管理专用恢复模式、核查审批或解除 dirty 的接口。

## 验证

本地可控 RESP/HTTP 测试覆盖：意图先于脚本写入、脚本回复丢失与同操作重试、值改变、TTL/历史/淘汰策略不符、操作冲突、在途超时与不确定结果、独立认证、忙时拒绝、意图创建失败保留保护、确认和控制器恢复、关闭时取消等待、工作空间释放，以及真实 Service TCP/管理监听器的准备和停机。

真实后端验证使用本地临时 Redis 7.2.5，未触碰开发机既有实例。通过 Gateway SET 41、INCR 到 42，管理入口准备与重复准备成功，直接检查热值仍为 42、标记内容匹配；后续业务 INCR 被拒绝，同步器端点不可用时保持屏障。另回归原有真实 Redis 准备→PSYNC 捕获→持久恢复用例，脚本已改为复用本轮内部实现。

两项真实 Redis 用例在 race 模式下连续三轮通过，合计 2.841 秒。这不是性能数据，也不是新增真实 Kvrocks 联合验收。普通全量测试已通过，外部后端用例仍按显式启用规则执行。
