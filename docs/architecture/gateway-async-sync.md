# G6：低热写延迟的异步同步路线

## 已确认的方向

业务优先考虑热写延迟。正式目标保持 Cluster 的 Redis 热层 + Kvrocks 冷层，不改成纯 Kvrocks；不修改两种引擎源码仍是优先约束。

- 业务写入先在 Redis 执行，成功响应不等待冷层确认。
- 冷层尚未应用最新修改时，不能视为最新数据来源，也不能据此淘汰对应热数据。
- 不额外把同步日志的同步刷盘加到每次业务写入确认路径；这不是零丢失承诺。
- 业务响应丢失仍可能产生不确定结果，不能自动重试 INCR 等非幂等业务命令。

选择低延迟不等于用户已经接受某个数值 RPO。热层 AOF always / everysec、热副本确认策略、允许损失窗口和恢复时间仍需实测与确认。不能因为用了 AOF，就声称机器丢失或主从切换也不会丢失已成功写入。

已完成 G6a-1 复制接收与恢复原型，并推进到 G6a-4 隔离的无 TTL String 应用实验，交付边界见下文。已有真实捕获数据写入专用测试 Kvrocks 的验证；没有接入运行服务或修改现有开发实例持久化配置。

## 最先实现：G6a 单向同步验证，禁止降冷

用一个逻辑分片、一套独占测试 Redis 和一套独占测试 Kvrocks，验证从完整数据源到空冷层的单向同步。它是 Cluster 的分片级实验，不是单点冷热产品。
暂不回温、不淘汰、不处理迁移或自动切主，不把测试数据并入任何已有 Kvrocks 实例。

优先验证 PSYNC + 初始 RDB + 增量复制流，而不是在网关转发成功后才把原始请求塞进 Go 队列。后者在 Redis 已执行、网关尚未记日志时宕机会形成数据缺口，也不能从请求本身得知命令的实际执行结果。
复制接收器及可恢复日志可以先与 Gateway 同进程、资源隔离；不在 Server SQLite 中保存业务数据，不通过 Agent 转发。

首批客户端命令范围：GET、SET（先无条件写入及明确支持的过期参数）、DEL、INCR、EXPIRE/PEXPIRE、TTL/PTTL。只处理 String；实际复制流可能含 SELECT、事务边界、绝对过期时间或改写后的命令，不能只按客户端白名单解析，也不能默默忽略未知修改。
先固定一个 Redis 7.x 测试版本和 Kvrocks 2.15.0，具体版本与传播行为记录进测试结果后再固化兼容范围。

### 四个必须分开的进度

1. 接收位置：读取到了哪些完整复制记录。
2. 本地可靠日志位置：哪些记录已按协议刷盘保存。
3. 冷层应用位置：哪些数据变更已执行。
4. 冷层可靠确认位置：哪些数据和进度一起达到约定的持久化要求。

位置必须带复制历史标识，不能只存一个数字 offset。Redis 的复制 ACK、Kvrocks 的成功响应和端到端可靠确认不是同一概念。
初期保留单源顺序，不做 slot 间并发应用；断点只能前进到连续完成的边界。

### 先验证的危险窗口

- Redis 返回成功后，网关/同步器立即退出：能够从仍保留的源历史续传，而不是依赖已丢失的进程内队列。
- 冷层修改成功，但确认响应丢失：重放不得重复增加 INCR 结果。
- 数据修改后、记录进度前退出：不能出现“重复执行”；进度先提交、数据未提交也不能跳过修改。
- Redis backlog 不足或复制历史变化：必须识别不可续传，不能默认安全。
- 过期时间在传输和恢复期间流逝：使用正确的到期语义，不能把 TTL 从恢复时刻重新计时。
- 未知命令、截断日志、磁盘满、冷层长时间不可用：明确停在可诊断的边界，不跳过数据继续运行。

目标侧“修改 + 去重进度”的崩溃安全提交方式是 G6a 的首要技术实验。不能未经 Kvrocks 2.15.0 源码/故障测试验证，就把 MULTI 或 Lua 称为跨崩溃原子提交。若此路线不能满足要求，评估带版本状态覆盖或收缩命令范围，不先开启淘汰。

## 冷层故障与资源限制

目标是允许有限热写，而不是立即拖慢所有热请求：在 Redis 数据可信、日志历史可恢复、内存与积压低于阈值时继续；达到阈值则拒绝新写入，保留已接受数据。
允许积压的时间/字节、热层剩余内存阈值、状态过期后的保守行为和错误码尚待确定。只有这些保护已经可执行并验证后，才可以启用该降级策略。
标准 Redis backlog 不保证无限保留未消费日志；同步器观测 offset 或上报 ACK 本身也不自动构成无缺口的写入准入屏障。

Redis 在该验证阶段设置 noeviction，不允许原生 LRU 自行删除业务 key。该限制并不解决后续外部淘汰的分类问题，只是避免在单向同步验证中引入错误删除。

## G6b 之后才开启冷热流动

先证明去重、续传及资源保护，再处理受控淘汰与回温。两个阻塞条件不能省略：

- 必须可靠区分业务删除/到期删除与内部淘汰/回温/迁移，不能仅凭“网关知道自己发了 DEL”来推断异步复制流中某个删除的性质。
- 热层已只有部分数据时，源历史缺失不能用热层 RDB 清空覆盖冷层；简单合并也可能复活已删除数据。

回温版本校验、并发写入屏障、多网关 fencing、切主、slot 迁移在后续阶段验证。第一阶段的“单网关 + 单分片”约束不代表已经解决这些问题。

## G6a-1 交付：捕获与本地恢复原型

代码位于 `internal/gateway/sync_source.go`、`sync_journal.go`，仅由隔离测试显式调用；没有新增生产运行模式，尚未接入 Gateway 启动流程、Server 或 Agent。

已实现：

- 可选 AUTH、REPLCONF、PSYNC；首次保存长度前缀 RDB 原始字节，持续捕获完整 RESP 命令原文。
- 断线后从本地日志恢复复制历史 ID 和最后捕获字节位置，使用 `offset + 1` 请求续传。
- 每个记录有长度和 CRC32C，写入及 fsync 成功才前移内存中的可靠捕获位置；重开扫描记录并再次 fsync。文件 0600，独占文件锁；同一日志不能由两个进程同时打开。
- 容量上限、快照与命令长度上限；日志达到容量时返回错误，不覆盖旧内容。
- 已有历史收到 FULLRESYNC，或 CONTINUE 切换到另一历史时拒绝继续，不自动替换或拼接历史。
- 周期复制 ACK 和 GETACK 应答仅代表本地捕获位置；**不是 Kvrocks 应用位置或可淘汰证明**。

当前限制：

- 仅允许字面回环源地址，单次连接尝试；重试调度和 Gateway 进程启动恢复尚未接线。
- RDB 只作为有界原始快照保存，尚未解析数据结构或验证其内部校验和；不支持 EOF 标记式快照。本地 CRC32C 保护的是保存后的记录完整性，不能替代 RDB 格式校验。
- 快照最多 8MiB、增量单命令最多 1MiB / 4096 参数；JSON 记录含 base64，存在空间放大。逐记录 fsync 是正确性验证基线，不是吞吐优化版；无分段、GC 或压缩。
- 截断尾部或校验错误会显式拒绝打开，不自动裁剪、跳过或宣称已经恢复；需要后续可审计修复协议。
- 本地日志没有副本，不能覆盖主机/磁盘永久丢失。进程强杀测试不等于掉电或磁盘故障验收。
- 不解析或应用增量命令语义，不解决目标去重、事务边界、TTL、降冷/回温分类和 Cluster 切主/迁移。
- 复制接收器会被 Redis 视为副本，可能影响 WAIT 或副本数量策略；本原型不可接入业务 Redis，也不能把这类确认当作可接管的数据副本。
- 容量耗尽仅中止捕获，**尚未实现热写准入/积压水位保护**，因此不能用于生产异步同步。

### 验证结果

本地 Redis **7.2.5** 隔离实例（非开发机已有实例）：首次快照含预置数据，随后捕获 SET、INCR、PEXPIRE、DEL 的实际传播帧；日志关闭/重开后续传停机期间的 SET，只有一份初始快照，该 SET 只捕获一次；人为耗尽小 backlog 后返回历史缺口，旧日志位置未改变。
这是复制字节流捕获验证，**不代表这些命令已经正确应用到 Kvrocks，也不代表 INCR 目标去重和 TTL 恢复验收通过**。

另验证独占锁、容量满不推进位置、重复偏移拒绝、校验损坏/截断拒绝、快照长度限制、复制历史变化拒绝；子进程完成日志 fsync 后被 SIGKILL，重新打开后完整记录与偏移可恢复。
普通及真实 Redis 捕获用例均经过 5 轮 race 检测；未执行性能压测。

```sh
go test -race ./internal/gateway -run '^TestSync' -count=5 -timeout 60s
GATEWAY_TEST_REDIS_SERVER=/opt/homebrew/bin/redis-server go test -race ./internal/gateway -run '^TestSyncCaptureRedis$' -count=5 -timeout 45s
```

G6a-2 已完成 Kvrocks 2.15.0 提交实验，见 [冷层提交验证](gateway-kvrocks-commit.md)。正常提交、回复丢失读回和进程强杀恢复通过；执行期错误反例说明不能无条件包装任意命令，不表示正常事务路径不可用。

G6a-3 已增加 [回放边界验证](gateway-replay-validation.md)：无 TTL 计数器在 EXEC 未发送/回复丢失两种情况下，重新建立连接、读取进度并重试通过；仍只是测试探针，序号未接 PSYNC 字节位置。同时验证真实 Redis 7.2.5 传播的 INCR 不携带最终值，Kvrocks 延迟执行“到期时间已过的 SET + INCR + PERSIST/续期”会无报错地得到错误值。**绝对过期时间防止重新计时，但单独使用它并不能保证历史增量回放正确。**

保留原生数据格式与同事务进度方向；先固定无 TTL 的受限应用协议，再接 RDB 导入和增量应用。TTL 支持仍是目标，需先明确逻辑过期/物理回收与历史重放的协议，不能以“目标暂时未命中”直接把 INCR 从 0 开始。当前不启用淘汰、回温，也不改引擎。

## G6a-4 交付：有界无 TTL String 应用

详见 [应用原型与实测](gateway-string-apply.md)。`sync_rdb.go` 解析受限 RDB v11 String 快照并验证 CRC64；`sync_apply.go` 从持久化日志生成真实 Source/History/Offset 与链式摘要，将初始快照和后续 SET/INCR/单 key DEL 写入专用 Kvrocks。SELECT 0、PING、REPLCONF GETACK 仅推进连续位置；其他命令、TTL、源事务等显式拒绝。

恢复不只读取 checkpoint：原型从小日志重建该位置的完整预期状态，并与冷层 SCAN/GET/PTTL 结果核对。这样能拒绝数据与进度不一致的恢复；但它依赖全量小状态核对，**不是可直接用于大容量冷层的恢复算法**。

真实 Redis 7.2.5 的两段捕获日志经离线文件传输送入隔离 Kvrocks 2.15.0，初始 RDB、增量写入、捕获断线续传、INCR 提交前断开/回复丢失后的重新调用、重复前缀与状态异常拒绝经过验证。尚无服务生命周期接线、自动重试、海量 RDB 导入、TTL、淘汰、回温、fencing 或 Cluster 路由；捕获 ACK 仍不等于冷层可靠确认。

## G6a-5 交付：单项 pending 恢复

详见 [待确认项恢复](gateway-pending-recovery.md)。新增独立实验入口 `applyPending`：在 Kvrocks 中先保存原始记录和 before/after，再条件提交业务命令及真实 checkpoint；初始化、准备和提交均防止旧请求晚到覆盖新状态。恢复只核对最近一项，不再重建/扫描整个冷层；仍依赖目标独占，不提供全库偏差审计。

真实同步子进程强杀、三阶段及控制/删除的断线/丢回复/迟到 EXEC、元数据异常拒绝均有测试。日志采用固定长度的流式视图，仍需要两遍扫描，没有完成分段索引、GC、大 RDB、TTL、服务接线或生产 fencing。热写确认路径没有新增冷层等待。
