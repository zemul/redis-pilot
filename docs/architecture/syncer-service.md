# G6a-10：独立同步服务受控入口

后续 [G6b-2d 隔离确认模式](gateway-confirmation-rpc.md) 在同一二进制新增独立 `-confirmation-config` 入口，与本文普通 `-config` 互斥；它只使用停止捕获后的已有日志，不改变本文持续同步模式的行为，未接业务淘汰。

本文保留 G6a-10 的单任务入口与部署契约。后续静态多任务、独立元数据和持久身份绑定见 [G6a-11 多任务管理](syncer-multitask.md)；下文“尚未实现多任务”均指 G6a-10 阶段，不是最新能力清单。

G6a-12 已增加可选的 [固定登记与状态上报](syncer-control-plane.md)，只观测本地 named tasks；下文“Server 注册尚未实现”是本阶段历史边界，自动任务下发与接管目前仍未实现。

## 定位与交付范围

`redis-syncer` 与 `redis-gateway` 使用同一个仓库，但有独立二进制、配置、进程和 systemd 服务。同步器承担数据面复制：订阅源 Redis、持久化本地日志、应用到 Kvrocks、维护断点和确认进度。Gateway 继续负责请求处理；未来回温、受控淘汰和冷热路由仍归 Gateway，不交给同步器或 Agent。

本阶段只把已验证的 G6a-1～G6a-9 隔离同步内核接成可显式启动的单任务服务。不新增复制协议；通过窄适配层复用暂存于 `internal/gateway` 的内核，由 `internal/syncer` 负责配置、进程生命周期和 HTTP 观测。暂不大规模搬迁协议代码，避免入口拆分与存储协议修改混在一起。

这不是正式冷热能力上线：当前 Gateway 仍是单后端测试透传，不读冷层、不淘汰热数据，也不通过此服务自动获得安全回温或迁移能力。

| 已接入的入口能力 | 当前没有的能力 |
| --- | --- |
| 显式 YAML 配置、凭据文件检查 | Server 注册、配置下发、任务调度 |
| 单源、单冷目标、单任务运行 | 一个进程管理多个分片 |
| 持久日志、续传和已有受控恢复内核 | 分布式归属、租约、fencing、故障自动接管 |
| SIGTERM/SIGINT 优雅停止 | Cluster 拓扑发现、重分片和迁移协调 |
| `/livez`、`/status`、`/metrics` | 空闲冷层主动健康探测、业务就绪证明 |
| 二进制构建、systemd 模板 | 远端部署、生产资源阈值或性能验收 |

## 进程与任务边界

最终设计按每个启用冷热的 Redis 主分片设置一个活跃同步任务。3 主 3 从应是 3 个任务，不是 6 个，也不是每个 slot 一个进程。一个同步服务进程未来可承载多个任务，但 G6a-10 的配置和实例仍只有一个源、一个目标。

后续 Server 负责根据拓扑分配任务；同步服务负责执行和上报。增加 Redis 主分片时应自动增减任务，增加 Gateway 不应复制同步任务。只有同步服务容量不足时才增加服务进程。多任务、自动分配和接管尚未实现，不能启动多个原型进程来替代这些协议。

独立进程允许分别升级、重启和控制资源；同机器部署依然竞争 CPU、内存、磁盘与网络，不等于资源完全隔离。热写延迟优先的目标，需要后续按进程验证 CPU/RSS、日志 fsync、冷层积压和尾延迟，再确定资源预算或跨机部署。

同步器和 Gateway 未来必须通过有明确源历史、分片归属和操作屏障的确认协议协调淘汰。`captured`、`applied`、`confirmed` 或 `drained` 不能单独当作“这个 key 可以安全淘汰”的凭据，当前没有这样的跨进程接口。

## 强制隔离约束

- 必须显式提供配置文件，`mode` 只能为 `isolated`，并设置 `confirm_exclusive_cold: true`。
- 源、冷层和管理监听仅允许 literal loopback 地址；不做 DNS、跨机、Cluster 或主从切换。
- 初次 bootstrap 必须使用专用、空的冷 DB；恢复必须保留原来的冷 DB 元数据和本地日志，不能为了重启把任意一侧清空。
- 冷层仍限现有原型验证过的 Kvrocks 2.15.0 可写 standalone 与同步 WAL 配置。命令、版本、角色及数据限制以同步内核检查为准。
- 当前固定使用 `{isolated}` 的 checkpoint、pending、anchor 元数据，冷 DB 必须独占；不能把多个任务指向同一个冷 DB，即使它们有不同日志目录。
- 本地运行锁和日志锁只能阻止对应的本地并发打开，不是跨机器所有权或后端 fencing。
- 数据面仍限小规模无 TTL String：初始 RDB v11 最多 256 个 key、512 KiB，受限 key/value，增量仅已有的普通 SET、INCR、单 key DEL 和复制控制帧。TTL、Lua、事务、其他类型及完整 Redis 语义没有因此扩展。
- 不修改 Redis 淘汰策略，不拦截热写，也不保证同步器停机期间所有 Redis 成功写入最终都可找回。复制 backlog 不足、历史缺口和不确定提交仍是必须处理的错误边界。

## 配置与启动

完整示例见 [syncer-isolated.yaml](../examples/syncer-isolated.yaml)。示例的 `26379`、`26666` 是待自行准备的专用隔离后端，不是已部署的端口，也不复用现有 Gateway 的 `16389` 测试后端。

| 字段 | 示例与语义 |
| --- | --- |
| `mode` | `isolated`，唯一支持模式 |
| `confirm_exclusive_cold` | 必须显式 `true`，确认冷 DB 由此任务独占 |
| `source_address` / `cold_address` | 不同的 loopback IP:port，不支持自动切主 |
| `source_password_file` / `cold_password_file` | 可选绝对路径；服务账户拥有、0600、单链接的常规文件，不接受符号链接、FIFO 或目录 |
| `allow_unauthenticated` | 示例仅为回环隔离测试显式设为 `true`；不是生产免密建议 |
| `journal_dir` | 绝对路径，例如 `/var/lib/redis-syncer/journal`，必须使用持久存储 |
| `segment_bytes` / `journal_bytes` | 示例 4 MiB / 128 MiB；单段 1～16 MiB，总预算至少两段、不超过 1 GiB |
| `io_timeout` | 示例 30s；单次 I/O 限制，不等于端到端同步延迟上限 |
| `shutdown_timeout` | 示例 10s；触发强制中断的优雅停止预算 |
| `admin_listen` | 示例 `127.0.0.1:19300`，不对业务暴露 |

配置拒绝未知字段、无效模式/地址/路径、冲突端点和不合理预算。配置文件只接受这些受控字段，不能直接注入完整内核参数绕过隔离限制。

配置文件必须为常规文件；不接受最终路径为符号链接、FIFO、设备或目录，避免启动检查阻塞在特殊文件上。

凭据父目录必须可信。启动、捕获连接、冷层连接和恢复校验每次实际读取凭据时，均使用非阻塞、不跟随最终符号链接的打开方式，并校验属主、权限、常规文件类型和单链接；不是只在启动时检查一次。替换为 FIFO、公开可读文件或符号链接会报错停止，不能阻塞退出或绕过检查。合规的原子文件替换将在后续重新读取时生效，配置检查不持有凭据的永久快照，也不提供已建立连接的热更新协议。

日志父目录必须事先存在，服务仅创建最终日志目录（0700）并加本地独占锁，不递归准备任意路径。

```sh
make syncer
bin/redis-syncer -config docs/examples/syncer-isolated.yaml -check-config
```

`-check-config` 只解析/校验配置和读取凭据文件：不创建日志目录、不打开日志、不监听端口，也不连接 Redis/Kvrocks。因此检查成功不表示后端存在、冷 DB 为空或可安全同步。无配置、无效参数或校验失败以非零退出码结束；日志不回显原始配置、口令、命令参数或后端响应。

明确准备好专用测试后端和可写的持久日志路径之后，才可以去掉 `-check-config` 运行。程序不会创建 Redis/Kvrocks 容器，不会自动选机器，不会修改现有 Proxy 路由。

`make syncer-linux` 只构建 Linux amd64 的 `bin/redis-syncer`。两个目标均是 opt-in，不加入 `all`、`build-linux` 或 `deploy`，不附带服务重启。

## 优雅退出与错误恢复

SIGTERM/SIGINT 由独立服务转换成 G6a-9 优雅停止请求，不把信号 context 直接传给复制内核强制取消。先停止捕获并等待最后完整帧落盘，再固定本地日志尾部，继续冷层应用/确认和安全清理。管理 HTTP 在服务退出时有界关闭。

启动过程中尚未发布运行控制句柄时，停止判断与取消使用同一把发布锁：之后不能再用有效 context 开始冷层操作或捕获。此时可返回 `stopped`，不是 `drained`。若已经发布，则走正常的有界排空；同时发生的安全错误仍保留。每个任务对象只接受一次 Run，进程重启重新构建对象并重新打开、校验旧日志，不复用上一轮控制句柄。

`drained` 只说明已落入本地日志的固定尾部处理完成，不说明源 Redis 停止写入，也不证明所有成功热写都已捕获。达到停止预算后强制中断；等待协程和本地文件操作结束可能超过触发时限。详见 [G6a-9 生命周期契约](gateway-sync-lifecycle.md)。

连续运行中的源/冷层连接错误沿用既有受控重试规则；日志损坏、历史缺口、状态不匹配和 uncertain 等终态不在服务外层无限重启。进程返回非零退出码，保留现场，由操作者判断恢复；不要自动删 journal、pending 或 checkpoint，不要在不确定状态下直接换一个空目录重跑。

正常停止后使用同一配置和持久化目录重新启动，仍由既有内核检查日志、冷层状态并尝试续传。是否可恢复取决于历史完整性和确认协议，不是“有 systemd 就不会丢数据”。

## 管理观测

仅提供 GET/HEAD 的只读入口，不开放控制、重置、清理或参数更新操作：

- `/livez`：服务进程的存活观测，不代表 Redis/Kvrocks 可用或同步追平。
- `/status`：只读、脱敏的服务/任务状态与错误类别快照，不读取业务 key，不触发同步/对账。`running` 是生命周期状态，不是冷层实时健康证明；复制位置和资源观测通过 `/metrics` 读取。
- `/metrics`：使用私有 Prometheus registry，复用 G6a-9 内存快照 collector。为避免同时更改指标契约，暂保留 `redis_pilot_gateway_sync_` 前缀；名称中的 gateway 不表示运行在 Gateway 进程。

不提供 `/readyz`，避免把“空闲时没有发现错误”说成“冷层健康、可承载业务”。缺失位置或不可比较的源历史不是零滞后；字节偏移差不是时间延迟，数值指标不替代持久恢复元数据。状态更新时间不是独立健康检查时间。空闲冷层断连检测、告警阈值、长期冷故障策略和热层限写仍待定。

## systemd 部署边界

模板见 [redis-syncer.service](../examples/redis-syncer.service)，延续其他基础进程的原生二进制 + systemd 方式，不用容器包装同步器，也不让 Agent 安装或启停它。

运维显式选定隔离测试机器后，负责准备专用 `redis-syncer` 用户/组、安装文件与权限：

| 路径 | 用途 |
| --- | --- |
| `/opt/redis-syncer/redis-syncer` | 二进制，服务用户不可修改 |
| `/etc/redis-syncer/syncer.yaml` | 专用配置，服务用户只读 |
| `/etc/redis-syncer/*-password` | 可选凭据文件，不放入命令行或仓库 |
| `/var/lib/redis-syncer/journal` | 持久日志目录，服务用户独占写入 |
| `/etc/systemd/system/redis-syncer.service` | 独立服务单元 |

`StateDirectory=redis-syncer` 与 `StateDirectoryMode=0700` 为 `/var/lib/redis-syncer` 提供受限持久写目录，在 `ProtectSystem=strict` 下仍可写。`PrivateTmp=true` 不影响这个目录；禁止把恢复所需日志存到临时目录。`ExecStartPre` 的配置检查是只读，但 systemd 自身可能在执行它之前准备 StateDirectory，二者职责不同。

模板的 `TimeoutStopSec=30s` 大于示例 10s 排空预算，并给 HTTP 关闭和清理留出空间。部署时需验证磁盘性能和真实退出时间；内核不可取消文件操作不具备严格的最坏耗时承诺。

`WantedBy=multi-user.target` 允许通过启用服务实现开机启动；模板刻意设置 `Restart=no`，避免不确定提交等终态反复自动启动。这不影响已启用服务的下次开机启动，也不等于具备终态自动修复能力。对重启后发现的旧状态，内核仍必须校验并可能拒绝运行。

本阶段不提供自动选机部署脚本，不加入普通 `make deploy`，不对 redis01–03 做远端部署或重启。正式部署位置、CPU/内存/I/O 配额和故障告警接入待后续验收确定。

## 验证与下一步

本轮已通过全项目 `go test ./...`、Gateway 与同步服务全包 race、适配层五轮定向 race、CLI 三轮 race、相关包 vet，以及 Linux amd64 编译。实际本机二进制的示例 `-check-config` 也通过，未连接示例后端。详细结果见 [G6a-10 验证记录](benchmarks/g6-syncer-service-20260908.log)。

测试覆盖只读配置检查、凭据/配置/参数脱敏、凭据在运行前检查后被替换的实际重读路径、启动与取消原子边界、排空/超时/不确定提交错误保留、日志锁和句柄释放、管理接口只读、HTTP 故障与有界关闭、并发状态/指标采集。进程测试用真实子进程接收 SIGTERM，验证正常退出、源连接关闭及同一空日志目录重开；三轮 race 共完成六次启动/停止。

进程测试后端是受控 RESP 测试端点，没有提供 RDB，也不接受业务写入，因此不代表真实 Redis/Kvrocks 数据一致性或数据续传验收。真实后端的启动/停止/重启续传、异常保留证据、Linux systemd 实际运行仍需显式隔离验证；4/24 小时长测按用户安排后置。本阶段没有远端部署、重启既有服务或启动长测，G6a-10 改动尚未提交。

之后依次考虑：单进程多任务和元数据隔离、Server 任务登记/分配、可靠归属与故障接管，再做扩容/重分片协调。TTL、更多命令、RDB 规模、冷热回温/淘汰和完整 Redis 语义仍按各自协议验证推进，不能因为新增服务入口而跳过。
