# Gateway 异常保护与单 key 操作屏障

> G6b-1，2026-09-08。已实现独立的进程内屏障基础和单元测试；**未接 Gateway 请求链路，不执行淘汰，不代表冷热协议已完成**。
> 前置：[同步器进度观测](syncer-progress.md)、[异步同步路线](gateway-async-sync.md)、[冷层 pending 恢复](gateway-pending-recovery.md)。

后续进展：[G6b-2a 复制标记实验](gateway-eviction-envelope.md) 已验证临时 Redis 的真实记录组和部分失败；不是冷层确认或持久意图恢复，未改变本页屏障未接业务的边界。

## 1. 本轮实现范围

代码：[key_barrier.go](../../internal/gateway/key_barrier.go)，测试：[key_barrier_test.go](../../internal/gateway/key_barrier_test.go)。

一个 `keyBarrierSet` 对应一个测试分片、一个进程内执行者。组件没有网络、磁盘、后台协程、定时器或新配置项。没有接入 `Service`、Proxy、Server 或同步器，也没有修改原有命令准入、复制日志和冷层回放规则。

已实现：

- 普通热路径请求的准入与在途计数；普通请求之间仍可以并发，不是逐 key 串行执行器。
- 申请屏障时立即阻止该 key 的新请求，再等待已有请求结束。其他 key 仍可进入，除非共享预算已满或整个集合关闭。
- 唤醒通知与最终资格检查分离。被唤醒不代表能执行操作，取消、关闭和结果不确定也会唤醒等待者。
- 尚未进入派发阶段的屏障可以取消；取消不会丢掉尚未结束的请求计数。
- 进入派发阶段后，不再允许通过取消恢复准入。当前故意不提供“淘汰成功后放行”接口，因为持久化协议和冷路径尚未实现。
- 请求结果不确定时保留隔离状态；其他请求成功、重复回调、屏障取消都不能清除它。
- 旧请求的重复完成、旧屏障的取消/派发不能修改同 key 的新操作。
- 集合关闭是终态；晚到的完成只能清理计数，不能重新允许请求。
- 活跃 key 数、保存的 key 字节数、在途请求数分别有上限。单 key 最长 64 KiB，支持空 key 和二进制 key；保存独立副本，避免短字符串引用整个大请求缓冲区。无屏障且结果已确定的空闲记录会释放，不为全量热数据保留一份目录。

未实现：冷热位置目录、冷回退、回温、真正删除、持久操作日志、精确冷层确认、异常阈值执行、LRU 选择、分布式所有权、故障接管和 Cluster 迁移。部署方式不变，不增加服务，不由 Agent 管理。

## 2. 为什么不能马上删 Redis 中的 key

当前同步器的 `syncPendingCommand` 将普通 `DEL` 当作业务删除；`UNLINK`、事务和其他未支持命令会拒绝回放，而不是被识别为内部降冷。

因此下面两种方案都不能接入：

1. 看见采样进度相等就删除：采样不是该次操作的确认，检查之后也可能发生新写入。
2. 加本地锁后发送 `DEL`：即便挡住并发写，同步器仍会把这个删除应用到冷层。

此外，删除热副本后继续沿用普通透传路径也不安全：`GET` 会把冷 key 当作不存在，`INCR` 可能从零开始。必须先有冷热位置及恢复协议，不能先上线淘汰再补回温。

## 3. 屏障的调用约束

`enter(key)` 只负责“允许一个已被上层判定可以走热路径的请求进入”。表中不存在该 key 仅表示没有活跃记录，**不表示 Redis 存在该 key，也不证明冷层不存在它**。

调用顺序：

1. 普通请求在向后端派发之前取得请求句柄。
2. 后端结果确定，或能够证明完全没有派发时，调用 `settle(true)`。这不代表应用命令一定成功；确定的命令错误也可以结束在途状态。
3. 无法确定命令是否执行或仍可能晚到时，调用 `settle(false)`，该 key 保持隔离。不能把客户端断连、超时或本地取消等同于后端没有执行。
4. 控制操作调用 `reserve(key)`，立即关住该 key 的后续准入。可等待句柄的 `wake` 通知，并同时监听自己的取消信号。
5. 等待结束后通过 `beginDispatch()` 再检查：必须还是当前句柄、所有在途请求已结束、没有不确定结果、集合没有关闭。
6. 未进入派发阶段可以 `cancel()`。进入派发阶段后本轮组件只保持阻断，没有提交成功、回温或恢复接口。

`beginDispatch()` **不是允许向 Redis 发删除命令的凭证**。它只记录本地生命周期边界；真实执行器还需验证下一节全部持久协议条件。目前没有任何执行器调用它。

该基础只覆盖单 key；未来多 key 请求、事务、脚本必须识别完整依赖并原子取得相应准入，不能循环取得一半 key 后执行。Pipeline 的准入应跟随各命令的后端在途生命周期，不能客户端一断连就全部释放。对这些链路的接线和测试均待做。

## 4. 真正淘汰的协议要求（尚未实现）

第一版验证应限定单分片、单执行者、无 TTL String、小数据量隔离环境；先手动指定一个候选 key，不做自动 LRU。

| 阶段 | 必须满足的条件 | 失败时的动作 |
|---|---|---|
| 准备 | 有效分片归属；相关请求全部经过同一个执行者；确认 key 的热驻留身份 | 无法证明就不开始 |
| 关门、排空 | 阻止新请求，在途请求全部获得确定结果 | 有不确定请求则隔离，不删数据 |
| 持久化操作意图 | 记录操作 ID、分片/归属版本、源历史、key、预期状态及阶段，崩溃后可找到 | 意图持久化未确定时不能派发删除 |
| 精确冷层确认 | 验证与本次操作绑定的日志记录和源历史；冷层数据与其确认记录按已验证的提交协议一致推进 | 不用心跳、采样对齐或仅一个 offset 代替确认 |
| 降冷派发 | 同步流能无歧义地区分内部热副本移除与业务删除，并能恢复部分失败 | 结果不明则保留意图/屏障，禁止盲目重试 |
| 发布冷驻留 | 冷路径已可读取完整值；驻留状态、删除结果与操作意图可恢复 | 不能把 key 放回普通热透传路径 |
| 后续回温 | 与新写互斥，按同样的持久操作协议防止旧值覆盖；回温事件不能被误回放为新业务写 | 回温结果不明不放行业务写 |

必须先确定的协议细节：

- **同步流标记如何编码和验证：待定。** 需要持久操作 ID、严格保留命名空间、业务侧禁止伪造、关联到精确记录及完成边界。不能简单跳过某个 key 的所有 `DEL`，也不能仅凭 Gateway 内存里记得自己删过。
- **标记与热副本移除如何构成可恢复操作：待定。** 若采用后端事务/脚本辅助，必须先在支持的 Redis 版本上观察实际复制形式、断连和重启行为，再扩展回放器；当前应用器不支持这些控制操作。不能先假定命令成组发送就等于原子且持久。
- **操作意图和驻留状态存在哪里：待定。** 不把高频全量 key 状态放进 Server 的 SQLite；是否复用同步器日志、引入专用操作日志或冷层元数据，需要根据故障恢复顺序选择。当前没有新增 Gateway 数据库。
- **确认返回通道及权限：待定。** 建议确认绑定 task/shard、ownership epoch、source history、operation ID、精确记录位置及链式摘要；字段匹配本身仍不能取代服务端对真实提交的验证。G6a-13 的观测接口不可直接充当这个通道。
- **断线重连、源主切换与 FULLRESYNC：待定。** 一旦 Redis 只有热子集，全量热快照不再等于完整逻辑数据集；重建不能据此清空冷数据或遗失冷驻留信息。
- **TTL、复杂结构和多 key 语义：待定。** 当前屏障没有解决到期和业务删除的区分，也不扩大同步器的支持命令范围。

## 5. 异常保护策略（设计，尚未接线）

保护粒度优先按任务/分片，不因一个分片异常停掉所有分片。普通热写仍保持异步同步路径，不逐次请求 Server 或等待冷层；涉及冷热位置变化时才需要精确确认。实际额外延迟尚未测量。

| 条件 | 建议动作 |
|---|---|
| 同步积压、冷层不可用、观测过期 | 禁止新淘汰；无确认依据的冷读/回温返回明确错误，不返回假不存在 |
| 热副本确定存在、源主和执行权限有效 | 可按降级策略继续热路径；这不是所有 Redis 命令都可无条件放行 |
| 内存/日志预算逼近安全上限 | 暂停回温等增大资源占用的后台操作；独立执行限写/拒写策略，不能为腾空间丢弃未同步数据；具体高低水位、时限与允许命令待定 |
| 单 key 请求/控制操作结果不确定 | 隔离该 key，等待持久证据恢复；不能靠超时自动解锁 |
| 分片归属失效、源历史变化或待恢复状态未知 | 停止相应分片危险操作；若无法证明热访问也安全则拒绝该分片请求 |
| 心跳重新正常 | 只恢复观测，不自动清掉操作屏障；需要重新验证归属、历史、资源与未完成操作 |

热写先返回、冷层异步确认仍有数据丢失窗口。该屏障不会把它变成零丢失复制；Redis 持久化、副本配置、可接受 RPO 和冷层故障下持续写多久仍待确定。

多个 Proxy 指向同一个实际执行者可以共用它的屏障；多个 Gateway 各持一把本地锁不能互相排斥。禁止绕过 Gateway 的写入、后端 fencing、租约失效时旧执行者/旧连接的隔离仍需设计。Server 的任务登记和 syncer 本地目录锁都不是这种授权机制。

## 6. 有界性、恢复与验证边界

当前预算分别限制 map 条目数、保留 key 的负载字节数和活跃请求句柄数；这不是整个进程的 RSS 上限。map/对象/通知 channel 的开销随条目数增长，释放后的句柄需由调用者及时丢弃；尚未测量每条目实际内存。

预算满时拒绝申请，不淘汰未知结果记录来腾空间。不创建无限等待队列，也不启动每 key 协程。全分片共用一把短临界区 mutex；真实请求接线后的竞争与性能待测，当前没有热写开销结论。

组件内存状态不跨进程重启保留。**重新创建空集合不等于恢复成功**，以后接线时必须先关闭业务准入、从持久意图和驻留状态完成核对，再接受业务。当前无恢复加载接口，因此不能在已经降冷的数据集上使用这个组件启动服务。

单元测试覆盖：在途排空、新准入拒绝、跨 key 隔离、派发前取消、派发后禁止取消、不确定结果保留、晚到/重复/旧句柄、终态关闭、空与二进制 key、条目/字节/在途预算、并发请求与屏障竞争、取消与派发竞争。

```sh
go test -race ./internal/gateway -run '^TestKeyBarrier' -count=10
```

这些是内存并发测试，没有向 Redis/Kvrocks 发送命令，不证明后端淘汰正确性。下一步 G6b-2 应先验证“复制可识别的控制标记 + 精确冷层确认 + 持久意图恢复”，之后才允许隔离执行器尝试真正降冷。自动 LRU、业务接线、长期故障测试及生产部署继续后置。
