# Redis / Kvrocks 冷热混合存储预研

> 日期：2026-09-07
> 状态：冷热方案为预研，未完成可行性验证；独立 G1 骨架与 G2 单连接转发已实现，尚无冷热能力。
> 用途：后续详细设计、技术原型、评审和实现时的参考。
> 本文不承诺完整 Redis 兼容、零数据丢失、无感扩容或上线周期；不改变现有实例行为。

后续细化：[冷热网关设计与第一阶段实现计划](hot-cold-gateway-design.md)，包含职责边界、代码复用评估和纯转发骨架验收，不表示冷热协议已完成。

## 1. 目标、范围与结论

### 1.1 业务目标

- 在 Redis Pilot 已有管理平台上支持大容量、较低存储成本的 Redis 兼容服务。
- 热数据尽量在 Redis 读写，冷数据存于磁盘，候选冷层为 Apache Kvrocks。
- 自动回温和降冷，业务尽量不感知数据位置。
- 常用 Redis 命令尽可能支持；兼容基准版本、具体命令及参数清单待定。
- 支持增加容量、分片迁移和故障恢复，控制读写延迟、内存与磁盘成本。

### 1.2 当前探索方向

优先预研：不修改 Redis / Kvrocks 引擎源码，由冷热网关及同步模块承担跨层协调。
业务写入先在 Redis 执行，修改异步同步到 Kvrocks。该方向尚未最终选型。

本文中的状态约定：

| 标记 | 含义 |
|---|---|
| 目标 / 约束 | 已讨论的需求，不表示已经实现 |
| 建议 / 候选 | 可供验证的实现方向，尚未拍板 |
| 待定 / 待验证 | 尚无完整协议、选型、测试证据或业务结论 |
| 安全要求 | 若采用此路线必须满足的正确性条件，不是现成组件能力 |

总体判断：网关为回温、淘汰、同步和迁移提供了集中协调的位置，但没有消除一致性问题。
正常路径可用不等于故障时可靠。最先验证的应是操作分类、可恢复同步提交、回温并发和网关接管。

### 1.3 数据模型：不是冷热两边互斥存储

- Redis：热数据，以及尚未同步到冷层的最新修改。
- Kvrocks：全量业务数据的持久化承载层，但异步期间可能落后于 Redis。
- 热 key 可以同时在两层存在；降冷只释放热副本，不等于业务删除。
- Redis 热副本可以释放的前提是最新修改已满足冷层确认条件。
- Redis 故障或未命中，不代表可以无条件读取冷层旧值。

因此本文路线中，Kvrocks 是全量存储目标，但不能把它称为“任何时刻都具有最新值的唯一权威库”。

## 2. 已有系统与新增能力的边界

现有文档和代码表明：

- [现有 Proxy 设计](proxy-design.md) 面向单点 / 主从读写分离，明确不包含 Cluster slot 路由。
- [ProxySnapshot / ProxyCluster](../../pkg/apitypes/types.go) 当前提供监听器与后端端点，不含本方案所需的 slot 归属、网关所有权和冷热迁移状态。
- [命令路由表](../../internal/proxy/route/table.go) 对 Lua 等走主节点，不表示已经支持冷 key 回温或脚本冷热协调。
- Server 使用 `pilot.db`（SQLite）管理状态与审计；Agent 管理 Podman 容器。
- 当前引擎范围包括 Redis 5 / 6.2 / 7、Kvrocks 2.15.0；原型应固定一个 Redis 版本，具体版本待定。
- [Redis 配置模板](../../internal/agent/config_template.go) 中已有 `appendfsync everysec`；本文讨论其他策略不表示模板已修改。

可复用：容器部署、配置管理、健康检查、备份上传、审计、Server 快照分发、部分连接管理。

需要新增或重新评估：Cluster 管理、冷热网关、复制接收与应用协议、冷热状态、故障隔离、迁移编排、完整性验证。
现有读写分离允许读到副本旧值。已确认：冷热实例第一版使用单业务入口，热读热写固定走对应 Redis 主节点，不开放副本读；现有普通实例双端口行为不变。
冷热层副本用于高可用，数量与切换协议待定；不开放副本读不等于取消副本。未来副本读需另行评估一致性与性能收益。

## 3. 路线比较与 Tendis 参考边界

| 路线 | 优势 | 主要代价 | 当前定位 |
|---|---|---|---|
| Kvrocks 权威存储 + Redis 缓存 | 修改在完整数据上执行，热缓存可重建，降冷不涉及同步删除 | 写入等待 Kvrocks；缓存失效与回填仍需协调；复杂操作可能无法热层加速 | 备选、收缩范围时的退路 |
| Redis 先写 + 外部网关异步同步 | 热读热写可在 Redis 执行，不维护引擎分支 | 回温、降冷、同步、恢复与复杂命令语义转移到中间层 | 当前优先预研 |
| 定制 Redis 热层 + 磁盘冷层 | 在引擎内部集中处理数据就绪、淘汰和命令执行 | 内核级研发与长期版本维护，仍需可靠同步协议 | 外部方案不能满足兼容目标时重新评估 |

普通“双写”不是可靠协议：同时向两边发命令，或一边成功后异步补另一边，均需处理部分成功、乱序、超时和重试。

Tendis 公开的混合版架构包括 Proxy、定制 Redis、Tendis 存储层和 Redis-sync。
回温在定制 Redis 内部完成；Redis-sync 接收复制数据并导入冷层；公开资料说明了版本去重和冷热层独立扩容。
开源 Tendis 存储版不等于完整混合系统；本次未找到定制热层及整套混合组件的完整官方开源实现。
不能把公开概念直接视为不改 Redis 即可获得的能力。
资料对安全降冷屏障、故障隔离等未完整公开，不应补写成已知实现。
参见 [Tendis 官方架构文章](https://cloud.tencent.cn/developer/article/1815554)、[开源仓库](https://github.com/Tencent/Tendis)。

## 4. 组件拆分与共享部署

候选访问链路：客户端 → Proxy → 对应逻辑分片的冷热网关 → Redis / Kvrocks。

| 组件 | 建议职责 | 不应默认具备的能力 |
|---|---|---|
| Proxy | 认证、接入、逻辑分片到活跃网关的路由 | 不直接自行回温或淘汰，不默认理解所有后端迁移状态 |
| 冷热网关 | 后端路由、命令分类、回温、降冷、并发控制、资源限额 | 普通进程锁不能约束其他活跃网关或直连写入 |
| 同步模块 | 复制接收、转换、持久化缓冲、有序应用、确认进度、故障恢复 | 不能原样转发所有删除或盲目重试修改 |
| Server | 实例与分片配置、操作编排、路由发布、审计 | SQLite 与 HTTP 长轮询本身不是分布式选主或 fencing 协议 |
| Agent | 容器、资源指标、部署执行与节点操作 | 不能仅凭健康检查认定旧写入者已经失效 |

部署建议：一个网关进程可服务多个实例组和逻辑分片；每个分片只有一个活跃协调者，另有备用接管。
不是一个 slot 一个进程，也不是每个 Redis 主从副本都配一个网关。
各实例组的连接、认证、冷热状态、同步进度、内存及队列限额必须隔离。
同步模块可先与网关同进程、代码及资源隔离，是否后续拆服务待定。

安全约束：所有业务访问必须经过协调路径。运维写入、备份恢复、迁移命令也必须被纳入协议或维护窗口。
现有后端无密码、运维直连的约定需要重新评审；认证、ACL、网络隔离、TLS 的具体实现待定。

## 5. 分片、slot 与冷热映射

Redis Cluster / Kvrocks Cluster 使用 16384 个逻辑 slot。每个主分片通常负责多个 slot；副本复制主分片数据。
key 的 slot 由哈希规则确定，扩容通常改变 slot 所属节点，不增加 slot，也不把 key 改算到另一个 slot。

网关至少需要区分：

- 逻辑服务 / 实例组 → 网关协调分片 → 活跃管理者及版本。
- 热层 slot → Redis 主节点。
- 冷层 slot → Kvrocks 主节点。

建议第一版采用冷热 1:1 配对、相同 slot 范围，简化同步与管理；是否作为正式约束待定。
未来可扩展为 N:M，冷热两张 slot 表独立，不要求节点一一对应。
管理分片不一定永远等同于某个物理节点，具体边界及数据结构待定。

单点 / 主从实例不会因为网关定义 slot 就自动具有原生 Cluster 迁移能力。
采用原生集群模式的部署、版本与接口适配必须另行实现。
参考 [Redis Cluster 规范](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)、[Kvrocks Cluster 文档](https://kvrocks.apache.org/docs/cluster/)。

## 6. 冷热状态与并发控制

### 6.1 建议的概念状态

以下仅为协议设计词汇，不是已确定的状态机或数据库表：

| 状态 | 含义 | 相关请求处理 |
|---|---|---|
| HOT | 热层有可用数据 | 在有效路由与所有权下执行 |
| COLD | 热层无副本，需从冷层恢复 | 开始一次受控回温 |
| LOADING | 回温进行中 | 合并同 key 回温；冲突操作等待或拒绝 |
| EVICTING | 正在确认同步并释放热副本 | 阻止冲突写入、回温或迁移 |
| UNKNOWN / RECOVERING | 状态或历史不可信 | 重新验证；不能猜测不存在或直接回填 |

“不存在 / 已过期”与“降冷”不同；删除标记、过期元数据及其保留时间待定。
冷热状态不代表同步状态：HOT 数据也可能尚未同步。

### 6.2 必须满足的条件

- 同一个 key 的业务修改、回温、降冷和迁移交接必须遵循同一套并发协议。
- 避免旧值回填覆盖新值、重复回温、检查同步后又漏掉新写入。
- 多 key 操作不能用独立单 key 锁随意拼接；锁顺序、死锁避免与原子性范围待定。
- 锁粒度、超时、取消、在途请求恢复、版本校验方式待定。
- 全量精确冷热目录是否必要、保存位置、恢复与清理策略待定；不能直接假设所有元数据都进 `pilot.db`。
- 分片当前 owner / epoch 可用于管理，但后端不认识这些字段时，不能据此宣称旧网关已被隔离。

## 7. 请求执行与回温

### 7.1 普通单 key 命令的候选流程

1. 获取有效分片所有权及热层路由，按协议处理后端重定向。
2. 识别命令是否依赖原值、存在性、类型或 TTL；不能只看是不是 GET。
3. 热数据就绪则执行；否则进入协调后的回温流程。
4. 必要时查询完整可信的存在性过滤器；可能存在或过滤器不可信则查询冷层。
5. 取回值、类型和原到期时间，校验期间是否有业务修改、迁移或路由变化。
6. 在正确节点恢复数据，恢复操作与正常业务修改在同步协议中明确区分。
7. 执行原始命令，按定义返回；修改由同步模块持续传到冷层。

Redis 原版没有“执行中发现冷 key，向网关请求回温”的通用钩子。
外部网关必须在执行前准备数据，或限制命令使用范围。
数据传输使用 DUMP/RESTORE 还是按类型读取与重建、各版本格式兼容、大对象流式处理均待定。
不能把 Tendis 自定义的 DUMPX/RESTOREEX 当作 Redis/Kvrocks 的通用接口。

### 7.2 并发及错误语义

- 热层 nil 可能是真不存在、过期、降冷或特殊迁移状态；不能统一解释成“回温”。
- 同 key 多个请求触发回温时应合并，避免重复加载及缓存击穿。
- 冷读失败不能返回 nil；应有界等待后返回明确错误。
- 请求已发送但响应丢失，不能盲目重放 INCR、LPUSH 等修改；业务请求去重与同步去重是两回事。
- 冷层返回的数据若不能确认适用于当前执行历史，停止并校验，不能以“优先 Redis”掩盖旧数据。
- key 回温后是否长期保留、访问次数门槛及缓存污染防护待定。

## 8. 存在性过滤器

过滤器可选，不是正确性基础。原型可先让热 miss 查询冷层，后续再优化不存在 key 的访问。

候选：热层附近保存布隆过滤器或布谷鸟过滤器，由网关查询和维护。
普通 Redis 5/6.2/7 不能默认具有 BF.* 命令；使用模块是否符合“不改引擎”的部署约束、模块版本与运维方式待定。
也可在网关内使用库，具体放置位置待定。

要求：

- 表示对应范围的全量 key，而非仅热 key；降冷不移除存在记录。
- 只能回答“肯定不存在 / 可能存在”，不能表示准确位置、版本或同步进度。
- 新增记录必须与业务可见性协调，禁止因维护漏记而返回不存在。
- 重启、重建、迁移、恢复或插入失败时，过滤器不可信则绕过。
- 普通 Bloom 不能删除单项；保留已删除记录只增加无效查询，但需要控制长期膨胀与重建。
- Cuckoo 支持删除，但仍要避免错误删除、重复插入处理不当及失败插入；并非天然免维护。
- 保存为 Redis key 时不能被普通淘汰；单个过滤器 key 不会自动跟随它表示的所有业务 slot 迁移。

容量参考：标准 Bloom 理论位数组在 1000 万元素、1% / 0.1% 误判率下，约为 12 / 18 MB（十进制），不含实现开销。
容量需按全量数据及历史新增、删除、重建周期估算；扩展子过滤器会增加内存与查询成本。
目标误判率、分片粒度、容量增长与重建切换协议均待定。
参考 [Bloom](https://redis.io/docs/latest/develop/data-types/probabilistic/bloom-filter/)、[Cuckoo](https://redis.io/docs/latest/develop/data-types/probabilistic/cuckoo-filter/)、[Cuckoo Filter 论文](https://www.cs.cmu.edu/~binfan/papers/conext14_cuckoofilter.pdf)。

## 9. LRU、内存水位与安全降冷

### 9.1 选谁降冷

建议关闭 Redis 自动淘汰，使用 `maxmemory-policy noeviction`，由网关控制降冷。
noeviction 不会增加内存，到上限后相关写入会被拒绝。

可复用 Redis 已有热度：

- `OBJECT IDLETIME key`：距离上次访问的秒数，非 LFU 策略可用，包括 noeviction。
- `OBJECT FREQ key`：近似访问频率，仅 LFU 策略可用，不能同时假设 noeviction 下可用。
- Redis 使用近似 LRU；在所讨论的 Redis 5/6.2/7 中没有直接导出内部淘汰候选池的标准命令。

候选实现：限速 SCAN 获取候选，pipeline 查询 IDLETIME，只维护有上限的候选池。
不要求网关复制全量 key 热度表；采样量、扫描周期、候选排序、大 key 权重待定。
热度可以近似，安全同步判断不可以近似。
参考 [IDLETIME](https://redis.io/docs/latest/commands/object-idletime/)、[FREQ](https://redis.io/docs/latest/commands/object-freq/)、[淘汰机制](https://redis.io/docs/latest/develop/reference/eviction/)。

监控 Redis used_memory、maxmemory，并同时关注 RSS、容器上限、碎片、复制缓冲、持久化开销和回温临时内存。
80% 开始降冷、70% 停止、90% 加强保护仅是讨论示例，不是正式默认值。
网关 Go map、key 字符串、GC、连接缓冲、同步日志索引也要计入成本。

### 9.2 怎么安全释放

候选过程：选 key → 排除冲突与处理在途操作 → 确认对应修改已可靠同步 → 仅释放热副本 → 更新状态 → 放行。

未解决的协议点：

- 如何把该 key 的最新修改关联到源复制位置；一个“延迟为 0”指标不够。
- 检查与删除之间如何阻止漏写；超时如何恢复而不误判。
- 业务删除、过期删除、降冷删除、回温恢复、迁移清理如何精确分类。
- 原版 DEL / UNLINK 是删除命令，会进入复制流；UNLINK 只改变内存释放方式，不表示“仅热层删除”。
- 不能用“忽略此 key 下一条 DEL”的临时表，可能误吞业务删除且无法可靠应对重启。
- 需要操作级标识、顺序和恢复协议；标记如何与实际 Redis 操作绑定待定，尚无已验证方案。

冷层不可用时第一版建议暂停所有自动降冷，避免增加异常路径。

## 10. Redis → Kvrocks 同步设计

### 10.1 接入方式

建议模拟 Redis 从库订阅复制流：初始 RDB + 后续增量，而不是记录网关收到的请求。
复制流包含实际产生的变化，但也包含过期、淘汰和内部维护操作，必须分类。
初始全量只在数据源确实完整、目标导入规则明确时进行。

Kvrocks 原生复制使用 RocksDB 备份和 WAL 批次；不能直接以 `SLAVEOF Redis地址` 构成异构主从。
同步模块需要解析 Redis 数据并转换为 Kvrocks 支持的操作。
参考 [Redis 复制](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)、[Kvrocks 复制](https://kvrocks.apache.org/docs/replication/)。

### 10.2 现成组件评估

RedisShake 可作为 PSYNC、RDB 解析和写入转换的复用候选，不直接作为最终长期同步方案。
调研时 v4 官方 README 明确列出：重启后无 checkpoint 续传、无集群拓扑变化感知，定位更适合一次性迁移。
固定版本、许可证合规、代码复用边界、Kvrocks 命令和 RDB 格式适配均需评估。
没有验证 RedisShake 开箱即用兼容本项目的全部组合。
参考 [RedisShake 官方仓库及限制](https://github.com/tair-opensource/RedisShake)。

### 10.3 日志与确认

建议按源主节点接收有序流，第一版保留源顺序；之后再评估 slot 间并行。
事务、跨 key 和全局命令不得因拆队列破坏顺序或原子性。

同步模块需要区分接收位置、持久化缓冲位置、目标应用位置、目标可靠确认位置。
源位置必须带复制历史标识，不能只保存 offset；切主后的历史关系需验证。
并行后确认位置只能越过连续完成的范围，不能把后面的完成项当成前面全部完成。

候选：有界磁盘日志保存已接收增量；容量、刷盘、校验、加密、GC 和故障副本策略待定。
本地日志不能防整机磁盘永久丢失，不能自动提供零丢失承诺。
Redis backlog 是有限缓冲，AOF 是本机恢复格式且会重写；不能默认二者是无限保留的消费日志。

### 10.4 去重与提交：必须先验证

目标已执行修改但 ACK 丢失后，重放可能重复生效。仅使用 pipeline、按序写入或本地 checkpoint 都不够。
不能笼统假定复制流里的每条修改都是原始业务命令，也不能反过来假定所有传播形式天然幂等；需检查具体版本与命令。

候选路线：

- 目标侧原子校验序号、应用修改并记录进度；能否在 Kvrocks 2.15.0 中不改源码覆盖目标命令范围，待验证。
- 转换为带版本的状态覆盖；复杂集合、大 key、TTL、删除墓碑、并发取值与带宽成本待验证。

上述不是已选方案。普通 MULTI、脚本、额外元数据 key 不应未经测试就宣称具备崩溃安全的 exactly-once 效果。
数据修改与去重元数据必须具备所需的原子性、持久化和副本恢复语义。
无法证明时，不能启用自动降冷并承诺可靠。

### 10.5 断点失效与全量重建

开始降冷后 Redis 只有部分数据。此后若 PSYNC 不可续传，不能拿热层 RDB 清空并覆盖冷层。
简单合并也不安全：遗漏的业务删除可能导致冷层保留已删数据。

需设计保留日志、经过验证的补偿重建或人工恢复流程；超出可恢复范围时冻结相关操作并告警。
同步进程重启、源主切换、冷层切主、历史缺口、迁移生成恢复/删除等分别设计，不得都归结为“重试”。

## 11. 写入承诺与持久化

业务可接受的数据损失范围（RPO）、恢复时间（RTO）、失败场景及延迟目标均待定。

| 项目 | 候选基线 | 限制 |
|---|---|---|
| 热层 | AOF always 与 everysec 都做基准，先以 always 测保守成本 | 本机刷盘不等于机器/磁盘损坏或切主零丢失 |
| 冷层 | WAL 启用，评估 write_options.sync yes | 默认 sync no 不能当作已可靠刷盘 |
| 返回成功 | 性能路线不等待冷层，依赖约定的热层确认 | 异步窗口必须明确披露 |
| 允许降冷 | 冷层数据、应用进度满足恢复要求且无冲突写入 | 不能仅凭复制接收 ACK 或监控延迟 |
| 高可靠选项 | 额外副本/冷层确认纳入成功条件 | 策略与协议待定，会改变延迟和可用性 |

Redis always 在相应 AOF 刷盘后返回；everysec 存在近期写入丢失风险。WAIT 也不能把异步 Redis 集群变成零丢失系统。
Kvrocks 2.15.0 默认 `rocksdb.write_options.sync no`、`disable_wal no`；打开 sync 会影响写入性能。
这些配置只提供局部保障，不替代端到端同步协议。
参考 [Redis 持久化](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)、[Redis 复制与 WAIT 限制](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)、[Kvrocks 2.15.0 配置](https://raw.githubusercontent.com/apache/kvrocks/v2.15.0/kvrocks.conf)。

## 12. 冷层故障与资源保护

建议第一版采用保守降级，范围按受影响分片确定，不拖垮整个服务：

| 请求或操作 | 冷层确认不可用后的候选行为 |
|---|---|
| 可信热层上的普通热读 | 继续 |
| 需要冷数据的读取或修改 | 有界等待后明确报错，不返回 nil、不从零执行 |
| 新业务写入 | 第一版建议暂停受影响分片；已经执行的修改继续可靠保留 |
| 降冷、非必要回温、启动扩容 | 暂停 |
| 在途迁移与维护操作 | 按任务阶段恢复或停止，不强行改路由 |

后续可选有限热写模式，前提是修改日志可恢复且不会淘汰未同步数据。
监控并限制积压字节、最老未同步时间、日志磁盘占用、内存水位、等待请求数。
阈值必须在资源耗尽前触发；预留在途请求、日志与回温空间。

恢复顺序：确认身份与复制历史 → 续传和校验 → 逐步恢复写入 → 限速回温 → 恢复降冷。
熔断阈值、探测方式、超时、错误码、恢复速率、允许有限热写的条件均待定。
不能把超时但可能已执行的写请求标注为“安全重试”。

## 13. 扩容与重定向

### 13.1 复用底层能力

- N 指主分片数量。N→N+1、N→2N 都是增节点并重新分配已有 slot。
- 均匀分配下，前者迁移约 1/(N+1) 的总 slot，后者约一半；不保证相同比例的 key、字节或 QPS。
- Redis add-node 不等于自动均衡，仍需 reshard/rebalance 等编排。
- Kvrocks 提供 CLUSTERX MIGRATE 与 slot 拓扑更新能力，管控要发起、跟踪和处理失败。
- 底层搬迁引擎尽量复用；Server 实现流程封装，不自己重新写逐 key 复制工具。

### 13.2 谁知道 key 搬完了

Redis Cluster 迁移期间可能由旧节点返回 ASK；同一连接先 ASKING，再执行原命令，临时转向不等于更新永久路由。
MOVED 表示应刷新/更新 slot 路由。nil 不是迁移信号。
执行到后端的网关可承担这些处理，前置 Proxy 只维护逻辑网关路由。
多 key 迁移状态还可能产生 TRYAGAIN 等错误，不能只实现单 key ASK/MOVED 分支。
Kvrocks 需按固定版本的迁移状态与错误行为适配，不能假设与 Redis 每个细节一致。

### 13.3 冷热联动

| 扩容对象 | 底层负责 | 本系统还要负责 |
|---|---|---|
| 热层 | 搬热层实际持有的数据 | 回温/降冷协调、同步源交接、冷热目录与过滤器有效性 |
| 冷层 | 搬全量存储数据 | 同步目标与冷读路由更新、重试语义、未同步数据保护 |
| 网关 | 不属于引擎迁移 | 协调所有权、在途操作与旧管理者隔离 |

建议一次迁移少量 slot，允许受影响请求在最终交接时等待或重试，暂停时间必须实测。
复制阶段不应停整个实例；但不能笼统描述为“完成前全在旧节点”，应尊重原生迁移协议。
冷热 1:1 方案可由一个逻辑任务协调两层交接；未来独立扩容先避免冷热同一范围并发迁移。
具体切换屏障、顺序、超时、提交点、失败回滚/向前恢复均待定。
一旦新节点已接受写入，不能简单把路由改回旧节点当作回滚。

原生热层迁移只搬热数据，不包含已降冷 key；所有权元数据和过滤器必须覆盖完整逻辑范围。
内存纵向扩容不改变 slot，但需真实增加宿主机/容器资源并调整限制；不能只调大 maxmemory。
参考 [Redis Cluster 规范](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)、[Kvrocks Cluster 文档](https://kvrocks.apache.org/docs/cluster/)。

## 14. 网关高可用与故障隔离

建议每分片单活、多副本待命，一个进程管理多个分片；负载按分片分散，不随机把同一分片的协调请求送到独立状态副本。

必须解决：

- 选主与所有权的可靠存储、租约、任期以及故障检测，技术选型待定。
- 真正阻止旧 owner 继续写后端。修改路由、内存锁或宣告租约过期都不是充分条件。
- 不改引擎时网络隔离、连接隔离、凭据切换等候选的有效性需验证；未完成隔离不得安全宣称接管成功。
- 恢复 LOADING/EVICTING、同步提交和迁移任务，不依赖易失内存标记。
- 网关已执行但未响应的业务请求不能自动重复执行。
- Server、Agent、网关、同步程序、冷热主节点分别故障及组合故障的行为待定。

网关本地持久化目录、备用节点如何获取状态、Server 不可用时数据面可持续多久、滚动升级协议均待定。

## 15. 命令兼容、TTL 和全量视图

### 15.1 命令目标

目标是常见命令尽可能支持，不承诺所有 Redis 版本、命令与参数。
当前普通 Proxy 能透传事务/脚本，不表示冷热网关也能透明支持。

| 类别 | 原型建议 | 需要重点验证 |
|---|---|---|
| 字符串 GET/SET/INCR/DECR/APPEND、条件写 | 首批逐项验证 | 冷原值、NX/XX、类型错误、返回值、TTL |
| Hash / List / Set / ZSet 常用非阻塞操作 | 后续首批扩展 | 完整对象恢复、计数返回、大 key、内存放大 |
| DEL/UNLINK/EXISTS/TYPE/过期命令 | 必测 | 冷 key 语义、业务删除与降冷区分 |
| 多 key 操作 | 建议先同 slot | 原子性、锁顺序、迁移期间错误、部分回温失败 |
| MULTI/EXEC/WATCH、Lua | 待定，不能默认支持 | 全部依赖 key 的准备、脚本契约、执行期间原子性 |
| 阻塞命令、Pub/Sub、Stream/消费组 | 待定 | 独占连接、等待唤醒、确认/重投、会话恢复 |
| SCAN/DBSIZE/KEYS、全局命令 | 待定或明确限制 | 全量逻辑视图、跨分片、权限与成本 |

不支持的命令及参数应明确拒绝；不能只识别命令名后让冷数据按“不存在”执行。
协议版本、SELECT/多 DB、hash tag、客户端重试行为、错误码兼容、事务和脚本准入条件待定。
最终清单需对固定版本测试，参考 [Kvrocks 命令清单](https://kvrocks.apache.org/docs/supported-commands/)。

### 15.2 TTL

过期属于业务数据失效，不是降冷。冷 key 也要按原到期时间判定存在性。
回温携带原绝对到期时间或等效剩余 TTL，并扣除传输等待时间；不能重新延长寿命。
时钟偏差、恢复时过期、过期删除传播、持久化日志重放中的 TTL 行为需测试。
具体时间来源、误差容忍和原子恢复协议待定；“TTL 没问题”仅表示认可需求，不表示实现已解决。

### 15.3 全量查询

Redis 只含热数据，Kvrocks 又可能落后；只查任一侧都不能自动等同于最新逻辑数据库。
简单合并还会遇到未同步删除、重命名、重复记录和遍历期间变化。

建议后台分别展示热层、冷层指标与同步延迟，不伪装为精确全量统计。
业务 SCAN/DBSIZE 在正确视图实现前明确限制，不能只返回热数据却声称完整兼容。
全局索引、合并游标、墓碑处理与成本待定；KEYS 建议默认禁止。

## 16. 备份、恢复与初始化

建议以 Kvrocks 全量检查点为备份主体，Redis 热缓存可重建；不能只备份 Redis。
Kvrocks 原生支持 BGSAVE 生成备份，但冷热一致性边界需网关和同步模块协调。
参考 [Kvrocks 备份](https://kvrocks.apache.org/docs/backup/)。

第一版候选维护窗口流程：

1. 暂停逻辑实例新写入及相关冷热迁移，处理完在途操作。
2. 记录各源分片截止位置，等待冷层应用、去重状态及持久化满足要求。
3. 建立冷层备份检查点，记录拓扑、同步历史与恢复所需元数据。
4. 确认备份边界固定后恢复服务，再完成文件上传和校验。

仅发出 BGSAVE 命令不能推断快照边界已固定；确认方法和暂停时长待验证。
跨分片一致性、绝对过期时间、备份加密、保留周期、全量/增量策略、PITR 均待定。

恢复流程候选：在隔离的新环境恢复冷层及元数据，建立新的合法同步历史，Redis 从空热缓存启动。
同步程序不得把这个空 Redis 当成新的全量权威快照覆盖冷层；如何启动新同步纪元待定。
过滤器未恢复可信前绕过；校验完成后再切入口，旧环境保留至验收完成。
已有 Redis 服务首次导入、启用冷热模式的切换窗口、回退到原服务方案待定。

## 17. 可观测性、成本与容量规划

建议至少采集：

- 业务热命中率、冷查命中率、过滤器误判/绕过率、回温成功率与耗时。
- 网关排队时间、同 key 等待、在途回温量、拒绝数、未知结果写入数。
- 同步接收/持久化/应用/确认位置、最老积压时间、日志字节与磁盘剩余。
- 降冷候选数、成功释放字节、因未同步跳过数、状态卡住时间。
- ASK/MOVED/TRYAGAIN、路由版本、所有权切换、恢复失败、备份恢复校验。
- Redis 内存/RSS/碎片、Kvrocks WAL/compaction/写停顿、网关堆内存/GC/连接数。

容量需同时计算冷热副本、网关与过滤器内存、同步日志、迁移临时空间、备份与网络。
冷热分离节省的 Redis 内存不能掩盖新增组件成本。
目标 QPS、P50/P95/P99、数据量、key 长度、对象大小分布、冷热比例、访问偏斜、同步带宽、恢复时间均待定。
大 key 限额、对象部分回温、热度门槛、压缩参数、SSD 规格和容量安全余量均待定。

## 18. 实施阶段与验收门槛

| 阶段 | 工作 | 进入下一阶段的条件 |
|---|---|---|
| P0 协议设计 | 固定版本、命令范围、操作分类、同步去重、故障模型 | 关键状态与不确定结果有明确处理，不靠临时标记猜测 |
| P1 单向同步 | 单分片，禁止降冷/回温，验证 RDB + 增量 | 命令/TTL 正确，断线重启、重复投递、ACK 丢失可恢复 |
| P2 单分片冷热闭环 | 受控回温、LRU、安全降冷、资源保护 | 并发及故障注入后不丢不乱，日志缺口可检测 |
| P3 网关高可用 | 所有权、旧节点隔离、备用恢复 | 分区与接管中无双写，不盲目重放业务请求 |
| P4 Cluster 扩容 | 热冷路由、原生迁移、同步交接 | 迁移中持续负载、过滤器不完整和故障切换均可验证 |
| P5 命令与运维扩展 | 常见类型、多 key、备份恢复、监控 | 按兼容矩阵与性能目标验收；高级命令单独准入 |

并非必须一次性实现全部阶段。P0/P1 若证明“不改引擎”无法满足关键语义，应收缩命令范围、转为权威冷层缓存路线，或重新评估定制 Redis。

最低故障测试集：

- 回温取值后、恢复前发生业务写入、过期、降冷或 slot 迁移。
- 确认可降冷后、实际删除前发生修改；标记、删除、进度提交的每个窗口进程退出。
- 冷层已应用而响应丢失；日志重复、截断、校验失败、磁盘满。
- 源复制历史缺口、热层已降冷后被要求全量重同步。
- Redis/Kvrocks 切主、网关网络隔离、旧 owner 在新 owner 接管后恢复连接。
- 大 key、热点 key、冷层慢、同步停滞、集中回温、所有队列达上限。
- 备份恢复到隔离环境后，验证值、类型、到期时间、计数、删除和恢复边界。

故障测试应使用可追踪操作历史的校验模型，区分“明确未执行”和“结果不确定”，不能只比较最终 key 数量。
