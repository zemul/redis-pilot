# G6b-2e：持续同步期间的准备屏障与确认

> 2026-09-08。持续捕获、屏障前应用、运行中确认和重启恢复已接通。显式隔离单任务模式；仍无热删除、冷驻留发布、回温和业务请求接线。

前置：[G6b-2d 确认通信](gateway-confirmation-rpc.md)。旧的离线确认模式保留；本轮不改变普通 `-config` 多任务同步服务的默认行为。

## 1. 新增运行方式

同一 `redis-syncer -confirmation-config ...` 入口增加 `mode: isolated-confirmation-live`。它在一个进程内同时运行持续同步循环和确认 HTTP 接口，独占同一个源日志。确认不再要求每次停止捕获、切换到离线模式。

仍要求一个**已有、历史固定的 named 捕获日志**，初次启动此模式前原日志持有者必须已退出。空库初始化/初次源快照编排没有新增自动接口；不得拿新日志代替丢失日志，也不得自动接受 FULLRESYNC 覆盖。

沿用 [隔离确认配置](../examples/syncer-confirmation-isolated.yaml)，仅将 `mode` 改为 `isolated-confirmation-live`。绑定中的 source/history/epoch 等字段仍必须真实且匹配，两端目录及凭据规则不变。

`-check-config` 支持新模式，但依然只检查配置和凭据，不启动捕获、不打开日志、不监听或访问后端。

## 2. 持续循环怎样停在正确位置

在同一份不可变日志视图中识别第一条准备标记，并应用到相应终点。不能先扫描一次，再让普通应用器打开一个可能包含新标记的更晚视图，否则会出现检查与执行边界不一致。

- 没有准备标记：校验并应用该视图的普通业务前缀，沿用已有 pending 机制及安全分段回收。
- 找到准备标记：严格检查原始 RESP、任务绑定、意图版本、key、history 和 epoch，先持久保存本地意图与准备证据；冷层只应用到该标记的前驱 checkpoint。
- 一旦屏障生效：缓存已经验证的停止位置，不反复扫描增长的后续日志、不逐轮重放业务写；停止这条任务的冷层应用和相应日志回收。
- 标记后的记录只捕获、持久保存，不被普通应用器执行。它们可能包含本轮不支持的命令，未来解除屏障前必须另外验证，当前不能声称已经兼容。

这里暂停的是**该单任务/分片的整条冷应用队列**，不是只跳过某一个 key。确认后也不解除。这样保留顺序与恢复证据，但会让其他 key 的冷层更新一起滞后；它是当前单未完成操作原型的明确限制。

非法准备标记、错误任务/epoch、屏障之前的普通不支持命令都拒绝，不扩大原同步器的白名单。源端标记是数据，不是执行授权；即使匹配也只会关闭应用通道、建立待确认记录，不允许删除热数据。

## 3. HTTP 确认如何与循环协调

应用循环和确认请求共用本进程串行通道；捕获线程不持有这个通道，可以继续写分段日志。

同步器必须已经完成恢复、识别了对应准备事件并应用到屏障前，才接受该操作的 POST。未发现标记、任务未就绪、操作不匹配、失败或停止中均拒绝。

确认路径复用 G6b-2c 的源日志证明、Kvrocks WATCH/receipt 提交以及双端独立落盘。实时源角色/历史仍在确认前后核对。Live 模式使用已经定位的准备事件，并由提交内核再次证明来源，不为了每次确认扫描整个增长中的后续日志。

同步器停止或失败时及时关闭确认准入，正在执行的请求完成后还要再次检查停止状态；不能在捕获循环已经退出时继续把 HTTP 端点当作可用的同步服务。接近停止边界的凭据依然只是历史核验结果，不是分布式租约或删除许可。

## 4. 持久恢复与状态

待确认状态不是靠内存标签保存：日志中的精确准备事件 + 本地 `confirmation-operation.log` 中的意图/准备记录是恢复依据。已确认状态还包含该文件的第三条 receipt。

| 观察状态 | 含义 |
| --- | --- |
| `none` | 当前恢复/扫描位置尚未建立准备屏障；不是“没有冷数据” |
| `waiting_confirmation` | 准备证据已落盘，屏障前业务已应用，尚未得到本地确认记录 |
| `recorded_requires_revalidation` | 重启读到了历史 receipt，仍需客户端请求在线重新核验 |
| `confirmed_held` | 本次运行曾完成在线确认，屏障仍保持；不是永久有效证明 |

已有操作却找不到源标记、恢复意图不一致、日志链/receipt 不匹配，均停止，不跳过标记。确认成功或重启不推动普通 checkpoint 跨过准备标记。

新增受相同 Bearer token 保护的只读接口：`GET /internal/v1/cold-confirmation/status`。返回循环状态、上述屏障状态、是否接受确认、持久捕获/应用位置及其有效性、捕获尝试次数、暂停标志和最近在线核验时间；不返回 key、值、路径或 token。

位置只有 `captured_valid/applied_valid` 为 true 时可解释，启动阶段的默认数字不能被当成真实进度。`accepting_confirmation` 只是此端点的本地准入状态，不代表冷库健康或业务可删除。确认失败会清除本次运行的在线核验标签；历史 receipt 仍保留，等待重新核验。

## 5. 持续写入与资源上限

屏障后的源写入仍由 PSYNC 捕获并落盘。沿用磁盘空闲水位、文件总预算、视图数和重试上限；live 模式进一步把未确认积压阈值设为 `min(64 MiB, journal_bytes / 8)`，恢复阈值为其一半。该差值基于持久 GC 确认位置，属于保守积压预算，不是准确业务大小或物理磁盘占用。

达到积压/磁盘阈值时，循环停止并等待捕获线程及 ACK 线程退出，不为了恢复捕获而跨过屏障或清理它之后的日志。持续压力默认超过现有循环的 5 分钟上限会以错误停止；本轮真实测试只验证短时暂停/恢复，不是 5 分钟长测。

`journal_bytes / 8` 留出了封装和元数据空间，但不是文件大小的数学保证或磁盘预留。极端小命令的高封装开销、超大记录、磁盘错误或硬容量上限仍可能直接终止任务；这些错误不会自动删除证据或继续不安全应用。

**暂停捕获不等于限制 Redis 写入。** 当前 Gateway 尚未接业务限写；Redis backlog 如果在暂停期间不足，后续 PSYNC 可能无法续传，届时拒绝自动全量替换。热内存限写、业务背压与灾难恢复仍须另外实现。

## 6. 退出行为

SIGTERM 先阻止新确认并停止捕获，等待最后完整记录落盘，再验证屏障停止位置和本地尾部。保持屏障的退出报告为 `stopped`，不能报告 `drained`，因为冷层并没有应用完全部已捕获记录。

普通同步循环原有“冻结尾部并完全排空”的退出语义不变；特殊停止规则仅用于显式 live-confirmation 模式。HTTP 请求、循环、捕获和 ACK 工作者退出后才释放日志锁。关闭时不会生成虚构确认、删除热 key 或自动解除屏障。

## 7. 验证与未完成项

本地测试覆盖同视图边界（含扫描后并发追加）、非法标记、普通命令白名单不变、准备文件恢复与冲突、真实分段写入下的暂停/保留/停止状态，以及配置只读检查和原有循环/确认回归。相关 race 测试三轮通过；需要外部后端的用例在本地普通测试中按规则跳过。

真实集成使用独立 `redis-syncer` 二进制、Gateway 测试进程与专用 Redis 7.2.5 / Kvrocks 2.15.0：先运行持续循环，再生成准备标记，同时持续写入后续 key；验证捕获前进而冷应用不前进、确认前强杀恢复、回复丢失与重复确认、确认后重启重验、积压暂停、保持屏障的优雅停止和再次恢复。旧离线确认模式也同时回归。命令与最终结果见 [验证记录](benchmarks/g6-live-confirmation-20260908.log)。

本轮不修改生产/开发既有服务路由，测试后停止新建专用容器。不提供性能结论，不覆盖所有 fsync/掉电故障窗口，也不是 Cluster 接管验收。
