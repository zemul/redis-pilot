# G6b-2b：持久操作意图与删除前准备标记

> 2026-09-08。已实现隔离的单操作本地日志和只准备、不删除的真实 Redis 实验。
> **没有冷层 ACK、没有业务淘汰接口、没有接 Gateway/同步器服务，也没有写 Kvrocks。**

前置：[G6b-1 操作屏障](gateway-key-barrier.md)、[G6b-2a 内部移除记录实验](gateway-eviction-envelope.md)。

## 2. 先准备，再等待冷层确认

上一轮的 begin/UNLINK/complete 是**移除阶段**的记录形态，不能用它的事后位置证明删除前冷数据已经安全。

本轮顺序为：

1. 从已知源历史构造操作意图：task、随机 128 位 operation ID、epoch、源 history、二进制 key、预期值 SHA-256；同时绑定源/冷目标端点。
2. 创建本地日志，写入意图并完成文件及父目录 fsync；失败不得继续派发。
3. 在临时 Redis 执行准备脚本：确认 key 是无 TTL String、值与预期字节完全相同，才 SET 专用准备标记。**不删除、不改写业务 key**。
4. 从本地持久捕获日志取得这一次准备事件的原始 RESP、源 history、前后 byte offset，校验后保存到操作日志。
5. 停在“已捕获准备事件，仍等待精确冷层确认”。没有任何方法把这个状态转换成“允许删除”。

准备 key 为 `__pilot_sync_v1__:{g6b-probe}:prepare:<task>:<operation>`，值为 `prepare:<intent>`；它和上一轮的移除阶段标记分开。前缀仍是单实例实验格式，不是已经确定的 Cluster 元数据布局。

相同标记且热值仍符合预期时，重试返回“已经准备”，不会新增一条复制写入。若热值改变，即便标记还在，也拒绝旧操作重试。

实际捕获的准备事件是普通 SET 标记，可能有前面的 SELECT 0；操作日志绑定的是精确 SET 记录及其前驱位置，不把 SELECT 当作业务变化。DB 0 的上下文、脚本权限和后端绕写隔离仍由未来执行器保证。

## 3. 日志内容与恢复规则

一个日志文件只容纳一个操作，格式为固定 magic + 校验帧：

| 记录 | 内容 | 本轮含义 |
|---|---|---|
| 初始记录 | 源/冷目标身份、task、完整 intent | 有一项需要恢复/追踪的操作，可能尚未派发，也可能已经派发准备事件但结果丢失 |
| 可选第二条 | 准备事件原始记录和前驱位置 | 已保存该事件的位置证据；不是冷层完成证明 |

每帧有长度与 CRC32C，并复用现有分段日志的规范 JSON 校验；拒绝未知/重复字段等非规范编码。单帧最多 256 KiB，文件最多 512 KiB；key 和预期 value 各限制 64 KiB。日志不保存 value 原文，但保存二进制 key 和值摘要，因此仍视为敏感文件。

写入规则：

- 创建使用 exclusive create，绝不覆盖已有文件；恢复使用只打开现有文件，缺失时绝不创建空日志。
- 要求可信的 owner-only 父目录，文件必须为当前用户所有的 owner-only 普通文件；拒绝叶子符号链接、硬链接、非普通文件和不私有目录。通过已打开父目录的 `openat` 创建/打开文件。
- inode 上的非阻塞排他锁拒绝同路径并发打开。它不是跨 Gateway 的分布式锁，也不能阻止特权用户替换目录或另用一个路径。
- 每次记录完成文件 fsync 才发布内存状态；创建还必须完成父目录 fsync。恢复完整存活记录后也重新 fsync，再返回句柄。
- 写入/同步边界结果不确定时句柄失效，不能继续写或读出“成功”状态，必须关闭、重新核验。错误不会直接输出底层路径或业务内容。
- 相同准备记录重复保存不追加；同操作出现另一位置或改写记录则拒绝。
- 关闭后不能使用句柄；快照和输入记录进行深拷贝，避免调用方改动已经保存的内存状态。

恢复时重新核对源/冷端点与 task 身份，重建意图和可选准备记录。空文件、损坏、半条尾部、额外记录、越界文件、身份不匹配全部拒绝；不截断、不清理、不把它们视为“无事发生”。失败创建留下的空/部分文件也要显式处理，不能重新创建覆盖。

**恢复出的 epoch 只是历史数据，不是有效执行权限。** 源历史/分片所有权/冷热驻留核验没有完成前，不得接业务。这个日志恢复不是完整 Gateway 恢复，更不是自动故障接管。

## 4. 信任与资源边界

`recordPreparation` 能验证准备事件和当前意图的精确字节、源身份、history、offset 连续性，不能单靠传入结构证明记录确实来自持久 PSYNC 日志。当前真实集成测试从已停止的 capture journal 读取；正式实现必须由同步器持有的已验证日志视图提供，不能接收客户端伪造的“确认”。

当前只保存两种状态，不接冷层 ACK、不提供派发删除/完成/清理接口，也没有后台恢复扫描。未来必须为每个分片规定固定日志位置；现在调用方若自行创建很多不同文件，单文件上限不会限制全机总占用。多操作队列、任务总预算、并发候选数、压缩和回收均待做。

准备标记当前留在测试 Redis 中直到测试实例关闭；生产不能按全部冷 key 永久积累描述符。标记何时回收、回收后如何阻止旧操作复活，须与持久驻留和旧执行者隔离一起设计，不能随意加 TTL。

## 5. 下一步：精确冷层确认，仍未实现

现有冷层 pending 协议会核对 checkpoint、pending 原始记录和 before/after 数据；可以复用这一验证思路，**不能直接把观测到的 offset 相等当作 ACK**。

下一步需要在隔离应用路径中实现：

1. 先建立准备记录与已验证源日志链的关联，按顺序确认它之前的业务写已经应用。
2. 同步器识别受信任的准备事件，检查冷层该 key 的类型、TTL、值摘要和操作身份；准备动作在冷层不改变业务逻辑值。
3. 用经过故障验证的提交协议，把准备确认与冷层 checkpoint/恢复证据一致推进。ACK 绑定 operation ID、task/归属、源 history、精确位置及摘要；字段匹配仍不能取代真实后端提交验证。
4. 处理回复丢失、pending 未完成、checkpoint 已推进但确认缺失、值偏差等情况；任何不能证明的状态继续阻断。
5. Gateway 在接受可信 ACK 后将相关状态落盘，再进入独立的删除派发阶段。重启后仍需重新核对未完成操作和冷热驻留，不能直接依赖旧 ACK 放行。

确认的存储格式、鉴权通道、与现有冷层元数据所有权检查的兼容方式尚待实现。当前应用器继续拒绝准备命名空间写入，未放宽业务命令准入；把本实验标记写入现有运行同步任务会导致其拒绝继续应用，不能当成上线步骤。

TTL、复杂结构、多 key、分布式所有权、Cluster 切主/迁移、FULLRESYNC 后冷数据保护、RPO 和长时间冷层故障策略仍未解决。

## 6. 测试及验收边界

真实 Redis 实验链路：意图 fsync → 准备脚本 → PSYNC 持久捕获 → 保存精确准备记录 → 关闭/重开操作日志；验证同一个 operation ID 和准备记录恢复、热 value 保留、重复准备不产生第二次写、热值更新后旧操作被拒绝。仅本机临时 Redis 7.2.5；冷目标端点在测试中只用于身份绑定，没有连接。

子进程测试分别在意图 fsync、准备记录 fsync 后发出信号，父进程强杀那个测试子进程，然后重开相同日志验证阶段恢复。另有 before-write/after-write/after-fsync/目录 fsync 边界的注入测试，以及截断、校验损坏、权限、软硬链接、身份偏差、文件/字段大小限制和并发重复保存测试。

这些不等于断电/文件系统故障测试；注入错误不等于真实磁盘写满；子进程不是已部署 Gateway；恢复“准备已捕获”不等于冷数据安全。

```sh
GATEWAY_TEST_REDIS_SERVER=/opt/homebrew/bin/redis-server go test -race ./internal/gateway -run '^(TestEvictionOperation|TestEvictionEnvelope|TestKeyBarrier)' -count=3
go test ./internal/gateway ./internal/syncer ./cmd/syncer
go vet ./internal/gateway
```

不设置 Redis 测试路径时真实 Redis 用例跳过。未远端部署、未启动长测、未修改业务路由。性能与正常热写开销尚未测量。

本轮实际结果：上述真实 Redis + 意图日志/强杀恢复 + 移除记录/屏障的三轮 race 组合通过（11.803 秒）；Gateway、同步器及同步器入口回归通过；`go vet ./internal/gateway` 与 `git diff --check` 通过。测试目录显式设为 0700，保留日志对私有父目录的要求，没有为通过测试放宽权限检查。
