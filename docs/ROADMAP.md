# Redis Pilot 产品优化路线图

> 版本：v0.1  
> 日期：2026-08-13  
> 状态：讨论稿  
> 范围：Redis Pilot Web/H5 管理平台及其配套 Server、Agent、Proxy 能力

## 1. 背景

Redis Pilot 已具备实例、节点、备份、故障转移、代理和操作审计等管理能力，Web/H5
当前主要承担全局状态查看和轻量操作。现阶段的主要问题不是页面数量不足，而是缺少从
“发现异常”到“完成处置”的运维闭环：

- 实例详情以即时 INFO 数据为主，缺少历史趋势。
- Redis/Kvrocks 已配置慢日志，但平台尚未采集、持久化和查询慢日志。
- 异常总览展示当前状态，尚未形成带产生、确认、恢复状态的告警事件。
- 备份和指标等能力分散在实例操作中，缺少跨实例的统一工作台。
- Proxy、实例、宿主机和操作事件尚未形成可关联的排障视图。

下一阶段以实际运维工作流为主线，不以增加菜单数量作为目标：

```text
发现异常 -> 定位实例 -> 判断原因 -> 执行操作 -> 验证恢复 -> 留下记录
```

## 2. 产品定位与边界

Redis Pilot 是 Redis/Kvrocks 的管理和诊断入口，负责解释“发生了什么、为什么、接下来
能做什么”；Prometheus/Grafana 等通用可观测系统负责大规模时序存储、自由查询和跨系统
监控。两者可以同时提供，但职责不同。

### 2.1 Redis Pilot 负责

- 展示精选的 Redis、Kvrocks、Proxy 和宿主机核心指标。
- 关联拓扑、慢日志、告警、任务、备份、配置变更和操作审计。
- 提供 Redis 语义化的异常解释、诊断建议和安全运维操作。
- 由 Agent、Server 和 Proxy 暴露指标，统一进入 Prometheus。
- 通过 Server 查询 Prometheus，并向 H5 提供稳定的 Redis 语义化接口。

### 2.2 Redis Pilot 不负责

- 替代 Prometheus 的大规模时序数据库能力。
- 提供任意指标表达式和通用 Dashboard 编辑器。
- 承担跨数据库、主机、网络和业务应用的统一监控平台职责。
- 在当前阶段实现多年数据保留和复杂的通用告警编排。

### 2.3 P1 已确认的数据边界

P1 不将高频性能采样写入 `pilot.db`，也不提供 SQLite 指标后端。数据按性质拆分：

| 数据 | 权威存储 | 平台使用方式 |
|------|----------|--------------|
| 数值型时序指标 | Prometheus | Server 通过 Prometheus HTTP API 查询并转换为 H5 模型 |
| 慢查询数量和趋势 | Prometheus | 使用 Counter/聚合指标绘制趋势和触发告警 |
| 慢查询具体明细 | `pilot.db` | 按时间、实例、节点、命令查询 |
| 实例、节点、拓扑 | `pilot.db` | 继续作为控制面权威状态 |
| 告警、任务、备份、审计 | `pilot.db` | 保存具体事件、状态流转和操作记录 |

Prometheus 采用拉取模型：Agent、Server、Proxy 暴露 `/metrics`，由 Prometheus 定时抓取；
H5 不直接访问 Prometheus，而是始终经过 Server 鉴权和查询聚合。

## 3. 信息架构

### 3.1 左侧全局导航

左侧导航用于跨实例发现问题和集中运维，按能力成熟度逐步开放：

```text
总览
实例管理
性能分析
告警中心
运维中心
服务器节点
操作审计
```

| 模块 | 主要职责 | 计划阶段 |
|------|----------|----------|
| 总览 | 全局健康、未恢复告警、资源风险、慢查询趋势、近期事件 | P1 |
| 实例管理 | 实例组、拓扑、版本、资源和生命周期操作 | 已有，P1 优化 |
| 性能分析 | 跨实例指标排行、趋势、慢查询和后续 Key 分析 | P1 起 |
| 告警中心 | 当前告警、历史告警、规则、确认和静默 | P1 起 |
| 运维中心 | 备份恢复、异步任务和变更事件 | P2 |
| 服务器节点 | 节点资源、Agent 状态和实例分布 | 已有，持续优化 |
| 操作审计 | 操作者、动作、目标、结果和高风险操作记录 | 已有，持续优化 |

### 3.2 实例组详情

实例详情用于定位和处理单个实例组的问题。随着能力增加，应由当前弹窗升级为独立详情页：

```text
概览 | 性能趋势 | 慢查询 | Key 分析 | 拓扑 | 参数配置 | 备份 | 事件
```

全局页和实例详情允许出现相同能力，但视角不同。例如，全局慢查询用于发现慢查询最多的实例，
实例详情中的慢查询用于分析该实例组的趋势、节点和命令明细。两处应复用查询接口和页面组件。

## 4. 优先级路线

优先级表示实施顺序和依赖关系，不代表需要同时启动所有工作。每个阶段应在上一阶段形成可用
闭环后再进入下一阶段。

## P1：可观测基础闭环

### 目标

让 Redis Pilot 从实例管理看板升级为可用于日常第一次排查的运维控制台。

### 范围

1. **实例详情独立页**
   - 建立概览、性能趋势、慢查询、拓扑、备份、事件等页签框架。
   - 保留现有实例生命周期和备份操作，改善深层信息的承载能力。

2. **历史性能趋势**
   - Agent、Server、Proxy 暴露 `/metrics`，Prometheus 负责抓取和保留。
   - Server 提供指标查询网关，将业务指标翻译为受控 PromQL。
   - QPS、连接数、阻塞连接。
   - 内存使用率、峰值、碎片率。
   - Key 数、命中率、过期和淘汰数量。
   - 网络输入/输出流量。
   - 主从链路状态和复制延迟。
   - RDB/AOF 状态；Kvrocks 增加 RocksDB/Compaction 核心状态。
   - 支持最近 1 小时、6 小时、24 小时和 7 天查询。

3. **慢查询中心**
   - Agent 增量采集 `SLOWLOG GET`，Server 持久化并提供查询接口。
   - 慢查询新增数量和受控的命令维度进入 Prometheus；完整明细只进入 `pilot.db`。
   - 支持时间、实例组、节点、命令和关键字过滤。
   - 提供数量趋势、命令聚合和日志明细。
   - 命令参数默认脱敏，避免在 H5、日志和数据库中扩散敏感数据。
   - 清楚说明慢日志耗时不包含客户端网络和 Proxy 排队时间。

4. **基础告警事件**
   - 首批覆盖实例不可达、主从断链、复制延迟、内存或连接数高、慢查询突增、
     磁盘不足和备份失败。
   - 告警具有产生、持续和恢复状态，并保留历史记录。

5. **总览升级**
   - 展示未恢复告警、风险实例排行、节点资源风险、慢查询趋势和近期变更。
   - 从总览异常项可以进入对应实例详情和关联时间范围。

### 非目标

- 不在 P1 提供任意 PromQL 查询和 Dashboard 编辑器。
- 不在 P1 将高频指标写入 SQLite 或实现第二套时序存储。
- 不在 P1 实现复杂通知升级、审批流或机器学习预测。
- 不在 P1 实现高成本、常态化的全量 Key 扫描。

### 验收标准

- 遇到常见 Redis 性能或可用性异常时，无需先登录服务器或打开 Grafana，即可完成第一次排查。
- 用户可以从全局异常进入实例，在同一时间范围内查看指标、慢查询、拓扑和近期事件。
- 慢日志不会因 Redis 环形缓冲区覆盖而在平台中丢失，且重复采集不会产生重复记录。
- Prometheus 不可用时，控制面操作不受影响；性能页面应明确显示指标数据源不可用。

## P2：统一运维中心

### 目标

集中管理跨实例的日常任务和恢复能力，减少逐个进入实例操作的成本。

### 范围

- 全局备份视图：最近备份、失败备份、未配置策略的实例和恢复点时间线。
- 任务中心：统一展示创建、备份、恢复、故障转移、配置变更、扫描和迁移任务。
- 任务状态：排队、运行、成功、失败、取消，包含进度、耗时、失败原因和有限重试。
- 统一事件时间线：关联告警、启停、配置、故障转移、漂移修复、备份和审计记录。
- Webhook/飞书通知、告警确认、简单静默和维护窗口。

### 验收标准

- 用户能在一个入口确认当天失败任务、未覆盖备份的实例和未处理告警。
- 所有异步或高风险操作都能查询执行状态、结果和对应审计记录。

## P3：Redis 专项诊断

### 目标

平台不仅展示指标，还能给出 Redis 语义化的候选原因和处理方向。

### 范围

- 大 Key 分析：使用限速 `SCAN`，展示类型、估算大小、成员数和 TTL；任务可取消。
- 热 Key 分析：先提供受控的短时采样，后续评估通过 Proxy 统计并限制 Key 基数。
- 无 TTL Key、即将集中失效 Key 等风险分析。
- 客户端连接分析：来源、连接名、空闲时间、数据库、订阅、事务和阻塞状态。
- 一键诊断：汇总指标、慢查询、Key、复制、持久化和近期变更，按规则输出结论与建议。

### 非目标

- 禁止使用 `KEYS *` 完成分析。
- 第一版诊断以透明、可验证的规则为主，不以接入大模型作为交付前提。

### 验收标准

- 对 QPS 下降、内存升高和请求变慢等常见问题，平台能给出带数据依据的候选原因。
- Key 分析任务的资源消耗受控，不明显影响生产请求。

## P4：全链路可观测与配置治理

### 目标

覆盖客户端到 Proxy、数据节点和宿主机的访问链路，并降低配置误操作风险。

### 范围

- Proxy 请求量、错误率、P50/P95/P99 延迟、重连、超时和后端连接池状态。
- 主库/副本请求比例、命令类别分布、拒绝命令次数和拓扑快照版本。
- 参数当前值、默认值、生效方式、修改 Diff、配置历史和回滚。
- 高风险参数保护以及重启影响提示。
- 内存和磁盘增长趋势、预计耗尽时间、节点分布和扩容/迁移建议。
- Redis/Kvrocks、Agent、Server 和 Proxy 运行日志的关联查询与下载。

### 验收标准

- 用户能够区分异常发生在客户端访问、Proxy、Redis/Kvrocks 数据节点还是宿主机。
- 配置变更具备明确影响说明、差异、审计和可执行的回退路径。

## P5：平台治理与高级可靠性

### 目标

支持多人、安全、可追责地长期管理生产 Redis/Kvrocks。

### 范围

- 用户、角色和按实例组或环境划分的权限。
- 高风险操作审批、操作原因和工单号。
- ACL 管理、密码轮换和危险命令策略。
- 告警升级策略、SLO 和可用性统计。
- 控制面自身监控和高可用性建设。
- Prometheus 长期存储扩展、Grafana 深链和更长周期的数据保留。
- 版本升级、批量滚动操作、扩缩容、跨节点迁移和灾备演练。

### 验收标准

- 不再依赖多人共享管理 Token；权限、审批、执行和审计链路完整。
- 平台本身的不可用、采集延迟和任务积压能够被监控和告警。

## 5. 阶段依赖

```text
P1 可观测基础
 ├─> P2 运维任务与事件统一
 └─> P3 Redis 专项诊断
          └─> P4 Proxy 全链路与配置治理
                    └─> P5 权限、SLO 与平台化
```

- P2 的统一事件模型依赖 P1 的告警和指标时间范围。
- P3 的诊断需要 P1 的历史指标、慢日志和告警作为证据。
- P4 的全链路分析需要先稳定实例侧指标语义和查询接口。
- P5 的审批和权限应覆盖已经稳定的运维动作，不宜在功能边界频繁变化时先行建设。

## 6. P1 推荐交付切片

P1 建议拆成连续、可独立验收的五个切片：

1. 实例详情路由、页面骨架和现有功能迁移。
2. Agent/Server/Proxy 指标暴露、Prometheus 抓取配置和历史查询 API。
3. 性能趋势页面以及总览核心指标联动。
4. 慢日志增量采集、去重、脱敏、查询和 H5 展示。
5. 基础告警规则、事件状态流转以及总览/实例事件关联。

P1 技术方案见 `docs/architecture/observability.md`。实现过程中还应同步更新：

- `docs/architecture/overview.md`
- `docs/architecture/components.md`
- `docs/architecture/flows.md`
- `docs/architecture/deployment-ops.md`

技术设计至少覆盖指标采集模型、Prometheus 查询网关、慢日志游标和去重、脱敏边界、告警
状态机、查询 API、数据保留策略和容量估算。

## 7. 待确认事项

以下产品决策仍需在开发前确认：

1. 实例详情采用独立路由页面，还是先使用全屏抽屉作为过渡。
2. 首批告警是否只在平台内展示，还是 P1 同时交付飞书/Webhook 通知。
3. 慢查询命令参数采用全量隐藏、按命令脱敏，还是提供具备权限控制的临时查看能力。

以下数据决策已经确认：

- Prometheus 是 P1 指标存储的运行依赖，不提供 SQLite 指标后端。
- Prometheus 指标默认保留 30 天，抓取周期默认 30 秒。
- 慢查询明细默认在 `pilot.db` 保留 30 天；慢查询数值趋势进入 Prometheus。
